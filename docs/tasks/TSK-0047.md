## Goal

For native Windows deterministic verification commands only, prevent `VerificationCommandResult` from being accepted until the root process has exited, both stdout/stderr have been captured completely and strictly decoded, and the verification command's owned Windows Job is proven quiescent. Bound application-level execution and cleanup waits, fail closed on all uncertain process ownership, I/O, cancellation, Job accounting and resource-release states, and terminate only processes assigned to Jobs exclusively created for this invocation. Preserve the existing completed-command result, error, Task authority and non-Windows contracts. Deliver in separately authorized MANUAL slices after required canonical publication; this umbrella draft is not an invocation, an executable S/M Task Spec, repository publication, implementation, or merge authorization.

## Scope

1. Introduce an internal native-Windows-only verification execution boundary called solely from `_run_one_verification_command()` for deterministic Task checkpoint and Full Verification commands. The exact approved `("python", ...)` first-token interpreter substitution remains in the orchestrator, never in approved command/evidence. All other command tokens remain unchanged. Retain original `cwd=config.repo`, effective inherited environment, shell-free execution, stdin inheritance and ordinary Windows executable/argv resolution semantics; cover empty, spaced, quoted and Unicode arguments. **Do not** assume that `lpApplicationName=argv[0]` automatically preserves CPython search semantics.
2. Create one fresh unnamed `J_supervision` and one nested command `J_command` per verification invocation; set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` for both, do not permit breakaway or mutate an external Job. H owns the last main handles; W receives only non-inheritable termination-limited `J_command` copy. H is not a member of either new Job. Place W atomically in `J_supervision` and payload atomically in `[J_supervision, J_command]` via `STARTUPINFOEX`/`PROC_THREAD_ATTRIBUTE_JOB_LIST` before any execution. Create both suspended, validate ownership/membership and remaining deadline before resuming. No uncontained fallback or alternate launcher.
3. Transfer each native handle explicitly, with single per-table owner and checked close. Pass Job/IPC/server handles to W using `DuplicateHandle` and non-inheritable copies, never into payload. Payload's `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` contains only whitelisted stdin/stdout/stderr inheritable duplicates. Close all H write-side pipe references after successful `CreateProcessW`, before resume; errors make lifecycle uncertain. Do not change the caller's stdin handle or allow concurrent broad-inheritance launches to expose temporary inheritable handles; record the residual cross-thread handle-inheritance risk.
4. Use two private local overlapped named-pipe instances for payload stdout and stderr; no `CreatePipe()` anonymous overlapped-read claim. Each `CreateNamedPipeW` uses `PIPE_ACCESS_INBOUND | FILE_FLAG_OVERLAPPED | FILE_FLAG_FIRST_PIPE_INSTANCE`, byte-type/read-mode, `PIPE_WAIT | PIPE_REJECT_REMOTE_CLIENTS`, max instances 1 and a non-inheritable server handle; nominal input buffer 65536, output buffer 0. Unique `\\.\pipe\wvc.<run_uuid>.<nonce>.<stdout|stderr>` names are generated once, collision is terminal. Set explicit current-logon-SID restricted security descriptors (not relying on random names or default ACL), and do not modify existing ACLs. H connects exactly once via synchronous `CreateFileW` write-only clients, `OPEN_EXISTING`, no `FILE_FLAG_OVERLAPPED`, non-inheritable and anonymous security QoS. `ERROR_PIPE_BUSY`, collision, unexpected client or denied access is failure without retry/reconnect. W owns both server/read endpoints after checked duplication, runs finite overlapped `ConnectNamedPipe` and `ReadFile` operations with one independent event/OVERLAPPED/buffer per stream, and checks `GetFileType`, `GetNamedPipeInfo`, endpoint creation provenance, and `GetNamedPipeClientProcessId == H` before READY. Support `TRUE`, `ERROR_PIPE_CONNECTED`, `ERROR_IO_PENDING` correctly; no blocking ConnectNamedPipe with NULL OVERLAPPED, `WaitNamedPipe`, `CallNamedPipe` or indefinite wait. Zero-byte read is not EOF without a verified pipe-end condition; no `FlushFileBuffers` as EOF gate.
5. Use exactly two pagefile-backed SPSC shared-memory queues for H ↔ W (one per direction), each with 8 slots of 64-byte header plus at most 65536-byte payload, and exactly two semaphores per queue (`free` initialized to 8; `ready` to 0). Total two-ring slot storage is 1,049,600 bytes, excluding mapping/synchronization/runtime overhead. H creates W suspended and duplicates into W handle table only the required non-inheritable mapping, semaphore, selected pipe and command-termination capabilities. Bootstrap uses per-run private session-local objects; validate identity and handle provenance; never grant these capabilities to payload. Fixed-size transport **does not** bound total captured semantic output memory.
6. The 64-byte little-endian IPC frame header contains: magic `WVC1` (4 bytes); protocol version uint16 (2); type uint16 (2); run UUID (16); per-direction sequence uint64 (8); per-stream offset uint64 (8); payload length uint32 (4); stream id uint8 (1: control, stdout or stderr); flags uint8 (1, must be 0 initially); reserved (18, all zero). Sequence starts at 0 in each direction and increments by one without wrap. Reject unknown type/version/UUID/stream/flags, malformed lengths, control payload >4096 bytes, duplicate/out-of-order offsets, data after EOF, duplicate EOF or unrecognized control state. DATA is 1..65536 raw bytes; control frames (`INIT`, `READY`, `ROOT_CREATED`, `FINISH`, `ACK`, `ERROR`, `CANCEL`) and an explicit stream-terminal `EOF` frame have strict bounded UTF-8 structured bodies, decoded with duplicate-field rejection and exact per-type required field sets. Control data must never contain raw stdout/stderr, prompts, environment, credentials or exception text. EOF supplies actual per-stream byte length and SHA256 for comparison against the accumulated raw bytes. W → H DATA interleaving across streams is allowed, but byte offsets in each stream are contiguous. A semaphore/slot publication counts only after checked `ReleaseSemaphore(ready)`. Any abnormal `WaitForSingleObject`/semaphore release, inconsistent sequence, interrupted frame, incomplete stream or peer crash fails closed; no unbounded IPC waits.
**IPC wire grammar for subsequent independent approval.** Use one closed uint16 type table: `INIT=1`, `READY=2`, `ROOT_CREATED=3`, `DATA=4`, `EOF=5`, `FINISH=6`, `ACK=7`, `ERROR=8`, `CANCEL=9`. Stream IDs are `control=0`, `stdout=1`, `stderr=2`. `DATA` and `EOF` require stdout/stderr; all other frames require control. `DATA` is raw (not a JSON/control payload) and has contiguous offset. `EOF` is a bounded control payload with exactly `total_bytes` (uint64) and `sha256` (lowercase 64-character hexadecimal string); its header stream offset equals `total_bytes`, and the verifier checks length and SHA256 over received raw DATA. Only `EOF` terminates a stream; `ERROR`/`CANCEL` never count as EOF.

**Closed control-payload sets for subsequent independent approval.** Serialize each object as strict UTF-8 JSON, reject duplicate/unknown/missing keys and wrong JSON types; use uint64 nanoseconds only for monotonic timing values and prohibit raw handles, tokens, paths and transcripts. Required keys: `INIT` = `run_uuid`, `deadline_ns`, `cleanup_budget_ns`, `worker_pid`; `READY` = `worker_pid`, `stdout_ready`, `stderr_ready`; `ROOT_CREATED` = `root_pid`, `created_suspended`; `FINISH` = `root_pid`, `root_exit_code`, `command_quiet`; `ACK` = `pending_io_zero`, `capture_handles_closed`; `ERROR` = `stage`, `category`, `winerror`, `errno`, `timed_out`, `cleanup_confirmed` (numeric errors may be null); `CANCEL` = `reason`. UUID in control body must agree with frame header, and enum strings `stage`/`category`/`reason` must come from a closed diagnostic allowlist. This schema is a **proposed binding detail requiring independent contract review**, not a claim that earlier reviews approved specific numeric frame IDs or JSON key names. H validates actual process/Job/handle facts independently of these assertions.

7. The normal message sequence is `BOOT → INIT → READY → ROOT_CREATED → STREAMING → both validated EOF → FINISH → ACK → W exit 0`. H creates and validates the suspended payload and closes its own writer copies before resume; `ROOT_CREATED` precedes resume. W may send DATA concurrently for each stream, with fair event-loop servicing of both reads, H/W process handles, control messages and deadlines. When a ring is full W stops issuing new capture reads for that stream rather than buffering indefinitely; normal pipe backpressure is permitted. ACK is W's last frame and means all pending capture I/O retired and capture handles closed. H can only accept a verification result after both full streams, exact lengths/hashes, valid ACK, actual W exit code 0, actual payload exit code, stable command/supervision quiescence and checked final H closes. W's returncode is never reused as the command returncode.
8. Use one monotonic execution deadline `D_execution = t0 + config.verification_timeout_seconds`, where `t0` is immediately before entering the Windows backend, including preflight, startup, IPC bootstrap/connect, payload creation, execution, descendant exit and output capture/validation. Do not restart the clock after root exit or I/O progress; check deadline before and after native operations, before resume and after each bounded event-loop iteration. Execution success must be fully established strictly before `D_execution`. `ReadFile`, `ConnectNamedPipe`, IPC semaphore waits, handle waits and finalization must never use unconditional `INFINITE` or unbounded `join`/`communicate`; pending native synchronous calls are **not** claimed preemptible. W watches the command deadline independently of H progress and can request `TerminateJobObject(J_command)` with its restricted handle.
9. On execution timeout or error, terminate **only** owned Job process membership and enter a separate cleanup deadline. Fix cleanup budget at **5 seconds**, non-renewable by secondary errors. On timeout, `D_cleanup = D_execution + 5s` (not five seconds after late discovery). On other error, `D_cleanup = first_failure_timestamp + 5s`. After normal execution completion timestamp `E < D_execution`, finalization uses `D_cleanup = E + 5s`; these five seconds are for mandatory finite resource retirement and final quiet checks, not permission to extend semantic execution or generate new output. At cleanup timeout, no result can be fabricated. Initial cooperative I/O cancellation can use no more than the first half of remaining cleanup budget; escalate immediately on fatal fault/peer crash, otherwise to owned supervision Job when cooperative cleanup is unconfirmed. Preserve the initial timeout (`TimeoutExpired` as cause of `RepositoryError`) and separately report bounded cleanup uncertainty. Underlying Windows API returns, cancellation or OS termination latency are not promised hard real-time.
10. Quiescence requires H to seal its own creation/assignment phase (all launches returned, no in-flight `CreateProcessW`, no new assignments and no assignment capabilities exported), then two complete consecutive accounting samples strictly before the relevant deadline. In each sample check `ActiveProcesses==0`, stable `TotalProcesses`, confirmed exited retained process handles (including explicit `WAIT_FAILED` handling), and repeat accounting query; change of membership or unknown/incomplete accounting invalidates/reset stability. Root exit alone, PID identity alone, completion-port notifications alone, one empty Job sample, empty Job with signaled status unknown or a quiet sample at/after deadline never proves quiescence. `J_command` and final `J_supervision` have their own verified quiet requirements; H never queries or terminates the existing external Job. Retain process handles until exit/code have been recorded; checked releases cannot be used to guess exit.
11. `CancelIoEx` on a specific overlapped connect/read is a **request**, not completion. Track each operation's event, buffer and OVERLAPPED through normal completion, `ERROR_IO_PENDING`, cancel request, normal completion racing with cancel, `ERROR_OPERATION_ABORTED`, `ERROR_NOT_FOUND`, `ERROR_IO_INCOMPLETE`, and cancellation that remains unconfirmed at cutoff. Poll `GetOverlappedResult(..., bWait=False)` or an equivalent finite completion mechanism; never free/reuse a buffer with I/O pending. If cancellation cannot retire, W must not unwind/free Python/native buffers as if completed; abort W through the owned supervisory termination mechanism. H never waits indefinitely for pending worker I/O.
12. The only public completed-result shape remains `VerificationCommandResult(command=<original approved argv>, returncode=<real root code>, stdout=<full decoded stdout>, stderr=<full decoded stderr>, passed=(returncode==0))`. Keep strict UTF-8 on **both** streams, including Unicode and CRLF/CR universal-newline normalization previously supplied by Python text mode, with no lossy replacement or success truncation. Real negative/259/nonzero exit codes must not be confused with pending wait states. Preserve completed nonzero as candidate rejection. Timeout/launch/Job membership/query/wait/IPC/capture/UTF-8/cancellation/cleanup/mandatory-close uncertainty raises existing `RepositoryError`, without any synthetic `VerificationCommandResult`, reviewer, candidate repair, retry or resume. Windows-specific internal structured `OSError` records safe bounded fields (stage, category, WinError/errno, deadline/cleanup flags) without raw transcript or environment data. Timeout must retain `TimeoutExpired` causality even if cleanup also fails.
13. Native-Windows-only fail-closed behavior. On other platforms continue using the current unchanged `subprocess.run` branch and preserve its direct regression tests. No dynamic import of Win32 code on non-Windows branch. Windows failures never fall back to current uncontained `subprocess.run`. Do not change `run_agent()`, Codex CLI/MXC, Git/GitHub subprocesses, repository fingerprint logic, approval/repair/routing/reviewer/CI/merge rules, persistence, or game engine.
14. A crash of H closes its last owning `J_supervision` reference, initiating termination of W and command membership; completion/quiescence is not inferred solely from handle close. A live W watches H's retained process handle and the deadline; a crashed/hung W is observed by a responsive H and triggers Job cleanup. If H is blocked indefinitely in an uninterruptible native call, its return within `T+5s` is **not guaranteed**. Do not create a third supervisor, assert global process-tree containment outside Job, claim rollback of subprocess side effects, or claim fixed total output memory. A protective extra Job must not intercept/kill unrelated external processes.
15. Before any implementation, separately review, authorize and publish the new Windows-verification-only containment contract in canonical process documentation; append the architectural rationale to `docs/DECISIONS.md` and the applicable `docs/ARCHITECTURE.md` cross-reference without altering gameplay contracts. Explicitly document that TSK-0046's historical scope remains unchanged; the new TSK supplies additional internal owned-resource cleanup. Keep `docs/ROADMAP.md` unchanged unless a real Roadmap-scope contradiction requires separate decision. Update `docs/AUTONOMOUS_PR_OPERATOR.md` terminal and safety guidance, and one concise `docs/DEVELOPMENT_LOG.md` entry on closure. ## Approved implementation approach

**Governance / authority.** This section expresses the explicitly accepted design direction, not task execution approval. Before code, gate C0 separately publishes the new canonical process contract through the normal reviewed MANUAL documentation process; implementation tasks may depend upon that contract only after publication on `main`. A delivery branch must not be treated as canonical publication. Deliver implementation MANUAL only, on a dedicated non-main branch. This document remains `draft` and is provisionally size `L` because it combines native process/Job creation, an IPC wire protocol, cancel-safe overlapped I/O, independent monitoring and production integration; `docs/TASK.md` permits approval only at size `S`/`M`. Decompose into independently reviewable and mergeable slices before approval, retaining all 19 cross-slice acceptance scenarios and the C0/C2 authorization gates. No commit/push/PR/merge is authorized by this planning document.

**Architecture / state ownership.** H is the existing orchestrator and sole owner of main `J_supervision`/`J_command`, worker/payload process/thread handles, primary and temporary pipe writers, main IPC references and deadline state. W is the only owner of pending OVERLAPPED/events/buffers, duplicated pipe readers, restricted `J_command` termination copy and worker IPC references. Payload and ordinary descendants inherit only whitelisted standard streams and belong to the dedicated Jobs. Ordinary Job creation via an already externally nested Job must either validate correct nesting/ownership or fail before payload resumes. H may request command termination; W independently requests termination by deadline. No component terminates arbitrary unrelated PIDs.

**Required module boundaries.** Keep orchestrator wiring minimal. Introduce a Windows-only adapter (`tools/autonomous_pr/windows_process.py` or equivalently named narrowly scoped internal module) that owns H-side job/worker/IPC/result orchestration, and a private `tools/autonomous_pr/_windows_verification_worker.py` for overlapped capture/deadline monitoring. Do not import either on non-Windows execution. Unit tests may exercise isolated pure frame/accounting/deadline helpers without launching native processes. No general process framework or cross-provider module.

**Start/resume transaction.** All Job/pipe/IPC/worker preflight checks and native ABI validations occur before payload resume. H creates W through atomic `JOB_LIST` while suspended; endpoint handles/capabilities are duplicated to W and H closes its copies with checked calls. W connects both overlapped named pipes and proves both client identities; READY requires prepared independent reads. H atomically creates payload suspended inside both Jobs, grants only allowed handles, confirms membership and final deadline then emits ROOT_CREATED and resumes at most once. On any failure all suspended owned processes undergo Job cleanup; there is no alternate uncontained retry.

**IPC contract.** Exactly two SPSC rings, the fixed `WVC1` 64-byte header and frame types stated under Scope. Per-direction sequencing and per-stream contiguous offsets are mandatory. Control message schema is bounded and closed to known stage-specific fields; encode only numeric process/deadline metadata and booleans plus run UUID. In INIT, communicate run UUID, execution/cleanup deadline values, worker identity and expected capabilities; READY confirms stream capability checks; ROOT_CREATED communicates suspended payload identity and lifecycle stage; FINISH requires all two EOFs and root/Job quiet; ACK reports pending-I/O retirement and checked closes. ERROR/CANCEL provide only allowlisted category/stage/numeric error metadata. In all cases validate actual caller-owned process/handle state independently; frames are not an authority source for Job or exit status.

**Deadlines and finalization.** `monotonic_ns()` (or an equivalent monotonic Windows counter) measures absolute deadlines. Progress never renews budgets. Event loops use finite waits and service control/peer liveness even under output backpressure. Primary execution outcomes are not accepted from completed/nonzero root exit alone; full capture, strict decode and command quiescence are prerequisites. After normal execution completion E, finalization is bounded by E+5 seconds. On timeout the cleanup cutoff is D_execution+5 seconds. A delayed native call can make cleanup impossible before that cutoff; this is reported as terminal uncertainty without pretending to have observed quiescence. Any failure in mandatory handle close or final ownership checks is terminal even after root returncode 0.

**Failure categories.** Internal `WindowsVerificationError(OSError)` with bounded `stage`, `category`, numeric `winerror`/`errno`, `timed_out`, `cleanup_confirmed`, plus monotonic timestamps; mapping in orchestrator remains terminal `RepositoryError`. When timed out, preserve a real `TimeoutExpired` as the primary causal exception and project secondary cleanup uncertainty without leaking external text. No new persistent state, public error enum, or synthetic returncode.

**Testing and staged review.** For every new native Win32 operation, test ABI size/flags/ownership and fault injection without launching payloads. Controlled Windows-native tests require separate explicit operator approval, a dedicated safety owner, bounded waits and unrelated-process sentinel. All such tests must run only after independently reviewed native layer. Native Job/process tests belong in a separate opt-in test module and are excluded from default full pytest and unapproved CI runs; the opt-in run must demonstrate actual non-skipped execution rather than treating skipped tests as passing evidence. Implementation checkpoints are independent review-risk boundaries; a failed checkpoint stops manual progression. Full pytest, configured mypy, diff review and relevant documentation checks remain necessary before final acceptance.

7. Failed, incomplete or inconsistent Job accounting/query prevents quiescence and completed evidence.
8. `WAIT_FAILED` or unknown exit on a retained process handle prevents quiescence, including a signaled-but-code-unknown handle.
9. An empty Job with any live retained handle is insufficient for successful quiescence.
10. A second quiet sample whose completion occurs at or after the absolute deadline is insufficient for acceptance.
11. Membership/accounting changes between samples reset stability; a logical assignment seal is required before final samples, and `TotalProcesses` is checked across samples.
12. Mandatory close, pipe/connect/read cancellation or capture-finalization uncertainty after root exit code 0 prevents success. A successful `CancelIoEx` request alone is not completion; buffers stay alive until retirement or W is terminated.
13. Large interleaved stdout/stderr with inherited stdin and IPC saturation cannot deadlock, corrupt, truncate or mis-order semantic streams; backpressure is bounded in transport, and no new input protocol is introduced. Exhaustion of memory is not converted into partial success.
14. Invalid UTF-8 in either verification output stream is terminal execution uncertainty, never lossy evidence or repair.
15. H crash initiates owned `J_supervision` kill-on-close without terminating unrelated processes, and parent/worker stall limitations are explicitly reflected in expected outcomes. Native crash test requires independent safety supervision.
16. An existing outer Job either permits validated nested containment or causes failure strictly before payload resume; no modification of the outer Job, breakaway or fallback.
17. Non-Windows execution remains original `subprocess.run` with identical kwargs and original failure mapping, including the existing tests.
18. Public diagnostics contain only bounded allowlisted metadata and never raw stdout/stderr, environment variables, prompts, credentials, full argv or provider/MXC internals. Internal control frames also obey the same no-transcript rule.
19. Verification-only containment neither implies MXC/agent containment nor authorizes Probe A; static call-site and documentation checks confirm `run_agent()` and its security profiles unchanged.

## Execution checkpoints

## Known constraints / edge cases

- The accepted design decision is verification-only containment for a finite, owned Windows Job; it is not yet an authoritative published repository contract and is not universal process-tree security. Windows Job containment does not guarantee containment of processes created by a foreign broker or every descendant outside assigned membership. Process termination does not undo filesystem/network side effects. No MXC or real agent behavior was tested by Probe B.
- A Job cannot be treated as empty solely because the immediate child exited, all pipe ends closed, a single active-process accounting query returned zero, or one `TerminateJobObject` succeeded. Two samples are a conservative observation protocol, not absolute proof of future OS state; the assignment-seal invariant prevents new assignments by this harness after closure.
- A kill-on-close flag initiates termination when the last relevant Job handle closes; do not leak an additional handle capable of preventing this. If both H and W stop progressing or native calls stall, hard bounded OS completion/API return is not guaranteed. The 5-second cleanup is the limit on application-managed wait attempts, not a guarantee that kernel cancellation/termination completes within five seconds.
- Named server pipes must be actually overlapped; anonymous `CreatePipe` handles are not overlapped and cannot support the specified cancellation discipline. An H client opened synchronously is permissible: W uses overlapped server reads. Unexpected client, inherited handle, endpoint identity or object creation failure is terminal.
- Windows temporary inheritable stdin/stdout/stderr handles may have an inheritance race with other concurrent broad-inheritance process creation in H. Minimize inheritance interval; the controlled boundary must not launch such competing processes. There is no claim of absolute isolation against arbitrary unrelated threads in the same process.
- `CancelIoEx` requests cancellation but does not wait for completion; closing an operation's Python buffers before its I/O completion is unsafe. If retirement cannot be confirmed, do not unwind the worker as though normal cleanup succeeded.
- Per-frame 65536-byte payload and two fixed 8-slot rings bound transport storage only. Full captured stdout/stderr remain intentionally unlimited in aggregate; memory/resource exhaustion cannot produce truncated `VerificationCommandResult`. No new successful-semantic output limit or memory bound is introduced in this task.
- Existing `subprocess.run(text=True, encoding="utf-8")` applies universal newline normalization; returning raw `.decode('utf-8')` text is not sufficient to preserve the contract. Stream integrity hashes cover raw bytes before strict decode/normalization.
- Existing Windows process creation, `sys.executable` substitution, executable search, `cwd`, environment and stdin behavior must be preserved; passing the first token directly as explicit `lpApplicationName` may change search semantics. Reject unsupported parity rather than silently run different commands.
- `ERROR_PIPE_CONNECTED` is not an unsignaled pending operation; `ERROR_IO_PENDING` must be completed or canceled through a finite wait. Byte-pipe `ERROR_MORE_DATA` and repeated zero-length reads should not be used to manufacture EOF.
- Cleanup duration and resource closure are distinct from execution timeout; a normal root exit may still leave a descendant that naturally finishes within remaining execution budget. On timeout or non-quiescence, no completed result is manufactured even when the root code is zero.
- Task sizing and decomposition are blocking before approval: this umbrella draft is `L`, not execution-ready `M`; the total scope requires at least independent review of (a) C0 contract publication, (b) isolated Windows ownership/capture/lifecycle backend with native C2 validation, and (c) verification-only integration and regressions. Keep the accepted scope exclusions, publication/authorization barriers and acceptance cases 1–19 across derived task documents; do not silently drop safety tests or invoke unapproved native verification. The proposed numeric IPC type IDs and exact control schemas above require independent semantic acceptance before being promoted into a binding approved Task.
- Manual C0 contract publication and independent checkpoint review precede production wiring; CP-4 native test approval is separate. Approval of this draft, production code commit/push, PR, CI/merge and any re-run of diagnostic Probe B each require separate explicit user authorization. `docs/TASK.md` terminal rows are added only on factual reviewed closure; do not infer task `Done` from this file or planning conversation.
