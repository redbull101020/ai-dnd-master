## Goal

Устранить подтверждённый structural evidence-handoff gap operational `AUTONOMOUS_PR` v2 на границе Mode C, не расширяя authority, review semantics, repair policy, publication policy или gameplay scope.

Initial unpublished Mode C и post-publication Mode C replay должны получать authoritative Full Verification и accepted cumulative-review facts из уже существующего typed orchestration state. Эти факты должны детерминированно подтверждать fixed Task Execution Spec, historical accepted implementation base, exact verified implementation HEAD, cumulative-review identity и связь verified implementation HEAD с `UnpublishedCommitCandidate.published_predecessor_sha`.

Mode C при этом обязан отдельно различать historical accepted implementation base и current fresh Mode C audit base. После допустимого движения `origin/main` current audit base может измениться без изменения уже verified implementation HEAD; такое различие само по себе не делает evidence stale. Material task/closure movement по-прежнему должен fail closed через существующую revalidation semantics.

Задача не утверждает, что отсутствие Full Verification evidence было непосредственной причиной explicit `BLOCKED` во втором production TSK-0032 pilot: terminal result сохранил только generic reviewer-blocked reason, а semantic rationale designated reviewer не был сохранён. TSK-0034 исправляет независимо подтверждённый Mode C evidence-handoff gap до следующего production pilot.

## Context / References

Документ подготовлен по актуальному `main` commit `9cac3bd009934c9b409e71e9de49d85a8ad1a31b`. На этой базе TSK-0033 authoritative `Done` через PR #112, TSK-0032 остаётся approved nonterminal task, а `TSK-0034` является свободным task ID.

Второй production TSK-0032 pilot после TSK-0033 прошёл CP-1 designated review, Full Verification, pre-closure cumulative implementation review и prospective Task Closure review. Эти артефакты являются forensic evidence, а не resumable run state или execution input TSK-0034.

Актуальный Mode C data flow имеет подтверждённый structural gap. `_build_v2_mode_c_review_input(...)` требует от fresh designated reviewer проверить полный final cumulative candidate, включая every checkpoint и Full Verification, но получает fixed Task Execution Spec, current audit base/candidate identities и exact final cumulative patch без authoritative Full Verification/cumulative evidence. `_review_v2_mode_c_candidate(...)` также не принимает accepted pre-closure evidence. Post-publication `_stabilize_v2_published_candidate(...)` повторно вызывает Mode C после допустимого движения `origin/main`, но тоже не получает typed pre-closure evidence.

TSK-0033 уже добавила deterministic prospective-closure evidence validation и compact evidence projection. При этом существующая closure semantics намеренно связывает outer `V2ImplementationEvidence.base_identity` с текущим pre-closure context. Во время Mode C revalidation этот outer base может быть обновлён на новый `origin/main`, тогда как nested `V2FullVerificationEvidence.base_identity` и `V2CumulativeReviewEvidence.base_identity` продолжают описывать historical implementation base, на котором был принят unchanged implementation HEAD. Поэтому Mode C не может корректно переиспользовать closure validator как есть: ему нужна отдельная gate-specific validation semantics, различающая historical implementation base и current audit base.

`UnpublishedCommitCandidate.published_predecessor_sha` уже является implementation HEAD непосредственно под closure commit и exact remote delivery-branch HEAD до publication. Existing `repository.verify_unpublished_commit_candidate(...)` и `repository.verify_published_commit_candidate(...)` доказывают branch/HEAD/tree/remote facts; TSK-0034 должна добавить missing cross-layer relation между этим predecessor и accepted Full Verification/cumulative implementation HEAD, а не дублировать repository validation.

## Scope

1. Выделить или переиспользовать минимальную private deterministic validation logic для immutable accepted-implementation facts, общих prospective Closure и Mode C: fixed spec identity, Full Verification success, historical implementation base, exact verified implementation HEAD, exact approved Full Verification argv set, accepted cumulative-review identity и reviewed HEAD.
2. Сохранить existing prospective-closure semantics TSK-0033. Если common validator выделяется из `_format_validated_v2_closure_evidence(...)`, closure-specific checks и compact output должны остаться поведенчески совместимыми.
3. Добавить gate-specific Mode C evidence validation поверх current typed orchestration state, не используя старую prompt string как authoritative cross-gate state.
4. Явно различать `accepted_implementation_base` из nested Full Verification/cumulative evidence и current `mode_c_audit_base`, используемый для exact final cumulative `origin/main...candidate` patch.
5. Не требовать равенства historical implementation base и current Mode C audit base после успешно revalidated unrelated `origin/main` movement.
6. Детерминированно требовать, чтобы `full_verification.head_sha`, nested `VerificationEvidence.head_sha`, `cumulative_review.reviewed_head_sha` и `candidate.published_predecessor_sha` идентифицировали один accepted implementation HEAD.
7. Проверять, что Full Verification command sequence точно равна fixed `spec.full_verification`, каждая command сохранила original approved argv и имеет successful `returncode`/pass fact, а cumulative-review candidate identity/patch identity остаются согласованными.
8. Сформировать fresh compact Mode C evidence projection для каждого designated Mode C reviewer invocation. Representation должна включать selected task/spec identity, actual draft PR number, historical accepted implementation base/head, Full Verification verified HEAD и per-command original argv/returncode/pass facts, accepted cumulative-review identity/head, а также current Mode C audit base.
9. Передать Mode C evidence projection в initial unpublished Mode C reviewer вместе с existing exact `FINAL_CUMULATIVE_AUDIT` patch.
10. Не добавлять отдельный duplicate accepted implementation patch в Mode C review input: exact final cumulative patch уже содержит implementation плюс prospective Task Closure.
11. Явно указать reviewer'у, что prior accepted Full Verification/cumulative facts доказывают provenance и prerequisite facts, но не заменяют fresh independent Mode C material review.
12. Сохранить closure-only repair semantics: новый closure candidate может reuse всё ещё valid accepted implementation evidence, но fresh Mode C projection заново проверяет новый `candidate.published_predecessor_sha`.
13. Сохранить implementation-affecting repair/replay semantics: новый implementation HEAD требует нового downstream Full Verification/cumulative evidence, и старые facts не могут пройти Mode C predecessor/head checks.
14. Провести current accepted implementation evidence через post-publication `_stabilize_v2_published_candidate(...)` или эквивалентный узкий typed handoff, чтобы rebuilt Mode C после `origin/main` movement получал ту же authoritative implementation provenance без persisted run state.
15. Сохранить `GateAttempt.verification = None` для Mode C: Full Verification остаётся upstream evidence, а не gate-local verification attempt, и не должна менять routing/metrics semantics.
16. Fail closed до designated reviewer invocation при missing, failed, stale или internally inconsistent Mode C evidence; LLM не определяет evidence freshness и не исправляет identity mismatch.
17. Не включать successful verification stdout/stderr, machine-specific runtime Python path или parsed test counts в compact Mode C evidence.
18. Синхронизировать `docs/AUTONOMOUS_PR_HARNESS.md` с authoritative Mode C evidence handoff, two-base semantics и post-publication replay behavior. Обновить local comments/docstrings только там, где они становятся неточными.
19. Добавить focused regressions для initial Mode C, closure-only repair, implementation-repair replay, unrelated `origin/main` movement, material movement rejection и post-publication Mode C replay.
20. Выполнить полный tooling/architecture/repository regression для изменения operational harness behavior.

## Approved implementation approach

**A. Delivery and authority boundary.** TSK-0034 реализуется в `MANUAL` на отдельной branch от fresh `main`. Не использовать `AUTONOMOUS_PR NEXT` для доставки этого harness repair. Не менять authority contracts, чтобы harness мог расширить собственные permissions. Commit, push, draft PR и merge выполняются только по отдельной human authorization согласно `AGENTS.md`.

**B. Shared immutable accepted-implementation validation.** Выделить минимальную private validation logic из уже существующей TSK-0033 closure evidence validation только там, где это реально уменьшает duplication. Common validation должна проверять fixed spec identity, согласованный historical implementation base внутри nested Full Verification/cumulative evidence, successful Full Verification, exact original command set, verified implementation HEAD и accepted cumulative-review identity. Она не должна использовать current mutable outer base как historical implementation base.

**C. Preserve prospective Closure behavior.** Existing `_format_validated_v2_closure_evidence(...)` сохраняет свой gate-specific contract. Для Closure current pre-closure base по-прежнему должен согласовываться с accepted implementation context согласно существующей TSK-0033 semantics. Refactor не должен менять closure prompt shape, closure-only repair behavior или уже прошедшие TSK-0033 regressions кроме минимально необходимого internal factoring.

**D. Fresh Mode C evidence projection.** Добавить отдельный private Mode C formatter/validator, который строит compact JSON или эквивалентную deterministic textual projection непосредственно из current typed evidence, actual PR number, current audit base и exact candidate. Не кэшировать ранее сформированную closure/Mode-C prompt string и не превращать projection в persisted schema.

**E. Two-base identity semantics.** Mode C projection явно различает historical `accepted_implementation_base` и current `mode_c_audit_base`. Historical base определяется nested `V2FullVerificationEvidence.base_identity` и `V2CumulativeReviewEvidence.base_identity`; current audit base передаётся из fresh revalidated `origin/main` и совпадает с `ReviewPatch.base_sha`. После разрешённого unrelated main movement эти значения могут различаться. Такое различие допустимо только после существующей successful task/closure revalidation; TSK-0034 не создаёт нового materiality exception.

**F. Candidate predecessor binding.** Перед reviewer invocation orchestrator проверяет `candidate.published_predecessor_sha == full_verification.head_sha == full_verification.verification.head_sha == cumulative_review.reviewed_head_sha`. Existing repository candidate verification продолжает независимо доказывать local/remote branch, HEAD и tree facts. Любой cross-layer mismatch заканчивает gate fail closed до LLM call.

**G. Initial Mode C reviewer handoff.** `_review_v2_mode_c_candidate(...)` или эквивалентная boundary получает authoritative accepted implementation evidence и actual draft PR context. `_build_v2_mode_c_review_input(...)` включает compact evidence рядом с `BASE_SHA`, candidate HEAD/tree и exact cumulative `CURRENT_PATCH`. Prior accepted facts являются evidence prerequisites, а не reviewer verdict hint; prompt обязан сохранить requirement свежего полного Mode C audit.

**H. Repair freshness.** Closure-only repair может reuse unchanged typed implementation evidence, но Mode C projection перестраивается для нового candidate и заново проверяет predecessor/head relation. Implementation-affecting Mode C repair проходит существующий CP-3 replay, создаёт новый implementation HEAD и новые downstream Full Verification/cumulative evidence; Mode C получает только новый current evidence state. Старый accepted HEAD должен deterministic fail при попытке handoff к новому candidate.

**I. Post-publication replay handoff.** Провести current accepted implementation evidence до `_stabilize_v2_published_candidate(...)` минимальным typed способом. При fresh unrelated `origin/main` movement post-publication Mode C строит новый `FINAL_CUMULATIVE_AUDIT` patch от нового audit base к тому же exact published candidate, сохраняет historical implementation evidence и повторяет reviewer invocation. Candidate-changing post-publication repair остаётся existing terminal limitation; TSK-0034 не разрешает remote-history rewrite.

**J. Compact factual evidence only.** Mode C evidence включает original approved argv, return code, pass fact, verified HEAD, accepted cumulative identity/head/base, selected task/spec identity, actual PR number и current audit base. Successful stdout/stderr, machine-local interpreter path, free-form agent output и inferred test counts не включаются. Verification claims остаются provider-neutral и machine-neutral.

**K. Gate/routing semantics unchanged.** Mode C designated reviewer остаётся fresh `CRITICAL`; `GateAttempt.verification` остаётся `None`; prior Full Verification evidence не становится новым routing signal. Existing review iteration, consecutive `CHANGES_REQUESTED`, rejection identity, closure-only repair proof и post-publication limitations не меняются.

**L. Documentation and minimal touch surface.** Expected primary touchpoints: `tools/autonomous_pr/orchestrator.py`, `tests/tools/autonomous_pr/test_orchestrator.py`, `docs/AUTONOMOUS_PR_HARNESS.md`. `model.py` допустим только для маленькой private/provider-neutral immutable value structure, если она заметно улучшает type safety. `agents.py`, `routing.py`, `__main__.py`, `repository.py`, task selection и gameplay modules не менять без выявленного binding requirement; если такой requirement противоречит current scope, остановиться для human decision вместо скрытого expansion.
