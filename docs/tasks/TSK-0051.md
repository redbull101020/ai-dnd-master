## Goal

Implement the published Architecture §3.39 / DEC-0056 first Character voluntary Combat Movement consumer, with explicit authoritative Character walking-speed State and exact additive State schema V11, without changing existing Monster Movement, Command/Event envelopes or turn resources. An active, positioned, positive-HP Character with a supported `walking_speed` must be able to issue the existing `MoveCombatantCommand`, split movement around a normal Attack, persist position and `movement_spent` together, and reload correctly. An absent speed must not be silently inferred as 30 feet. Final artifact must be an independently reviewable Phase 3 gameplay slice and must leave every existing historical State schema reader intact.

This execution-ready specification is approved for implementation **only after** the publication PR containing Architecture §3.39, planned V11 §12.13, DEC-0056 and this approved task is merged to authoritative `main`, and TSK-0040 remains terminal `Done`. The architecture decision was accepted on 2026-11-01; the new behavior is still unimplemented. Task approval and publication do not activate `AUTONOMOUS_PR`: execution requires a separate explicit invocation on a fresh authoritative baseline.

Exact `int >= 0` or `None`; reject `bool`, negatives, floats, strings and containers at construction **and StateSerializer write validation**, including an invalid value introduced by later object mutation. `None` is unknown, zero is a real zero speed; no computed or default speed. This value is initialized only through the trusted application-controlled campaign snapshot setup; no gameplay writer for changing it is introduced.

## Approved implementation approach

1. Treat the published Architecture §3.39, §12.13 V11 and DEC-0056 as the binding decisions; do not treat publication or approval of this specification as permission to invent a different authoritative speed source or invoke execution. The Character `walking_speed` field is appended after the existing `dead` field with default `None`, preserving prior positional callers. It is supplied explicitly by existing initial snapshot setup and read by gameplay, not written through a new gameplay Command. Neither AI nor payload may determine speed.
2. Keep exact strict serializer semantics: `SCHEMA_V11_VERSION=11`, set `SCHEMA_VERSION=SCHEMA_V11_VERSION` **only together with actual V11 implementation**; preserve every fixed historical version sentinel and historical decoding branch. Introduce an exact `_V11_CHARACTER_FIELDS` independent of `_V9_CHARACTER_FIELDS` and update **all current-version branches** in `StateSerializer` that currently enumerate V10: schema validation, V4+ Creature Conditions, V5+ Combat, V6+ Inventory/Equipment and weapon proficiencies, V9+ Character death-save/lifecycle and V10 Combat `movementSpent`. Failure to include V11 in any one of these branches can silently discard older state facts and must be an explicit regression test. V11 Character includes the exact V10/V9 Character field set plus required `walkingSpeed`; V11 non-null Combat retains the exact V10 field set including required `movementSpent`; V11 empty Character arrays and `combat=null` remain valid. V11 `walkingSpeed` JSON `null` maps to `None`; JSON `0` maps to 0; invalid primitive/container, negative, unknown extra or missing required fields fail. Serializer output validation must reject an invalid mutable `CharacterState.walking_speed`, not just construction-time failures. V2–V10 read speed as `None` without inference and later save as exact V11; V1 still has no Character. Reject V11-only fields in historical shapes, including inherited V9 Character lifecycle / V10 Combat movement fields. Preserve all root, Creature, Inventory, Equipment and Combat exactness and legacy compatibility tests.
3. Preserve first three existing `MoveCombatantHandler` checks in exact order: state load; actor Creature existence (`ENTITY_NOT_FOUND`, actor, no field); Combat existence/exact id (`ENTITY_NOT_FOUND`, combat id, `combat_id`); active actor (`ACTION_NOT_AVAILABLE`, actor, no field). Then select character by existing `CharacterState` membership. For the Character branch, do **not** call Monster `DefinitionSource`; require `actor.current_hp > 0` (`ACTION_NOT_AVAILABLE`, actor, no field) before requiring `character.walking_speed is not None` (`ACTION_NOT_AVAILABLE`, actor, `walking_speed`). For the non-Character branch retain §3.38 existing Monster Definition lookup/error mappings before HP and speed checks, without reordering. Both branches thereafter share existing position (`ACTION_NOT_AVAILABLE`, actor, `position`), non-identical destination (`INVALID_COMMAND`, actor, `position`), pure segment resolution, and cumulative budget (`OUT_OF_RANGE`, actor, `position`) in that order. Prior `movement_spent > walking_speed` is not an `INVALID_STATE` error by itself; every positive candidate that exceeds budget is `OUT_OF_RANGE`. Character `walking_speed=0` is not an absent source but cannot admit a positive segment.
4. One accepted Character Move allocates Event metadata once and emits exactly one unchanged `CombatantMoved` V1 (`actorId=Character ID`, `causedBy=null`); use existing applier to derive position plus `movement_spent` in a single new `CombatState`; produce one replacement `StateSnapshot`, call `StateStore.save()` exactly once, and return success only after it completes. Leave `CharacterState`/all other projections, `action_spent` and turn unchanged. Invalid input returns no metadata/roll/Event/save; loaded authoritative objects are not mutated; save failure propagates without success. Do not introduce an Event type, version, converter or extra speed parameter.
5. Deterministic tests must cover explicit speed 0/None/positive, invalid types and values, movement exactly at/above budget, cumulative segments, Move→Attack→Move after action expenditure, 0-HP, non-active/missing Combat/missing position, **actor without CharacterState** retaining its existing Monster Definition lookup/error behavior, unchanged Monster Definition source/behavior, reused unchanged Event and turn reset, V1–V10 migrations, V11 strict decoding/round trip and filesystem reload. Update exact `CANONICAL_FIELDS` expectations in `tests/domain/test_character_state.py`. Use existing concrete adapters and injected or seeded `DiceEngine`; no LLM or network. Document the new behavior as implemented only after these tests and actual production code land.

## Acceptance criteria

- Construction validates `CharacterState.walking_speed` exact `int >= 0 | None`; no bool coercion and existing Character constructions default to None.
- Production `StateSerializer` writer reports V11 and writes `walkingSpeed` for **every** serialized Character; a CharacterState with an invalid post-construction speed fails serializer validation. V11 empty Characters / null Combat remain valid; the reader strictly accepts only exact V11 data and preserves V10 Combat `movementSpent`, positions and Action, Character death saves, proficiency, Inventory/Equipment.
- V1–V10 historical fixtures/readers remain exact; V2–V10 Character objects reject `walkingSpeed`, while V1 has no Character and rejects an injected `characters` State field; V2–V10 Character speed reads as None without inference. Fresh V11 write/reload preserves speed None, 0 and positive values. No historical schema is silently rewritten in its decoder.
- Active positioned positive-HP Character with known speed moves with `MoveCombatantCommand`; same Command/Event/Result shape as Monster, `CombatState.positions` only position owner; exactly one successful save and one `CombatantMoved` V1 per segment; unchanged Action.
- Character rejection precedence and errors match §3.39 and binding approach item 3, and reject before Event metadata, dice, Event creation or persistence; `StateStore.save()` failures do not return success. Monster precedence, zero-HP/speed behavior, Definition lookup and turn reset remain unchanged.
- Character split Move→Attack→Move obeys independent resource and cumulative budget rules across reloads; speed 0 and missing speed disallow positive movement, reaching exact budget is allowed, exceeding budget is `OUT_OF_RANGE`, including prior expenditure already above later-read speed.
- Documentation and compact summary distinguish the delivered V11 writer from earlier V10, leave broad Phase 3 Movement unchecked, and preserve all canonical architecture/State ownership restrictions.

## Known constraints / edge cases

- Contract publication precedes execution. Task metadata controls eligibility: a draft never enters `NEXT`, while an approved, dependency-satisfied, published spec may become eligible, but still requires a separate explicit `AUTONOMOUS_PR` invocation. Textual readiness alone grants no authority. §3.38 remains the active Monster-only implementation until TSK-0051; its unconditional Character rejection is intentionally replaced only by the published §3.39 Character branch after implementation.
- A Character may have no speed yet (`None`), even after legacy upgrade; read-only game mechanics continue to work, but Character voluntary movement must reject with the specified error. In this headless MVP the speed is provided only by trusted initial-snapshot setup, not an AI/player-originated value or ad hoc update of a running persisted campaign. This is intentional and not an invitation to default to 30 feet.
- `CharacterState` speed is a narrow presently supported authoritative State fact, not a race/class derivation or an immutable CharacterDefinition. No gameplay Command for changing it is added.
- Snapshot migration and `StateStore.save()` are not a durable EventStore or multi-command transaction. Keep existing save failure/ID-gap behavior, and ensure tests verify the loaded snapshot is not modified before saving.
- Character zero-HP Movement rule does not establish full Character/Monster life-state or 0-HP targetability. Reactions/OA remain pending; do not state that moving is intrinsically safe from them.
