## Goal

Extend the existing, H-owned `PreassignmentJobs` with a narrowly bounded, fake-testable prelaunch lifecycle gate. Preserve one authoritative owner of `J_supervision` and `J_command` from initial creation through the prelaunch reservation and the first possible native-creation side effect; do not transfer the Jobs to another owning Python object. Permit checked one-shot empty-Job retirement before the native-invocation fence; irreversibly prohibit every empty/preassignment retirement path after that fence. Retain an auditable owner reference across exceptions and unresolved stages without claiming process creation, assignment, quiescence, actual handle provenance or full verification containment.

The deliverable is a dormant state/ownership prerequisite for future atomic suspended creation, not a process launcher or a general session manager. It must be independently reviewable and mergeable with pure/fake/static evidence, without activating any production behavior. This is a MANUAL-only task. Its published metadata stays `draft`; the task text, its review or its publication are not execution, native-test, commit, push, PR or merge authority.

## Scope

1. Extend only the existing `PreassignmentJobs` internal lifecycle with a private, monotonic prelaunch phase distinct from the preexisting per-Job `OwnershipState`. Keep the two `_OwnedJob` records, the original checked `JobNativeApi` and their sole H-side owner. Do not introduce `HJobCustody`, a second resource ledger or an owning handoff.
2. Introduce exactly the narrow module-private operations `_reserve_prelaunch(pair)`, `_abort_prelaunch_empty(pair)`, `_fence_native_creation(pair)` and `_prelaunch_snapshot(pair)`. They accept only an exact, fully initialized `PreassignmentJobs` owner; no raw handles, caller-defined roles, generic callback or external Job may be registered. No new public methods are added to `PreassignmentJobs`.
3. Require the following phases: `EMPTY_READY`, `RESERVED_EMPTY`, `NATIVE_CREATION_FENCED`, `EMPTY_CLOSE_CLAIMED`, `EMPTY_CLOSED` and `EMPTY_UNCERTAIN`; constructor/setup failure remains governed by the existing checked ownership state. `NATIVE_CREATION_FENCED` means only that a native invocation may subsequently occur: it is never proof that one occurred or succeeded. This task provides no `ASSIGNED`, `QUIET`, `RESUME_READY` or successful process-completion transition.
4. `_reserve_prelaunch()` atomically claims `EMPTY_READY -> RESERVED_EMPTY` under the existing state lock, only with both Jobs owned, checked and not in retirement. It invokes no Win32 operation, creates no new Job handle and returns no native capability. A reservation is one-shot. From `RESERVED_EMPTY`, old `release_preassignment()` must reject without a native call. Concurrent original release and reservation must have exactly one winning phase claim.
5. `_abort_prelaunch_empty()` atomically claims `RESERVED_EMPTY -> EMPTY_CLOSE_CLAIMED` only while no native invocation has been fenced. It then reuses the existing checked reverse-order retirement of `J_command` and `J_supervision`, at most once per actual handle, retaining truthful per-handle close results, original causal error and bounded secondary cleanup failures. Complete retirement sets `EMPTY_CLOSED`; failed, interrupted or ambiguous retirement sets `EMPTY_UNCERTAIN`. Neither outcome establishes process quiescence. No re-arm or automatic retry is allowed.
6. `_fence_native_creation()` atomically claims `RESERVED_EMPTY -> NATIVE_CREATION_FENCED` before any future native creation call. The fence performs no native call in this task. Once claimed, both `release_preassignment()` and `_abort_prelaunch_empty()` are permanently prohibited, including after a later simulated or future native wrapper failure, even if a process was never successfully returned. The future native launch implementation must use this fence before `CreateProcessW` and provide a separately reviewed assigned/uncertain owner lifecycle; this task adds no post-fence release.
7. Preserve the existing sole owner by registering a strong private H-process-lifetime reference to the exact `PreassignmentJobs` object *before* the reservation state can change. Registration is identity-based, never handle-number-based. On confirmed empty retirement it may be removed; on native-creation fencing, lock/claim uncertainty or failed/ambiguous close it remains pinned until a future reviewed terminal lifecycle or H process exit. A failure before reservation claim must not disable otherwise valid original preassignment release. A failure after a claim must not silently restore old release authority or lose the owner record. No destructor/finalizer, implicit context-manager cleanup or retry is introduced.
8. Handle concurrent/reentrant reserve, old release, abort, fence and snapshot reads through a single phase authority and one lock with no external calls while locked. Record unknown lock-enter/exit, claim and bookkeeping outcomes fail-closed; do not reacquire a damaged lock merely to guess success, expose raw state as permission, call an alternate close or clear the uncertainty latch. Keep diagnostics bounded to allowlisted stage/category/numeric fields and role labels; never include raw handles, pointers, paths, argv, environments, exception text or output.
9. Add deterministic portable fake-only tests in `tests/tools/autonomous_pr/test_windows_verification_prelaunch.py`; block real DLL/native acquisition even on Windows CI. Cover state transitions, close-order assertions, all concurrent claim orderings, reentrancy, post-claim exceptions, `MemoryError`, `KeyboardInterrupt`, poisoned-lock/registry failures, pinned-owner retention, redaction and existing API/production isolation. Existing TSK-0048 and TSK-0049 tests must remain unchanged and passing.
10. Keep the implementation dormant. Preserve the current public `VerificationCommandResult` and production `subprocess.run` boundary. No real native Windows operation, Worker/payload process, `CreateProcessW`, attribute-use pointer, stdout/stderr IPC, Job membership, quiescence, deadline engine or production integration is introduced. No new production dependency.

## Approved implementation approach

**Single owner and two orthogonal states.** The existing `PreassignmentJobs` remains the only authoritative owner of its two Job handles. The original `OwnershipState` tracks each actual native reference (`OWNED_PREASSIGNMENT`, `CLOSE_ATTEMPTED`, `CONFIRMED_CLOSED`, `UNCERTAIN_CLOSE`); a new private phase tracks *whether an empty-Job cleanup operation is still permitted*. Per-Job handle state alone must never authorize release. A `JobOwnership` snapshot continues to describe handle ownership, not launch permission. `_prelaunch_snapshot()` provides a distinct immutable, role-/phase-only audit view; it never reveals a handle or grants capability.

**Explicit phase transitions.** Initial normal state is `EMPTY_READY`. Original `release_preassignment()` remains valid only from this state; an unchanged unreserved object follows the TSK-0048 checked path. Reservation permits only `EMPTY_READY -> RESERVED_EMPTY`. The two competing operations in `RESERVED_EMPTY` are checked empty abort and fencing. Abort claims `EMPTY_CLOSE_CLAIMED` then attempts reverse-order closes; it finishes `EMPTY_CLOSED` or `EMPTY_UNCERTAIN`. Fence claims `NATIVE_CREATION_FENCED`, a permanently non-empty-release-eligible phase. No other successful transitions exist in this slice. A future launch implementation must add checked post-fence transitions and terminal cleanup; no current operation can reset, retry or erase the fence.

**Atomicity and memory ownership.** Every phase claim shares the existing Job owner's state lock with the old release path. The final release check and irrevocable claim occur under that lock. Both claimed routes release the lock before any external API call. A race may let a reservation finish after another thread has already aborted it; this never authorizes launch: only the later atomic `_fence_native_creation()` success could authorize a future native invocation. If abort wins, fence fails. If fence wins, abort fails. No snapshot read is an authority gate. No native call occurs while the state mutex is held.

**Owner retention.** The same owner object, not the numeric handles, is pinned in a private identity registry before its transition from `EMPTY_READY`. Registry insertion happens before the irreversible claim and without holding the Job state lock simultaneously with the registry lock. Once reserved, even a Python exception before normal return cannot erase the only owner reference. Registration failure before the claim leaves original preassignment release usable; a rejected preclaim reservation must discard any newly registered pin if its claim is known not to have occurred. If claim/lock outcome is ambiguous, retain a conservative strong reference and reject further cleanup rather than reconstructing state or attempting a second claim. Confirmation of both empty closes permits unpinning; an unsuccessful unpin must not fabricate OS cleanup, and a failed/unknown close remains pinned. The `NATIVE_CREATION_FENCED` owner stays pinned for the rest of this dormant task's H lifetime, pending a separately reviewed assigned/uncertain retirement design.

**Empty retirement reuse.** Reuse the current `_retire()` checked reverse-order logic and preserve its monkeypatchable private call boundary in existing fake tests. Both the old unreserved release and new reserved-empty abort must consume their own exclusive phase claim *before* `_retire()`, and each handle must have no more than one actual close attempt. The normal fake-native exception paths still attempt the remaining owned handle after a failed first close. Catastrophic Python bookkeeping/lock errors that prevent remaining attempts are terminal uncertainty with retained unresolved ownership; they do not permit a blind second cleanup pass. Keep primary failure and bounded secondary diagnostics. Successful `CloseHandle` is not quiescence evidence.

**Fence interpretation and downstream responsibility.** `_fence_native_creation()` is an irreversible pre-native risk marker, not the native call and not an assignment proof. The future H-only launch operation must execute native process creation only after successfully claiming this fence, must serialize it against all empty-release paths, must use a narrow private Job-handle consumption contract rather than a general raw getter, and must protect the prepared attribute-list pointer/use lifetime against retirement. It must distinguish confirmed failed creation, confirmed suspended creation and wrapper-exception/late-return uncertainty; after fence, none may use this task's empty retirement. No future payload resume is permitted before verified actual membership and the rest of published C0 pre-resume gates. This task deliberately provides no operation that could resume or launch any process.

**Provenance limits.** Successful construction of `PreassignmentJobs` demonstrates a checked sequence through its injected `JobNativeApi` only. An exact Python type, integer HANDLE and fake trace do not attest real Windows object provenance, rights, inheritability, external Job nesting or actual Job membership. The full trusted H capability ledger for bootstrap/stdio/process handles and actual native attestation belongs to future slices. Do not assert native containment from the new fence.

## Acceptance criteria

Invalid/foreign-type, partially initialized, closed, retiring or previously reserved/fenced owners fail closed.
3. `release_preassignment()` after successful reserve invokes no `CloseHandle`. Reserve vs release and duplicate/concurrent reservation are lock-linearized; at most one authority path wins, with truthful redacted snapshots. A snapshot does not grant launch or cleanup permission.
4. `_abort_prelaunch_empty()` succeeds only after reserve and before fence. It irreversibly claims `EMPTY_CLOSE_CLAIMED`, attempts `J_command` then `J_supervision` once using existing checked cleanup and records `EMPTY_CLOSED` only after both confirmed closes. No second abort or old release can close a handle again. This does not certify any process or Job quiescence.
5. Fake injected command/supervision/both-close faults produce bounded causal error and secondary diagnostics, correct unresolved records, `EMPTY_UNCERTAIN` and no retry. The remaining Job receives its one attempt after an ordinary failed first close; if catastrophic Python failure prevents completion, report terminal uncertainty and retain still-owned records instead of faking both-close success.

Abort, old release and second fence all reject thereafter, including when a later native-call outcome would be unknown. 7. Tests force both outcomes of reserve/release and abort/fence races and concurrent/reentrant attempts without relying on timing sleeps. They verify each close is attempted at most once and no native operation is called under the state mutex. Any transition that failed after a claim cannot enable an old release path.

Fault injection of registry/allocation/lock/diagnostic failures, `MemoryError`, `KeyboardInterrupt` and unexpected `BaseException` before and after claims preserves a reachable/pinned authoritative owner or conservatively quarantined uncertainty. ## Known constraints / edge cases

- A reservation/fence is not full launch-session ownership and grants no right to use an arbitrary raw native handle. The next reviewed native-launch slice must bind the same owner to a narrow trusted consumer of the private Job handles and serialize native `CreateProcessW` with the fence and `PreparedLaunchAttributes` borrow/use/retirement contract. It must add actual process/thread handle ownership, membership verification, assigned/uncertain cleanup and resume gates before any runtime activation.
- A successful `_fence_native_creation()` does not assert that a Windows API was called. It conservatively records that such a call may follow; the task deliberately provides no way to clear the fence or treat Jobs as empty afterward. In a future implementation, even a Python wrapper exception after an actual native call cannot restore empty-release authority.
- `PreassignmentJobs` is constructed through an injectable `JobNativeApi`; exact Python class identity and fake successful Job creation/configuration/readback are logical test facts, not independent proof of native Job provenance, nesting, handle rights or real OS membership. Neither this task nor TSK-0049 attests bootstrap/stdio inherited handles.
- The `JobOwnership` per-handle state may continue reporting `OWNED_PREASSIGNMENT` while the separate gate phase is `RESERVED_EMPTY` or `NATIVE_CREATION_FENCED`; that label describes still-owned handles, not permission to call legacy release. The new immutable gate snapshot is audit-only; permissions require an atomic phase check under the owner lock.
- Strong owner pinning is conservative retention, not proof of native cleanup or an excuse to leak OS resources silently. On confirmed empty closes the strong pin may be removed. On uncertain/fenced ownership the record remains reachable until separately reviewed terminal cleanup exists or H exits. H-crash kill-on-close behavior with live children remains untested.
- The first native process creation will require correctly configured `STARTUPINFOEXW`, `CREATE_SUSPENDED`, ordered JOB_LIST/whitelisted HANDLE_LIST, `bInheritHandles=TRUE` as applicable, trusted handle provenance, actual membership checks before resume, no breakaway/post-launch assignment/uncontained fallback, and preservation of real Windows argument/search/environment/stdin semantics. No claim of these behaviors follows from the gate.
- Future capture and completion must preserve full strict UTF-8 with universal newline conversion, actual root code (including final DWORD 259), W-controlled capture/ACK, `FINISH` acceptance strictly before `D_execution`, both sealed Job accounting samples, checked process/thread reference retirement, independent deadlines and the irreversible `0x57564301` forced-termination latch.
