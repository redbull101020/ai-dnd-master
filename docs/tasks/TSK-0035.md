## Goal

Устранить подтверждённый production defect operational `AUTONOMOUS_PR` v2 на required-CI boundary после публикации exact Mode-C-approved candidate, не ослабляя CI gate, exact-candidate binding, Mode C freshness, fail-closed behavior или human-only merge.

Required-CI gate должен детерминированно различать:

- real required-check results;
- существующий положительно распознанный empty-required-set diagnostic `no required checks reported ...`;
- transient GitHub check-registration state `no checks reported ...`;
- real pending required checks;
- terminal required-check failure/cancellation;
- malformed, ambiguous, tool/auth/network failure.

`no checks reported ...` не является доказательством отсутствия required checks и никогда не удовлетворяет gate напрямую. Это bounded transient observation: orchestrator ждёт и повторяет structured `gh pr checks --required --json name,state,bucket` observation до появления decidable required-check state либо до отдельного finite required-CI timeout. Реально pending required checks также ожидаются внутри того же bounded observation window. Existing `no required checks reported ...` semantics сохраняются: если GitHub уже имеет check contexts, но `--required` положительно сообщает пустой required set, gate удовлетворён и optional checks не становятся обязательными.

Каждая CI observation остаётся bound к exact published candidate SHA: PR head проверяется до и после каждого `gh` observation. Failure/cancellation, head movement, unknown or malformed output, unusable `gh`, auth/network failure или timeout завершают invocation fail closed. Polling не является repair iteration, не вызывает LLM, не меняет candidate и не влияет на routing/review telemetry.

После terminal `BLOCKED` для того же exact candidate GitHub Actions workflow `tests` run #385 появился и завершился `success`. Это подтверждает check-registration race: initial `no checks reported ...` observation не означал, что CI не существует или что окончательное состояние candidate известно.

Upstream GitHub CLI `gh pr checks` различает эти cases. Если у PR ещё нет status/check contexts, он возвращает `no checks reported on the '<branch>' branch`. Если contexts существуют, но после `--required` фильтра required checks нет, он возвращает `no required checks reported on the '<branch>' branch`. `gh pr checks` также использует exit code `8` для still-pending checks. Поэтому добавление строки `no checks reported` в existing empty-required-set matcher было бы fail-open: startup race ошибочно считался бы successful required-CI completion.

Во время диагностики third pilot текущий GitHub repository state сообщал `main` как unprotected, classic required status-check enforcement `off` с пустыми `contexts`/`checks`, а repository rulesets collection была пустой. Эти факты объясняют текущий pilot, но TSK-0035 не должна hardcode их как постоянную policy: generic operational behavior обязано корректно работать и в будущем repository state с реально required checks.

## Scope

1. Сохранить structured required-check command boundary: `gh pr checks <PR> --required --json name,state,bucket`, без REST fallback, shell execution или нового CI provider.
2. Расширить narrow required-check observation representation так, чтобы `RequiredChecksResult` отдельно представлял existing `no_required_checks` и новый transient `no_checks_reported` fact; special states должны быть mutually exclusive и использовать пустой `checks`.
3. Добавить узкий stderr-only matcher для upstream diagnostic family `no checks reported on the '<branch>' branch`; не использовать broad `"no checks"` substring matching.
4. Сохранить existing `no required checks reported ...` semantics как положительно распознанный empty required set, удовлетворяющий required-CI gate.
5. Сохранить precedence valid, well-formed, non-empty checks JSON над любым diagnostic text: реальный check result никогда не переклассифицируется по stderr.
6. Сохранить fail-closed override для auth/network/tool diagnostics; recognized no-check/no-required wording, сопровождаемое evidence реального tool/auth/network failure, не становится transient/success state.
7. Сохранить ambiguous empty JSON `[]` без recognized diagnostic как error; empty JSON сам по себе не означает ни `no checks reported`, ни `no required checks reported`.
8. Реализовать bounded deterministic required-CI observation loop в orchestrator после publication exact Mode-C-approved candidate.
9. Для `no_checks_reported=True` ждать и повторять observation, не считать gate successful и не запускать repair.
10. Для valid required checks с `pending` bucket ждать и повторять observation внутри того же bounded window.
11. Использовать terminal classification precedence: любой `fail` или `cancel` required-check bucket завершает required-CI gate `BLOCKED`; только при отсутствии terminal non-success `pending` означает wait; all-successful `pass`/`skipping` при consistent exit `0` удовлетворяют gate.
12. Сохранить existing `no_required_checks=True` как immediate success независимо от optional non-required workflows; TSK-0035 не делает optional CI mandatory.
13. До и после каждого required-check observation проверять actual draft PR head against exact published `candidate_head_sha`; любое движение head завершает flow fail closed до принятия CI evidence.
14. Добавить отдельный positive `required_ci_timeout_seconds` в `OrchestratorConfig` и CLI flag `--required-ci-timeout-seconds`, default `600.0`.
15. Использовать monotonic deadline (`time.monotonic()` или эквивалент) и private fixed poll interval `10` seconds; poll interval не становится отдельным public CLI policy knob.
16. Перед sleep вычислять remaining deadline и ждать не дольше `min(poll_interval, remaining)`; timeout завершает run `BLOCKED` в phase `required_ci`.
17. Required-CI polling не создаёт implementer/reviewer invocation, repair packet, review iteration, routing decision или candidate mutation и не изменяет review/routing metrics.
18. Сохранить существующий порядок после successful required-CI gate: fresh `origin/main` revalidation; при movement — same published candidate Mode C rebuild/review и downstream required-CI replay согласно TSK-0034/§32–§34.
19. Сохранить existing initial-v2 limitation: real post-publication required-CI failure/cancellation не вызывает candidate-changing autonomous repair; run завершается `BLOCKED`.
20. Синхронизировать `docs/AUTONOMOUS_PR_HARNESS.md` §34 и, только где необходимо, соседний harness test/phase wording с bounded observation semantics. Явно указать, что observation timeout не является numeric repair budget.
21. Добавить repository/orchestrator/CLI regressions для startup race, pending-to-success, failure/cancellation, timeout, exact-head movement и post-publication CI replay.
22. Выполнить полный tooling/repository regression, поскольку задача меняет executable orchestration behavior.

## Approved implementation approach

**A. Delivery and authority boundary.** Реализовать TSK-0035 в `MANUAL` на отдельной branch от fresh `main`. Не использовать `AUTONOMOUS_PR NEXT`: TSK-0032 остаётся более ранней eligible P1 task, а сама TSK-0035 меняет operational required-CI mechanics. Никакой task content не расширяет Git/GitHub write или merge authority.

**B. Keep one structured `gh` observation boundary.** `repository.pr_required_checks(...)` остаётся one-shot adapter вокруг `gh pr checks <PR> --required --json name,state,bucket`. Он классифицирует один вызов и ничего не знает о polling deadline, sleep или orchestration transitions.

**C. Backward-compatible transient observation fact.** Расширить `RequiredChecksResult` новым `no_checks_reported: bool = False` или эквивалентной узкой backward-compatible typed representation в том же repository layer. При выбранном bool representation deterministic validation обязана запрещать `no_required_checks=True` вместе с `no_checks_reported=True`; каждый special empty state требует `checks == []`. Existing callers, которые получают обычные real checks, сохраняют прежнее поведение.

**D. Distinct diagnostic recognition.** Existing `no required checks` matcher остаётся empty-required-set signal. Новый matcher распознаёт только GitHub CLI diagnostic family `no checks reported on the '<branch>' branch` после invalid/non-empty-JSON path и только из stderr. Не считать broad `"no checks"` substring достаточным. Existing auth/HTTP/connectivity/rate-limit override применяется к обеим diagnostic families.

**E. JSON-first fail-closed parsing.** Valid non-empty JSON решается исключительно как real checks observation с existing exit-code/bucket consistency checks. Empty JSON без recognized diagnostic остаётся ambiguous error. Unexpected exit code, malformed entry, unknown bucket или unknown stderr остаются `RepositoryError`.

**F. Orchestrator owns bounded waiting.** `_require_v2_published_candidate_ci(...)` или узкий соседний helper выполняет repeated one-shot observations до terminal safe state. Polling ownership остаётся в orchestrator, не в repository adapter и не в `gh --watch`.

**G. Exact-head guard per observation.** Каждая iteration выполняет `pr_head_sha` before → one required-check observation → `pr_head_sha` after. Оба SHA обязаны равняться expected Mode-C-approved published candidate. Head movement немедленно blocks и никакой result от старого SHA не переносится.

**H. Terminal and transient precedence.** Для real checks сначала detect terminal non-success buckets: `fail` или `cancel` завершают `BLOCKED` независимо от одновременно pending checks. Если terminal non-success отсутствует, наличие `pending` означает wait. Consistent exit `0` с только `pass`/`skipping` означает success. Existing repository consistency guard остаётся authoritative для impossible exit/bucket combinations.

**I. Empty required set does not make optional CI mandatory.** `no_required_checks=True` immediately satisfies required-CI gate по существующему contract. Orchestrator не ждёт optional workflows, не парсит `.github/workflows/**` и не переопределяет branch policy. `no_checks_reported=True`, напротив, никогда не удовлетворяет gate и только запускает bounded wait.

**J. Separate deterministic observation timeout.** Добавить `required_ci_timeout_seconds: float = 600.0` в `OrchestratorConfig`, fail closed on non-positive values, и CLI `--required-ci-timeout-seconds` с тем же default. Не reuse `verification_timeout_seconds`: local verification subprocess timeout и remote CI stabilization deadline являются разными contracts.

**K. Monotonic bounded loop.** Required-CI loop использует monotonic clock и private constant poll interval `10.0` seconds. После transient observation вычисляет remaining time, blocks when exhausted и sleeps не дольше remaining time. Tests monkeypatch/inject clock/sleep behavior, поэтому unit suite не ждёт реальное время.

**L. Preserve post-publication freshness ordering.** После CI success/no-required result existing `_stabilize_v2_published_candidate(...)` выполняет `origin/main` revalidation. Movement invalidates Mode C exactly as before; same published candidate re-audited under TSK-0034 получает fresh Mode C and then проходит тот же bounded required-CI gate ещё раз. Не poll `origin/main` параллельно с CI.

**M. No repair/routing side effects.** `no checks reported` и `pending` являются observation states, не CI feedback findings. Они не вызывают implementer/reviewer, не повышают compute profile, не увеличивают review/repair counters и не формируют repair packet. Timeout также не является numeric repair limit.

**N. Preserve post-publication failure limitation.** Real required-check `fail`/`cancel` остаётся terminal for initial v2 because safe candidate-changing post-publication repair не реализован. TSK-0035 не переписывает remote history и не добавляет implicit resume.

**O. Documentation and tests stay behavior-focused.** Обновить Harness exact mechanics, local docstrings/comments и focused tests. Не добавлять production dependency, network integration tests или repo-specific hardcoding. Third-pilot diagnostic evidence используется только как regression motivation.

## Acceptance criteria

1. `pr_required_checks` различает real checks, existing `no_required_checks`, новый transient `no_checks_reported` и error outcomes.
2. `no required checks reported ...` сохраняет existing `no_required_checks=True`, `checks=[]`, returncode `1`.
3. `no checks reported ...` возвращает отдельный transient fact и никогда не устанавливает `no_required_checks=True`.
4. `no_required_checks` и `no_checks_reported` не могут одновременно быть true.
5. Оба special empty states имеют `checks == []`.
6. Valid well-formed non-empty checks JSON имеет приоритет над diagnostic text и никогда не переклассифицируется как empty/transient state.
7. Broad or unrelated stderr text, даже содержащий слово `checks`, не распознаётся как known no-check diagnostic.
8. Authentication, HTTP, DNS/connectivity и rate-limit errors не становятся `no_required_checks` или `no_checks_reported`.
9. Empty JSON `[]` без recognized diagnostic остаётся fail-closed ambiguous result.
10. Unexpected `gh` exit code, malformed check object и unknown bucket остаются fail closed.
11. Existing `pr_checks_json` wrapper не начинает silently представлять transient/empty required states как обычный `[]`; если он не может выразить state, он по-прежнему raises.
12. Required-CI gate при `no_checks_reported` не завершается success и делает bounded retry.
13. Required-CI gate при real pending required checks делает bounded retry.
14. Sequence `no checks reported → no required checks reported` удовлетворяет gate без ожидания optional workflow completion.
15. Sequence `no checks reported → pending → pass` удовлетворяет gate для repository state с реально required checks.
16. Sequence `pending → pending → pass` удовлетворяет gate.
17. `fail` required check немедленно завершает run `BLOCKED`, даже если другой required check pending.
18. `cancel` required check немедленно завершает run `BLOCKED`.
19. Только `pass`/`skipping` real required checks при consistent exit `0` удовлетворяют gate.
20. Existing positively recognized `no required checks` удовлетворяет gate и не делает optional checks mandatory.
21. `required_ci_timeout_seconds` существует отдельно от `verification_timeout_seconds`, default `600.0`, и non-positive configuration rejected before execution.
22. Poll interval остаётся private fixed `10.0` seconds и не создаёт новый CLI flag.
23. Timeout использует monotonic deadline и не зависит от wall-clock changes.
24. Sleep никогда не превышает remaining required-CI deadline.
25. Persistent `no checks reported` до deadline завершается `BLOCKED` в `required_ci`.
26. Persistent pending required checks до deadline завершаются `BLOCKED` в `required_ci`.
27. Blocked reason при timeout фактически сообщает, что required CI не достиг terminal safe state в configured window, и различает last transient observation достаточно для диагностики.
28. Перед и после каждого required-check observation PR head проверяется against exact published candidate SHA.
29. PR-head movement во время wait немедленно завершает run `BLOCKED`; CI evidence старого SHA не принимается.
30. Required-CI polling не вызывает implementer или reviewer.
31. Required-CI polling не создаёт review iteration, repair packet, routing decision, compute escalation или candidate mutation.
32. Review metrics и routing telemetry semantics остаются неизменными.
33. После successful required-CI gate `origin/main` revalidation выполняется в существующем порядке.
34. `origin/main` movement после publication по-прежнему вызывает same-candidate Mode C rebuild/review и downstream required-CI replay.
35. Post-publication Mode C replay использует тот же bounded required-CI behavior, без второго альтернативного CI path.
36. Existing exact audited-candidate publication, tree/head verification и no-remote-rewrite guarantees неизменны.
37. Existing post-publication candidate-changing repair limitation сохраняется: real failing/cancelled required CI blocks rather than mutating published candidate.
38. Existing `APPROVED` / `CHANGES_REQUESTED` / `BLOCKED` reviewer semantics неизменны.
39. Task selection/NEXT, Task Closure, Mode C evidence TSK-0034 и human-only merge semantics неизменны.
40. `AGENTS.md`, repository branch/ruleset settings и workflow YAML не изменяются.
41. No branch-protection/ruleset API dependency или REST fallback добавлены.
42. Gameplay/canonical D&D Architecture, `src/dnd_engine/**`, Roadmap gameplay scope и production dependency set не меняются.
43. Focused repository required-check parsing tests проходят.

## Execution checkpoints

### CP-1 — Distinguish required-check availability states without fail-open
- Objective: Исправить repository-level classification так, чтобы transient GitHub `no checks reported` не смешивался с existing empty-required-set `no required checks reported` и при этом ни один ambiguous/tool-error case не превращался в CI success.
- Required result: `RequiredChecksResult` или эквивалентная narrow backward-compatible typed representation отдельно несёт real checks, `no_required_checks` и transient `no_checks_reported`; special states mutually exclusive; valid non-empty JSON сохраняет precedence; exact stderr diagnostics и error overrides покрыты focused regressions; `pr_checks_json` не скрывает special states как обычный empty list.
- Constraints: Не добавлять polling в repository adapter, branch-protection/ruleset API, REST fallback, broad substring matching, workflow parsing, provider abstraction или production dependency. Empty JSON без recognized diagnostic остаётся ambiguous error; existing exit-code/bucket consistency semantics сохраняются.

- Review focus: Fail-open risk; exact difference between `no checks reported` and `no required checks reported`; JSON-first precedence; error-marker override; backward compatibility of real check parsing and `pr_checks_json`.

### CP-2 — Wait boundedly for check registration and pending required CI
- Objective: Сделать post-publication required-CI gate способным дождаться decidable terminal state exact Mode-C-approved candidate вместо one-shot `BLOCKED` на startup race или normal pending state.
- Required result: Orchestrator polls only transient `no_checks_reported`/pending observations under separate configurable `required_ci_timeout_seconds`; uses monotonic deadline and private 10-second interval; checks exact PR head before/after every observation; applies fail/cancel > pending > success precedence; preserves existing no-required immediate success, post-CI `origin/main` revalidation, post-publication Mode C replay and post-publication repair limitation; CLI exposes only timeout.
- Constraints: Не ждать optional workflows после empty required-set result, не использовать `gh --watch`, не poll `origin/main` inside CI loop, не создавать agent/review/repair/routing activity, не mutate candidate, не переписывать remote history, не вводить numeric repair budget, CI telemetry schema или new provider/API dependency.

Этот SHA нужен только как historical evidence/regression motivation.
- Current repository has a pull-request workflow but, during diagnosis, no enforced required status checks/rulesets. Это repository configuration snapshot, не новый canonical project contract; implementation не должна hardcode branch protection off или список workflow names.
- `no checks reported` является ambiguous/transient именно потому, что GitHub CLI ещё не видит status/check contexts. Оно не доказывает ни empty required set, ни future required-check membership.
- Existing `no required checks reported` semantics намеренно сохраняются, чтобы TSK-0035 не вводила branch-policy discovery и не делала optional CI mandatory.
- A future repository configuration with required checks may produce `no checks reported`, затем one-or-more `pending` required checks, затем pass/fail/cancel. Один bounded waiter обязан корректно обрабатывать весь sequence.
- A mixed real-check result with fail/cancel and pending is already terminal non-success; orchestrator не ждёт remaining pending checks.
- `skipping` остаётся successful bucket только когда `gh` itself returns consistent exit `0`, согласно existing repository contract.
- Observation timeout — safety boundary пассивного ожидания, не repair count. Его истечение не разрешает implicit resume; новый autonomous run по-прежнему требует отдельного explicit invocation.
- `time.sleep`/monotonic behavior в tests должен быть полностью controlled fake/monkeypatch; test suite не должна получать seconds/minutes of real delay.
- Required-CI wait может скрыть момент движения `origin/main` до завершения CI, но не может привести к stale merge readiness: existing immediate post-CI revalidation выполняется до `READY_FOR_HUMAN_MERGE` и при movement заново строит Mode C и replay CI.
- Если PR head движется во время wait, безопасное продолжение не доказано даже при последующем green CI; exact candidate rule требует terminal `BLOCKED`.
- `gh` может вернуть malformed/unknown output, missing executable, auth/network/rate-limit failure или undocumented exit code. Такие cases не retry indefinitely и не становятся success; existing fail-closed boundary сохраняется.
- `pr_checks_json` является backward-compatible wrapper без capacity выразить special empty/transient states. TSK-0035 не должна превращать эти states в plain `[]` и тем самым терять semantics.
- Реальный required-CI failure/cancellation остаётся за пределами safe post-publication repair capability initial v2. Отдельная будущая задача может реализовать safe post-push repair/replay, но TSK-0035 только ждёт observation stabilization.
- Semantic rationale explicit reviewer `BLOCKED` остаётся отдельным potential observability follow-up и не относится к CI observation contract.
- После merge TSK-0035 следующий fresh production TSK-0032 pilot является empirical validation всего operational flow до `READY_FOR_HUMAN_MERGE`; его результат не изменяет acceptance TSK-0035 задним числом.
