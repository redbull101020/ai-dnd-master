## Goal

Make every remaining external-process boundary used by the operational `AUTONOMOUS_PR` path convert expected launch/timeout/output-decoding failures into deterministic fail-closed results instead of leaking unmanaged Python exceptions, losing useful timeout diagnostics, or attempting to interpret corrupted authoritative output.

TSK-0042 through TSK-0045 already hardened candidate-local repair, changed-path authority, runtime/preflight/environment setup, and Full Verification repair. TSK-0046 is the final planned preventive hardening slice before a controlled Windows/MXC timeout-containment probe and a new real `AUTONOMOUS_PR` production pilot. It changes external-process reliability only; it does not add a new workflow, retry policy, authority mode, repair permission, model-selection rule, or merge capability.

The binding distinction is between **semantic subprocess output** and **diagnostic subprocess output**.

Semantic output is output whose decoded content can change an authoritative orchestration decision. It remains strict UTF-8:

```text
reviewer successful stdout
→ ReviewVerdict / RepairPacket / BlockedReviewRationale parsing

Git/GitHub command output used as repository/PR/CI facts
→ SHA / path / status / JSON / recognized required-CI diagnostic parsing

deterministic verification completed output
→ VerificationCommandResult / failed-verification repair evidence

Codex launcher identity output
→ "codex-cli <version>" identity check
```

If required semantic output cannot be decoded as strict UTF-8, the boundary fails closed. Replacement-decoded text must never be used to infer a reviewer verdict, parse Git/GitHub facts, manufacture deterministic verification evidence, or accept a Codex identity.

Diagnostic output is output that cannot authorize a continuation by content and is only retained after process status already determines the outcome. It may be decoded best-effort with UTF-8 replacement characters and projected through a bounded diagnostic excerpt. Examples include partial output after timeout, stdout/stderr from a non-zero agent process, implementer stdout/stderr, and repository tool stderr included in a terminal `RepositoryError`.

The agent boundary has an additional role-specific distinction:

```text
successful reviewer:
    stdout = semantic → strict UTF-8
    stderr = diagnostic → best-effort decode

implementer:
    stdout/stderr = diagnostic only
    repository candidate + verification + review determine correctness
    invalid diagnostic bytes alone do not reject a returncode-0 candidate

timed-out / launch-failed / non-zero agent:
    no stdout/stderr content may authorize continuation
    captured output is diagnostic only
```

A valid-looking token such as `APPROVED` in timeout or non-zero-process partial output never becomes a reviewer verdict.

Terminal diagnostic excerpts derived from external-process output must be deterministic and bounded. Use one implementation-level source-text limit of `4096` characters per excerpt. If a diagnostic source string exceeds that limit, retain the first `2048` source characters and last `2048` source characters with a fixed truncation marker between them. The marker itself is not counted against the `4096` source-character budget. This is a diagnostic projection limit, not a subprocess capture limit, model token budget, repair budget, or governance limit. Successful semantic reviewer output is not truncated before parsing.

The existing agent result shape must distinguish expected process-boundary failures without overloading `returncode=None`. Add one internal provider-neutral agent-process failure classification with exactly:

```text
TIMEOUT
LAUNCH_ERROR
OUTPUT_DECODE_ERROR
```

`OUTPUT_DECODE_ERROR` is used only when semantic agent output that is required to be strict UTF-8 cannot be decoded, primarily successful reviewer stdout. Completed non-zero exit remains represented by its real integer return code and is not a new failure-kind value. The classification is internal in-memory execution state only: it is not a `RunOutcome`, reviewer verdict, routing input, persisted state, Task status, provider identity, or public lifecycle schema.

`run_agent()` must use a bytes-first subprocess boundary so it can decide how to decode each stream only after process status and role are known. The prompt is encoded as strict UTF-8 input bytes. Completed raw stdout/stderr are captured as bytes. Implementer output and terminal agent diagnostics are decoded best-effort; successful reviewer stdout is decoded strict UTF-8 before any verdict/parser call. Reviewer stderr is diagnostic-only and may be replacement-decoded even on a successful reviewer process.

Repository/GitHub boundaries remain stricter because stderr is itself semantic for some existing required-CI special-state recognition. Generic Git/GitHub stdout and stderr therefore stay strict UTF-8. A decode failure raises `RepositoryError`; it is never replacement-decoded before repository, PR, or required-CI classification. Any repository error message that embeds external-process stdout/stderr must use the same bounded diagnostic projection rather than unbounded raw tool output.

Deterministic verification semantics delivered by TSK-0045 remain unchanged:

```text
completed returncode == 0
→ pass

completed returncode != 0 with valid UTF-8 evidence
→ deterministic candidate rejection
→ existing repair path where applicable

timeout / launch OSError
→ RepositoryError
→ terminal execution uncertainty

semantic output decode failure
→ RepositoryError
→ terminal execution uncertainty
→ never repair from lossy evidence
```

The Codex launcher keeps its current executable/profile/runtime/preflight contract. `codex --version` output remains strict UTF-8 because the text is used for identity validation; invalid UTF-8 becomes `LauncherConfigurationError` before generic harness delegation.

This task deliberately does **not** claim that `subprocess.run(..., timeout=...)` terminates every descendant process. Timeout remains terminal because process-tree quiescence is not proven. No automatic retry follows timeout, launch failure, output decode failure, Git/GitHub ambiguity, or agent process failure. Windows/MXC descendant containment is a separate controlled post-merge experiment.

Because TSK-0046 changes the external-process mechanics that the autonomous harness itself depends upon, delivery is `MANUAL`. ## Known constraints / edge cases

- The `4096` source-character diagnostic projection is an implementation-level observability bound only. `subprocess.run(capture_output=True)` may already have captured more bytes in memory before projection. TSK-0046 does not claim to cap subprocess output production, OS pipe buffering, or peak memory.

- The fixed truncation projection retains both head and tail because launch/tool diagnostics frequently place context at the beginning and the final error summary at the end. This is not semantic parsing and must never affect a workflow decision.

- Best-effort replacement decoding is permitted only for streams that cannot authorize continuation by their content on that path. A replacement character in implementer diagnostics is acceptable; a replacement-decoded reviewer verdict, Git SHA/path/JSON, verification evidence, or Codex identity is not.

- Reviewer stdout is semantic only when the reviewer process completed with exit code `0`. On timeout or non-zero exit, even valid UTF-8 `APPROVED` text is diagnostic-only and cannot become an explicit verdict.

- Reviewer stderr is not part of the existing reviewer verdict/repair protocol. This task does not add stderr fallback parsing.

- Implementer stdout/stderr remain non-authoritative. A successful implementer that emitted malformed diagnostic bytes still has to satisfy every existing repository scope, deterministic verification, reviewer, acceptance, replay, closure, Mode C, and CI gate.

- Strict repository stderr is necessary because current required-CI behavior positively recognizes specific stderr diagnostics. TSK-0046 therefore cannot safely adopt replacement decoding for generic Git/GitHub stderr before classification.

- A Git/GitHub non-zero error may contain a very large stdout/stderr body. Full strict-decoded content may be inspected by existing classification code where required, but only a bounded excerpt may enter `RepositoryError` text.

- The exact Git blob reader deliberately remains bytes-first and strict because task/document bytes, newline representation, and digest identity are authoritative. Its invalid-UTF-8 behavior is not relaxed.

- Verification decode failure is not equivalent to a completed deterministic test failure. The process may have returned a real exit status, but the harness cannot construct trustworthy approved-spec verification evidence from invalid semantic output, so the run fails closed rather than repairing from lossy diagnostics.

- Agent diagnostic replacement decoding does not create a new evidence source. Those strings are not supplied to routing or reviewer semantic parsers and do not replace repository/verification facts.

- `AgentProcessFailureKind` is intentionally confined to `agents.py`. Repository, launcher, and verification boundaries retain their existing exception-domain types (`RepositoryError` / `LauncherConfigurationError`) rather than adopting one cross-layer failure enum.

- No exact provider/Codex version behavior is assumed by this task. The launcher identity boundary only requires its existing `codex-cli <version>` semantic output contract to be valid UTF-8.

- Timeout remains terminal because descendant-process quiescence is still unproven. TSK-0046 neither worsens nor solves that separate containment question.

- After TSK-0046 merges, the next validation action should be a controlled native Windows/MXC timeout-containment probe. If the real launcher/sandbox proves descendant quiescence, no containment implementation task is needed. If surviving descendants are positively demonstrated, that evidence can justify a separate task.

- After the containment probe, the preferred next development validation is a small ordinary gameplay/product `AUTONOMOUS_PR` pilot with clear deterministic tests, followed by a post-run audit. Further hardening should then be driven primarily by observed failures rather than speculative expansion.

- TSK-0046 is execution-ready but MANUAL-only. Its task document is execution input for that MANUAL delivery line and is not authorization for commit, push, PR creation, merge, `AUTONOMOUS_PR TSK-0046`, or `AUTONOMOUS_PR NEXT`.
