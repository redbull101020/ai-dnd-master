# TSK-0029 — File-based task dispatch, deterministic NEXT and removable completed specs

## Goal

Заменить обязательную центральную очередь `Current / Next` самостоятельными файлами задач. После атомарного merge этой задачи пользователь должен работать по сценарию:

```text
обсуждение и одобрение задания
→ один готовый docs/tasks/TSK-NNNN.md
→ добавление этого файла в main
→ явная команда AUTONOMOUS_PR TSK-NNNN или AUTONOMOUS_PR NEXT
→ выполнение одной задачи по фиксированному spec
→ reviewed draft PR и prospective Task Closure
→ human merge
→ пользователь может удалить завершённый spec отдельным изменением
```

Добавление очередного задания не должно требовать изменения `docs/TASK.md`, отдельного queue-файла, назначения `Current`, редактирования `Next` или регистрации открытой задачи в другом документе.

Сохранить существующие deterministic execution, independent review, adaptive repair, exact-base revalidation, unpublished closure candidate, Mode C, CI и human-only merge. Изменить входной контракт и хранение task metadata, а не переписать весь harness.

**Эта задача выполняется только в MANUAL.** Она меняет правила invocation и полномочия выбора задачи; обычный `AUTONOMOUS_PR` не может менять собственную authority. Документ не является разрешением на commit, push, создание PR или merge.

### Что меняется относительно текущего контракта

Сейчас spec не содержит lifecycle metadata; preflight требует authoritative Current; готовые specs должны оставаться после Done. Утверждённая пользователем замена: metadata находится в самом файле задачи, выбор делается командой по ID или детерминированным NEXT, terminal-история остаётся постоянной, завершённый spec разрешено удалить после merge.

## Approved implementation approach

### A. Переходная задача и авторизация

TSK-0029 — одна cohesive MANUAL migration. Сохранить существующий operational v2 label, явно документировав file-based dispatch revision и её замену прежней Current-based модели. Не вводить version selector или автоматический fallback.

До её merge действуют существующие правила main. Поэтому прежде чем начинать implementation:

1. Проверить fresh main, AGENTS/README/Roadmap/TASK и связанные modules/tests.
2. В отдельном reviewed preparation change добавить этот spec и зарегистрировать TSK-0029 как Current в действующем thin tracker; следующая свободная identity после allocation — TSK-0030. TSK-0023 не изменять.
3. Довести preparation change до main до начала реализации. Не повторять ситуацию, когда task Current существует только в implementation branch.
4. Если live architecture tests жёстко ожидают пустую очередь/конкретные ID, заменить только snapshot-specific assumptions на действительные generic v2 invariants; не удалять readiness/dependency проверки и не добавлять исключение для TSK-0029.
5. Implementation branch создать от main, который уже содержит принятый preparation. Рекомендуемое имя: `codex/tsk-0029-file-based-task-dispatch`; при коллизии не перезаписывать существующую ветку.

Первоначальный spec TSK-0029 намеренно имеет действующий девятисекционный формат. Во время delivery его не переписывать под создаваемую им schema. После closure TSK-0029 станет terminal; новый reader должен пропускать body любого terminal spec по общему правилу, а не по hardcoded исключению TSK-0029.

В промежуточной branch новая schema может проверяться на fixtures. Финальное live состояние проверяется после prospective closure; никаких постоянных исключений для transition task и никаких отключённых tests ради её прохождения.

После этой одноразовой миграции для обычного следующего задания достаточно добавить один файл. Registration/Current-preparation больше не требуется.

Все commit/push/PR/merge действия этого MANUAL delivery требуют отдельного пользовательского разрешения по AGENTS.md. Изложенная последовательность не выдаёт их авансом.

### B. Единственный источник открытых задач

После activation каталог `docs/tasks/` содержит standalone tasks. Поддерживаемый путь — ровно `docs/tasks/TSK-NNNN.md` с существующим цифровым форматом ID; filename и H1 обязаны совпадать. Никаких status-based подкаталогов, второго alias `Task-*` или выбора по произвольному внешнему пути.

Новый документ начинается с H1, затем содержит один `## Task metadata`, затем девять существующих H2 execution sections в прежнем порядке. Metadata — один fenced JSON object; нужен только стандартный `json`, не YAML.

Пример metadata для будущего одобренного задания:

```json
{
  "execution_approval": "approved",
  "priority": "P1",
  "size": "S",
  "roadmap_target": "Phase 3 / approved capability slice",
  "depends_on": [],
  "group": "engineering"
}
```

Правила:

- Обязательны `execution_approval`, `priority`, `size`, `roadmap_target`, `depends_on`. `group` необязателен и служит навигации.
- `execution_approval` принимает только `draft` или `approved`; отсутствующее/повреждённое поле не считать draft или approved по умолчанию.
- Сохранить значения и смысл P0/P1/P2/P3, S/M/L и существующих groups. Approved executable task имеет размер S либо M.
- `depends_on` — JSON array task ID strings; пустой массив означает отсутствие зависимостей. Self-reference и повторение dependency запрещены.
- `roadmap_target` — строка; для approved она содержательна и не равна пустому значению/маркеру отсутствия. Draft может оставить её незаданной пустой строкой до refinement.
- Duplicate JSON keys, неверные типы, неизвестные значения/metadata keys и повторный metadata section являются ошибкой; не применять last-value-wins.
- Не добавлять второй ID в metadata: identity задают filename/H1. Не вводить Current/Next/Done как поля standalone spec.
- Approved требует полного execution body, конкретного согласованного подхода, всех обязательных CP fields, машинных verification-команд и отсутствия unresolved execution requirements.
- Draft требует корректного identity/metadata envelope, но не полного execution body; это позволяет хранить компактный backlog. Draft никогда не запускается, даже по явному ID.
- Поле approved фиксирует одобренность задания, а не факт завершения и не разрешение запуска. Publication на main тоже не является invocation.
- Девять execution sections, binding/advisory split, последовательность CP-1…CP-N и JSON argv для Verification/Full verification сохраняются. Metadata не меняет смысл требований внутри body.
- Проверять запрещённые lifecycle-дубликаты в body отдельно от разрешённого metadata block. Не оставлять старый blanket-reject Priority/Size/Depends on применимым к новому envelope.

Готовность по структуре не заменяет содержательное MANUAL одобрение и соответствие Architecture/Roadmap. Runtime не должен заново планировать Roadmap через LLM или приписывать свободной строке roadmap_target доказательство смыслового разрешения.

### C. TASK.md: инструкция и terminal-реестр, не очередь

Сохранить существующий `# Terminal task index` и его колонки `ID | Status | Evidence | Title`, чтобы не менять historical evidence без необходимости. Допустимые terminal Status — Done/Superseded; title сохраняет навигацию, не дублирует live scheduling metadata.

Удалить live `# Current position`, Open task index и обязательное обслуживание Current/Next/Hard blockers/Next free ID. Не заменять их queue.json, generated queue.md, open-tasks index или другим обязательным файлом. Убрать дублирующий Recently completed view: terminal-реестр уже хранит результат; Git/Development Log дают chronology.

В компактной инструкции сохранить идентичность задач, смысл приоритетов/размера, зависимости, approval/readiness, single-task execution, правила closure/deletion и распределение authority. Прежние Current/Ready/Blocked как центральные статусы заменить явными правилами draft/approved и вычисляемой eligibility; Superseded не означает Done.

Terminal-реестр не обрезается до последних N записей. Все существующие rows, включая Superseded TSK-0005 и Done TSK-0028, сохраняют достоверные значения/evidence. Исторические terminal ID без specs допустимы.

ID никогда не переиспользуются. Для нового задания автор вычисляет следующий номер как максимум существующих standalone ID и terminal ID плюс один; gaps не переиспользуются. Публикация нескольких файлов выполняется с разными последовательными ID; конфликт concurrent allocation решается до merge, не молчаливым renumber runtime. Удалять незавершённое задание с потерей identity нельзя: отмена фиксируется как Superseded до удаления файла.

### D. Запрос на запуск и детерминированный выбор

Поддержать ровно два явных селектора:

```text
AUTONOMOUS_PR TSK-0031
AUTONOMOUS_PR NEXT
```

CLI принимает `TSK-NNNN` либо literal `NEXT` вместо нынешнего обязательного Current ID. Отсутствующий selector — ошибка конфигурации, не скрытое NEXT. Имя файла в произвольном тексте, repository instructions, PR body и metadata не выдают authority.

Явный user invocation NEXT делегирует только детерминированный выбор одной допустимой задачи на стартовом snapshot. После выбора authority привязывается к её точному ID/spec; не становится разрешением traversal очереди или дальнейшего batch execution.

Read/selection порядок:

1. Fetch origin один раз для решения выбора, зафиксировать exact `origin/main` SHA.
2. Прочитать terminal-реестр и список Git-tracked regular files `docs/tasks/TSK-*.md` из этого же commit tree. Не использовать local working tree glob как authoritative catalog. Отсутствующий каталог означает пустой набор; отсутствие/ошибка terminal table — не пустая история.
3. Сначала исключить terminal ID. Их specs могут отсутствовать или иметь старый формат: body не требуется для исключения и не может снова сделать их executable.
4. Для оставшихся файлов проверить identity/metadata. Чистый draft исключить. Повреждённый envelope или approved body не пропускать молча как «неинтересную задачу»: catalog/preflight error.
5. Проверить approved execution body, size, зависимости и eligibility. Known незавершённые зависимости — ожидание, не ошибка parser. Unknown dependency, self-reference, duplicate identity или cycle — invalid catalog/dependency input. Зависимость Superseded не удовлетворена и не заменяется автоматически её преемниками.
6. Для NEXT отсортировать допустимые задачи по P0, P1, P2, P3, затем по числовой части TSK ID. Directory order, mtime, порядок выдачи Git и мнение агента не участвуют.
7. Выбрать ровно одну задачу. Для явного ID сортировку не применять: допустимый task можно выбрать вне приоритетного порядка. Невалидный/отсутствующий/terminal/draft ID не подменять другим кандидатом.
8. До implementer invocation сообщить фактический выбранный ID, selection mode, source SHA/path/spec digest и основание выбора. Не писать выбор в TASK.md.

Зависимость считается выполненной только при Done на authoritative main. Prospective Done из открытого PR не удовлетворяет зависимость. Dependency-файл завершённой задачи не нужен.

NEXT с корректным catalog, но без допустимых кандидатов завершается до создания branch и agent calls. Ввести явный run-level результат `NO_ELIGIBLE_TASK` с причинами ожидания/исключения, exit code 0 и без READY_FOR_HUMAN_MERGE. Это не reviewer verdict и не успех выполненной задачи. Ошибка input/preflight остаётся BLOCKED; review verdict set остаётся строго APPROVED/CHANGES_REQUESTED/BLOCKED. Отсутствие selector остаётся CLI configuration error.

После выбора не пересчитывать NEXT ради переключения задачи. Более приоритетный task, появившийся позже, ждёт другого invocation. Один запуск — одна задача, STOP/NO_ELIGIBLE_TASK/BLOCKED не запускают следующий task.

### E. Integration, provenance и revalidation

Новые metadata/selection — input layer. После разрешения selector использовать существующий concrete execution pipeline и actual selected task ID. Ветка по умолчанию должна называться по выбранному ID, никогда `autonomous-pr/next`.

Сохранить source identity отдельно от меняющейся review base: первоначальный `spec_source_sha`, canonical path, exact text/digest и выбранные metadata фиксируются один раз; fresh origin/main SHA для нового аудита не переписывает provenance одобренного задания.

При fresh revalidation сохранить:

- неизменность всего выбранного task document, включая metadata/approval;
- отсутствие выбранного ID в authoritative terminal-реестре до выполнения собственного closure merge;
- authoritative Done для каждой dependency;
- существующие безопасные branch/head/patch факты и допустимость execution scope.

Исчезновение/изменение выбранного spec, отзыв approval или потеря Done dependency блокируют run. Изменения несвязанных task files, новая более приоритетная задача или удаление terminal spec не меняют выбранную работу сами по себе. Materiality проверять по фактам текущей задачи, не по byte-equality всего каталога.

Fresh exact-base revalidation перед ordinary checkpoint/late-repair commit/push сохраняется. Material change не должен сначала публиковать stale implementation и лишь затем обнаруживаться. No-progress identities по-прежнему сравниваются только внутри одного gate/spec/base context; смена base не смешивает contexts.

Сохранить защиту существующих delivery branch/PR от неявного resume/дублирования. Для минимального режима используется один активный запуск на репозиторий; оператор не запускает несколько runners одновременно. Existing same-task branch/open PR — причина остановиться для MANUAL reconciliation, а не молча выбрать другую задачу или обойти collision новым именем ветки. Не заявлять, что локальные проверки обеспечивают distributed locking. Повторное использование старого runtime состояния и новая lock-инфраструктура вне scope.

В draft PR фиксировать фактический selected task ID, первоначальные source SHA/path и spec digest из orchestrator state. Это позволяет найти одобренный документ в Git-истории после удаления файла. Не требовать ручной записи этих данных пользователем, копии spec в отдельный архив или placeholder merge SHA.

Existing implementer/reviewer invocation configuration остаётся обязательной. Документировать отличие команды-поручения в чате от фактического CLI запуска настроенного harness; новый selector не создаёт provider integration автоматически.

### F. Task Closure и post-merge удаление

Нормальный autonomous closure меняет terminal-реестр только для текущей задачи, добавляет фактический PR evidence и одну delivery entry в Development Log. Не создаёт новый task, не выбирает Current/Next, не правит approval/metadata других задач, не удаляет и не переписывает собственный spec.

Все existing stages обязательны:

```text
accepted checkpoints
→ Full verification
→ accepted pre-closure cumulative implementation review
→ draft PR
→ prospective closure + independent Closure Review
→ local unpublished closure commit
→ fresh revalidation + Mode C
→ publication exact audited candidate
→ required CI
→ READY_FOR_HUMAN_MERGE → STOP
```

Сохранить materialized byte-identical root review.patch, artifact mutation detection и A/B/C diff semantics. Не использовать cumulative commit range для невошедших в commit fixes.

Closure должна сохранять весь чужой terminal-реестр. Её baseline включает exact authoritative TASK.md; optional ROADMAP/DEFERRED materiality сохраняется, если конкретная closure их затрагивает. Изменившуюся history не затирать старым snapshot. Current/Next baseline больше не нужен, но отменять closure-aware staleness guard нельзя. Unrelated movement требует корректного revalidation/review, а не автоматического разрешения публиковать старый audit.

Done становится authoritative только после merge accepted implementation и Task Closure на main. Draft PR и веточный terminal row не являются завершением. Fallback reconciliation при пропущенной closure остаётся MANUAL; следующий task с такой dependency не запускается до её завершения.

После authoritative Done или Superseded пользователь может удалить `docs/tasks/TSK-NNNN.md` отдельным обычным reviewed Git change. Нормальная процедура не переписывает Git history, не удаляет terminal evidence и не добавляет archive copy. Cleanup не получает обязательный новый TSK и не требует перезаписи очереди.

До удаления terminal spec он уже исключён из NEXT; после удаления поведение такое же. Explicit ID terminal-задачи отвечает «завершена/отменена», даже если файл отсутствует. Missing nonterminal spec никогда не интерпретируется как Done. При выбранном активном task удаление файла остаётся blocking material change.

Architecture/reference tests больше не требуют существования текущего spec для terminal ID. Новые долговечные ссылки на удаляемый документ должны вести через PR/source SHA, а не требовать вечного live path. Разрешение удалить spec после merge не является разрешением harness автоматически продолжить после STOP или писать в main.

### G. Миграция и минимальные границы модулей

Перед удалением Open task index перенести TSK-0023 в `docs/tasks/TSK-0023.md`: корректные H1/metadata, execution_approval draft, priority P2, size L, group mechanics, исходный roadmap target, пустые dependencies. Сохранить название/известное направление, не проектировать mechanics и не заполнять body вымышленными решениями. Это перенос уже существующего backlog, не новая задача и не promotion.

TSK-0029 закрывается в final migration PR как Done с реальным evidence. Его исходный девятисекционный spec допускается как terminal history до последующего ручного удаления. Никакого production `if task_id == TSK-0029`.

Не оставлять тесты, которые hardcode единственный live Current/список ID/число задач. Общие invariants обязаны работать и при пустом каталоге, и при новых approved задачах, и после удаления terminal specs; дополнить non-vacuous synthetic fixtures.

| Компонент | Вход и выход | Владелец данных / разрешённые зависимости |
| --- | --- | --- |
| Task document parser | exact text/path → immutable metadata + spec либо typed validation error | Pure Python/JSON/model; без Git, сети, subprocess и LLM |
| Catalog/selector | snapshot task records + terminal facts + selector → выбранный target либо no-work/error | Детерминированные функции; не выполняют commits и не меняют repository files |
| Repository boundary | exact ref → listing/blobs; approved side-effect → Git/gh result | Только здесь Git/gh и filesystem artifacts; агент не пишет Git напрямую |
| Orchestrator | resolved target → existing execution stages/evidence/outcome | Владеет selection/run state и transitions; не делегирует выбор LLM |
| TASK.md | инструкции + permanent terminal facts | Не хранит active queue; ordinary invocation может писать только собственную closure |

Advisory touchpoints: `task_spec.py`, `task_context.py`, `model.py`, `__main__.py`, `repository.py`, `orchestrator.py`; один узкий `task_selection.py` допустим при реальной пользе, generic workflow framework — нет. Соответствующие tests, AGENTS/Harness/TASK/CLAUDE/README и только workflow-навигация ROADMAP. `pyproject.toml` менять только при непосредственно необходимой корректировке, не добавляя dependencies.

Согласовать текущие normative references и шаблон будущей standalone task в TASK.md; сохранить историческую достоверность TSK-0027/0028. Не переписывать прежние Development Log entries. Удалённые старые runtime paths/tests не прятать переименованием в неколлектируемые функции.

### H. Проверка без случайных side effects

Core tests работают на synthetic tasks, disposable Git repositories и fake agents/gh; не требуют реального LLM или GitHub writes. Использовать действительные parser/selector и public run в integration tests, не mock целиком три execution phases.

До merge обе новые команды должны быть подтверждены реальным public flow. Проверить, что добавление одного approved файла меняет следующий результат NEXT без изменения TASK.md, а запись Done и последующее удаление файла не ломают выбор/dependencies. Это основной пользовательский acceptance scenario, не только unit-тест сортировки.

## Acceptance criteria

1. Пользователь добавляет обычное согласованное задание одним `docs/tasks/TSK-NNNN.md`; нет обязательной записи в Open index, назначения Current, изменения Next/Next free ID или отдельного queue artifact.
2. Metadata принадлежат только файлу задачи; parser строго различает draft/approved, identity, обязательные поля и содержательный execution body. Approval не выдаёт invocation authority.
3. Explicit task ID запускает допустимую задачу без Current. Invalid/missing/draft/terminal/unready ID не подменяется другой задачей.
4. NEXT использует один captured main snapshot, исключает terminal/draft/waiting tasks, выбирает по Priority → numeric ID и не зависит от file order/mtime/LLM.
5. Отсутствующий selector отвергается; NEXT без кандидатов выдаёт NO_ELIGIBLE_TASK без branch/agent/PR writes и без ложного READY.
6. Missing terminal spec допустим; retained terminal spec старого формата исключается до body validation. Terminal ID не переиспользуется.
7. Done dependency удовлетворяется registry независимо от файла; open dependency ждёт; Superseded не равен Done; unknown/self/duplicate/cyclic dependencies не проходят как разрешение execution.
8. Выбранные task ID/source SHA/text/digest фиксированы на invocation. Новая более приоритетная задача не переключает выполняющуюся работу; registry/spec reads не смешивают refs.
9. Изменение selected spec/approval/dependencies либо конкурентный terminal outcome блокируют stale side effects; acceptance guard работает для checkpoint и late repair.
10. Public lifecycle использует реальные commit/push boundaries; default branch построена по выбранному ID, не NEXT. Existing branch/PR не становится resume authorization.
11. Adaptive review/repair, required second+ diagnosis, cycle detection, spec-owned JSON argv verification и passing evidence не ослаблены. Existing phase/reporting accuracy и Git safety сохранены.
12. Pre-closure review, Closure Review, unpublished local commit, Mode C, exact publication и CI остаются отдельными gates; review.patch материализован, точен и не коммитится.
13. Closure дописывает только собственный terminal outcome/evidence и factual log, не содержит queue reselection или удаления spec. Чужая история и closure baseline защищены до publication/STOP.
14. Done авторитетен только после merge. После этого пользователь может удалить task file без второго административного queue update; cleanup не запускается автономно после STOP.
15. PR содержит реальные spec source SHA/path/digest. Не создаются архивные копии; исторические records не требуют новых source SHA задним числом.
16. TSK-0023 перенесён только как draft P2/L с прежним scope и без новой зависимости; вся прежняя terminal-история сохранена, TSK-0029 закрыт без task-specific runtime exemption.
17. Документация/CLI не заявляют поддержку старого Current-based альтернативного runtime; сохраняется один operational contract и независимый MANUAL workflow.
18. Generic architecture checks реально исполняются на synthetic approved/draft/terminal cases, не проходят только из-за пустой очереди. Удаление terminal spec и добавление нового approved файла покрыты regressions.
19. Никаких gameplay edits, новых production dependencies, daemon/queue storage/parallel scheduler, autonomous merge или автоматического cleanup.
20. Focused tests, tooling/architecture suites, full pytest, configured mypy и git diff --check проходят на final prospective-closure tree; результаты приводятся фактически, без заранее заданного числа tests.

## Known constraints / edge cases

Все обязательные ограничения из этого раздела определены также в Scope, Approved implementation approach и Acceptance criteria; здесь только указатели для review.

- Исходная версия tracker tests содержит snapshot-specific assumptions о пустой Current и TSK-0023. Registration TSK-0029 не должна ломаться из-за таких fixtures; generic readiness остаётся обязательной.
- Python 3.12+; существующие JSON/Markdown/Git/pytest/mypy достаточны. Formatter/linter не добавлять ради этой задачи. Допустимый Windows disposable basetemp workaround сообщать отдельно, не менять expected test outcomes.
- Безопасные providers/credentials/role isolation настраиваются снаружи harness. Passing fake-agent integration не доказывает настройку реального Codex окружения.
- Если потребуется новое архитектурное решение, не покрытое этим spec, или существенное расширение scope, остановить implementation для refinement. Не превращать migration в generic task platform.
- Сам этот документ до публикации является передаваемым пользователю spec, не записью authoritative Current на main. После activation обычные задания больше не требуют tracker registration.
- Future spec creation и удаление terminal файлов — обычные пользовательские Git changes с существующей review/authorization процедурой; «один файл» не означает обход branch protection, review или merge governance.
- Fresh uncommitted repair проверяется через Mode A `git diff HEAD`; cumulative `origin/main...HEAD` строится только после отдельно разрешённого commit. Generated diff никогда не должен скрывать uncommitted fixes.
- Approval в чате, success tests и готовый draft PR сами по себе не выполняют human merge. После STOP новый запуск требует новой явной команды пользователя.
