## Goal

Prevent avoidable `AUTONOMOUS_PR` terminal failures caused by a stale locally loaded harness, an undersized Codex-launcher verification timeout, and host-global temporary/pip-cache permission state, without weakening any repository, review, verification, CI, publication, or merge gate.

After this task, the supported Codex operator path must establish the following execution boundary before autonomous implementation can start:

```text
valid explicit AUTONOMOUS_PR invocation
→ repository .venv launcher
→ loaded tools.autonomous_pr package provenance == normalized repository package
→ fixed Codex executable/profile validation
→ link-safe writable dedicated runtime temp root and pip cache
→ scoped TEMP/TMP/TMPDIR/PIP_CACHE_DIR + parent tempfile binding
→ generic CLI delegation
→ fresh fetch origin
→ clean local worktree/index
→ local runtime HEAD == captured origin/main SHA
→ task catalog/selection
→ delivery branch
→ ordinary AUTONOMOUS_PR v2 flow
```

Runtime freshness has two independent proofs. First, before generic CLI delegation, the launcher must prove that the already loaded regular Python package `tools.autonomous_pr` comes from the normalized repository selected by `--repo` (or the normalized current working directory when `--repo` is omitted). Second, after the harness performs the mandatory fresh fetch, the orchestrator must prove exact commit identity between local `HEAD` and the captured `origin/main` SHA. A fresh Git SHA check against one checkout is not sufficient when the Python process could have imported `tools.autonomous_pr` from another checkout, editable-install target, or `PYTHONPATH` entry.

The local Git runtime identity check is an exact commit-SHA check, not a branch-name policy. A clean checkout on any local branch or detached state may proceed when its `HEAD` is exactly the freshly captured `origin/main` commit. A clean checkout whose `HEAD` is behind or ahead of that captured commit must stop in `PREFLIGHT` before task selection creates any delivery side effect. The harness must never `pull`, `reset`, rebase, checkout `main`, or otherwise update its own loaded runtime automatically.

The Codex launcher verification timeout default must increase from `1800.0` seconds to `3600.0` seconds. This is a local deterministic verification subprocess timeout, not a repair budget. The fixed Codex agent timeout remains `1800.0` seconds, and the separate required-CI passive-observation timeout remains `600.0` seconds. TSK-0035 deliberately established the latter as an independent remote-observation contract; local pytest duration is not evidence that the required-CI window itself is wrong.

The launcher must isolate pip's writable cache under the existing dedicated runtime temp root rather than inheriting an arbitrary user/global cache path during the delegated invocation. It must also make Python's already-cached `tempfile` default agree with the same runtime temp root for the duration of in-process generic-CLI execution, then restore every modified environment/global value exactly after success or failure.

This task changes the operational launcher/preflight mechanics that future `AUTONOMOUS_PR` invocations rely upon and therefore must be delivered in `MANUAL` mode. Do not execute TSK-0044 through `AUTONOMOUS_PR TSK-0044` or `NEXT`. Because the task metadata schema has no MANUAL-only flag, do not merge this approved task document to authoritative `main` as a standalone open task before its implementation. Put the reviewed task document, implementation, documentation synchronization, and reviewed terminal Task Closure on the same MANUAL delivery line so TSK-0044 never becomes an eligible autonomous target on `main`.

## Known constraints / edge cases

- The 3600-second verification default is a finite execution timeout, not a guarantee that every future full suite will finish inside one hour. A future measured need may justify another reviewed change or an explicit operator override; this task does not introduce adaptive timeout tuning.

- The required-CI timeout remains 600 seconds by deliberate decision. TSK-0035 defined it as a separate remote passive-observation deadline; GitHub jobs can run concurrently, and the observed local full-suite wall time does not prove this remote window is insufficient.

- The agent timeout remains 1800 seconds. There is no production evidence in this refinement that normal Codex implementer/reviewer calls require a larger default; a longer verification command does not imply a longer LLM-agent timeout.

- The fresh-runtime guard proves exact commit identity only after the TSK-0044-capable harness has started. It cannot retroactively force a pre-TSK-0044 local launcher that lacks this guard to update itself. Operators must update the local checkout to the TSK-0044-containing main once after merge before relying on the guard for future stale-runtime prevention.

- The launcher provenance guard closes the other half of that proof: it rejects a process whose loaded `tools.autonomous_pr` regular package resolves outside the selected repository even when the selected repository itself has a fresh `HEAD`. It is not a cryptographic attestation and does not protect against an adversary mutating already loaded Python objects inside the process; that threat model is outside the current local operator contract.

- Exact SHA equality is intentionally stricter than tree equality. A different local commit with an identical tree is still a different runtime base and is rejected; the harness does not infer equivalence from content.

- Local branch name is intentionally not authoritative. A detached HEAD or differently named local branch at the exact captured commit is acceptable to the new runtime-identity check; existing delivery-branch collision/safety rules still apply later.

- `origin/main` may move again after the initial capture. That is not an initial-runtime mismatch: execution remains bound to the captured exact base and the existing later revalidation machinery decides whether subsequent movement is safe or terminal.

- The dedicated `pip-cache` is execution support state, never project state or orchestration state. Its contents are not task evidence, are not committed, and do not authorize offline assumptions. Setting `PIP_CACHE_DIR` neither enables nor disables network access.

- Launcher-owned runtime directories are deliberately stricter than arbitrary system-temp ancestry: the dedicated root and `pip-cache` themselves must not be symlinks or Windows junctions. The system temp parent may have platform-specific resolution semantics; safety is established from the resolved dedicated root/cache containment and repository-exclusion checks. This task does not claim race-free protection against a concurrently malicious host replacing filesystem entries after validation.

- The launcher temporarily overrides an inherited `PIP_CACHE_DIR` during autonomous execution to guarantee a writable cache, then restores the exact original value. It does not erase or mutate the caller's original cache directory itself.

- `tempfile.tempdir` is process-global mutable state. The Codex launcher delegates synchronously and does not run multiple generic CLI invocations concurrently in one process; this task relies on that existing single-run process model and does not introduce thread/concurrency support.

- The packaging installed-wheel test copies the current environment and removes only `PYTHONPATH`, so launcher-scoped `PIP_CACHE_DIR` reaches its pip child processes. This task does not change that packaging test's dependency/network semantics.

- Upstream Codex CLI still declares the launcher flag/config surfaces at refinement time, but this is informational only. A syntax/help check does not prove operational compatibility of the installed version, `--ignore-user-config`, config overrides, or MXC runtime behavior. A future concrete compatibility failure may justify a separate task; TSK-0044 does not add a false-confidence compatibility probe.

- Subprocess timeout diagnostics, invalid UTF-8 handling, and descendant-process containment remain separate hardening concerns. This task only improves the environment and initial runtime identity around existing process boundaries.

- Full Verification still blocks on failure under current orchestration semantics. A separate following task is expected to decide and implement safe in-process repair for candidate-local Full Verification failures; TSK-0044 intentionally removes environmental false failures before that repair capability is broadened.

- TSK-0044 is execution-ready but MANUAL-only for delivery. Its approved task document is execution input for the MANUAL implementation line, not standalone authorization for commit, push, PR creation, merge, or an autonomous invocation.
