## Goal

Close the remaining pre-closure repair gap in operational `AUTONOMOUS_PR` v2: a deterministic Full Verification command that successfully starts, completes, and returns a non-zero exit code must reject the current implementation candidate and enter the existing in-process implementation-repair machinery instead of terminating the run immediately.

The task must preserve a strict boundary between a completed verification result and uncertainty at the subprocess boundary:

```text
verification command starts and completes
├─ returncode == 0
│   → passing verification result
└─ returncode != 0
    → deterministic verification rejection
    → adaptive implementation repair

verification command cannot be executed safely to completion
├─ subprocess launch OSError
└─ verification timeout
    → fail closed
    → terminal BLOCKED
```

A timeout is intentionally not repairable in this task. `subprocess.run(..., timeout=...)` does not by itself prove quiescence of every descendant process or absence of later filesystem effects. TSK-0044 reduced avoidable local-verification timeouts by increasing the supported Codex verification timeout to `3600.0` seconds and hardening temp/pip-cache state, but it did not establish safe process-tree containment. Therefore timeout remains execution uncertainty until a separate subprocess/process-containment task proves a safe continuation contract.

A launch `OSError` is likewise not candidate evidence. A missing/unusable executable, permission failure, or equivalent subprocess-start failure must surface through the existing fail-closed repository/orchestration exception boundary and must never ask an implementer to modify repository code in response.

For a completed non-zero Full Verification result, the orchestrator must reuse the existing `IMPLEMENTATION_REPAIR` / `IMPLEMENTATION_REPAIR_REVIEW` path. The first repair receives the fixed Task Execution Spec and formatted Full Verification failure evidence, with no synthetic reviewer packet or verdict. The repair candidate must pass the exact `spec.full_verification` commands before it can receive a fresh late implementation-repair review. An approved repair is then committed and pushed only through the existing orchestrator-owned acceptance boundary.

Acceptance of that repair invalidates the previously accepted checkpoint evidence. Because a Full Verification failure is task-wide and does not prove the earliest affected checkpoint, the orchestrator must conservatively replay CP-1 through CP-N, then run a new authoritative Full Verification against the resulting current accepted HEAD, then build and obtain a fresh pre-closure cumulative implementation review. The pre-repair Full Verification result and any pre-repair checkpoint/cumulative evidence are never reused as accepted evidence for Task Closure or Mode C.

Direct verification-rejection routing semantics remain unchanged. The directly upstream Full Verification rejection contributes exactly one `seed_verification_rejection_count` to the child repair episode, so the first repair stays at the existing `DELIBERATE` baseline and a second deterministic verification rejection in that same causal episode escalates the next repair to `CRITICAL`. The upstream rejection must not also be inserted as a local `GateAttempt`, which would double-count the same rejection.

No-progress needs one additional causal seed separate from routing telemetry. In the child mode-A repair gate, the failed committed HEAD is the accepted base context; therefore its unchanged candidate state is the empty uncommitted delta. The child gate seeds `_candidate_identity("")` as already rejected for cycle detection, without creating a synthetic reviewer verdict, reviewer iteration, local verification attempt, or extra verification-rejection count. If the repair implementer makes no repository change, the resulting empty mode-A patch immediately reproduces that rejected state and terminates `BLOCKED` before another verification subprocess runs.

The same direct-verification no-progress seed must also be used by the existing replayed-checkpoint → child late-repair transition so a verification-triggered repair that makes no change is rejected consistently. This does not change ordinary checkpoint verification/review structure, routing baselines, or reviewer semantics.

Because this task changes the repair and fail-closed semantics of `AUTONOMOUS_PR` itself, implementation is `MANUAL`. Do not execute TSK-0045 through `AUTONOMOUS_PR TSK-0045` or `NEXT`. The approved document, implementation, documentation synchronization, and reviewed terminal Task Closure must remain on one MANUAL delivery line; do not publish TSK-0045 on authoritative `main` as a standalone approved open task before that same delivery reaches its reviewed terminal closure. Merge remains human-only.

## Acceptance criteria

- `_run_one_verification_command()` returns `VerificationCommandResult` only for a subprocess that completed and supplied a real return code.

- Completed `returncode == 0` remains passing; completed `returncode != 0` remains a deterministic `VerificationEvidence(passed=False)` candidate failure.

- `OSError` from verification execution raises `RepositoryError` and cannot create `VerificationCommandResult(returncode=-1)`.

- `TimeoutExpired` raises `RepositoryError`; timeout is not sent to implementation repair in TSK-0045.

- Ordinary checkpoint completed non-zero verification still rejects the candidate, records `VERIFICATION_FAILURE`, skips review, and invokes implementation repair as before.

- Ordinary checkpoint timeout/OSError ends the checkpoint result fail-closed with no repair or reviewer invocation after that execution failure.

- Replay checkpoint completed non-zero verification still enters child late repair; timeout/OSError during replay is terminal fail-closed.

- A verification-triggered child late-repair gate seeds the unchanged accepted-base-relative candidate identity without a synthetic local `GateAttempt`, reviewer verdict, review iteration, finding, packet, or extra local verification-rejection metric.

- A direct verification-triggered repair that makes no repository change produces the same empty mode-A identity and terminates deterministic no-progress before another verification subprocess or designated review.

- The existing `initial_verification_rejection_count=1` routing seed remains the only routing count for the upstream rejection. The no-progress identity seed does not double-count it.

- First implementation repair caused solely by one Full Verification rejection uses existing `DELIBERATE` baseline routing.

- If the first distinct repair candidate again completes Full Verification non-zero, the local rejection is recorded; seed plus local rejection causes the next implementation repair to select `CRITICAL` with existing `REPEATED_VERIFICATION_REJECTION`.

## Known constraints / edge cases

- This task deliberately uses subprocess completion state, not stderr wording, to decide repair versus terminal execution uncertainty. A completed command may still report an environment-related error through its own non-zero exit; under the deterministic Task Execution Spec contract that remains a verification rejection subject to fixed scope, independent review, no-progress, and fail-closed safeguards. Richer process/error attribution is outside TSK-0045.

- Verification timeout becomes stricter than the current implementation: it no longer creates a repairable synthetic `returncode=-1` result. This is intentional because descendant-process quiescence has not been established. A later process-containment task may revisit timeout continuation only with positive safety evidence.

- TSK-0044's `3600.0` supported Codex verification timeout remains unchanged. TSK-0045 does not adapt timeout values or retry timed-out verification automatically.

- The direct no-progress seed is relative to the child repair gate's accepted base. It does not assert that an empty patch hash is a globally meaningful identity across different HEADs, gates, specs, or base contexts.

- The task must not hard-code the digest of an empty string in documentation or tests as a governance constant. Tests may compare identities produced by the existing `_candidate_identity()` implementation.

- A direct upstream verification rejection is causal input, not a local child-gate verification attempt. It therefore seeds routing count and no-progress comparison separately and does not appear as a synthetic `GateAttempt`.

- `previous_reviewed_candidate_identity` and `previous_reviewed_candidate_state` remain reserved for candidates actually reviewed by the designated reviewer. The direct verification seed cannot populate them.

- Full Verification repair may execute the full suite more than once: once to prove the uncommitted repair before review, and again after accepted commit/push plus checkpoint replay to create authoritative downstream evidence. This cost is intentional.

- Conservative replay begins at CP-1 even when the failing Full Verification command appears related to a later checkpoint. The orchestrator does not infer semantic impact from test names, output, changed paths, or LLM judgment.

- If `origin/main` moves during a repair episode, existing acceptance/revalidation rules decide whether continuation is safe. This task adds no parallel base polling and no new movement exception.

- `RepositoryError` raised by timeout/OSError propagates through existing phase/result boundaries. Ordinary checkpoint execution reports its existing deterministic-verification failure phase; Full Verification execution reports `Phase.FULL_VERIFICATION`; no new public phase is required.

- Failed Full Verification evidence is ephemeral causal repair input. Task Closure and Mode C continue to receive only validated passing accepted implementation evidence.

- `review.patch` remains the existing mode-A repair artifact for late implementation repair and the existing cumulative range for pre-closure review; TSK-0045 adds no diff-range mode.

- Required CI failure/cancellation after publication remains terminal under the current initial-v2 limitation. TSK-0045 only changes pre-closure deterministic Full Verification behavior.

- Subprocess bytes/Unicode diagnostics, bounded output retention, agent/reviewer process errors, and Windows/MXC descendant-process containment remain separate hardening work after TSK-0045.

- TSK-0045 is execution-ready but MANUAL-only for delivery. Its approved task document is not standalone authorization for commit, push, PR creation, merge, or autonomous invocation.
