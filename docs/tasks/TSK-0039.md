### Definition ownership and semantics

Walking speed is an immutable rules/stat-block fact and belongs to `MonsterDefinition`, not to mutable Combat or Creature State.

The resulting Domain shape is conceptually:

```python
@dataclass(frozen=True)
class MonsterDefinition(Definition):
    name: str
    ability_scores: AbilityScores
    armor_class: int
    attacks: tuple[MonsterAttackDefinition, ...] = ()
    walking_speed: int | None = None
```

`walking_speed` is measured in feet.

`None` exists only to preserve phased direct-Domain construction and unrelated existing consumers whose `MonsterDefinition` does not yet need a speed source. It does not mean speed zero and must never be silently converted to `0` or `30`.

For a non-`None` value:

```text
type(value) is int
value >= 0
```

Because Python `bool` is an `int` subclass, validation must use exact-int semantics consistent with existing numeric Definition fields so `True`/`False` are rejected.

`0` is a legitimate authoritative walking speed and must remain distinguishable from `None`.

No arbitrary upper bound and no multiple-of-5 requirement are introduced by this task.

### Packaged Monster boundary

Packaged Monster JSON is a strict untrusted boundary and has stronger completeness requirements than direct phased Domain construction.

The exact packaged Monster field set gains required `walkingSpeed`.

A packaged `"monster"` Definition lacking `walkingSpeed`, supplying `null`, supplying the wrong primitive type, or otherwise violating the Domain invariant must fail closed as `InvalidPackagedDefinitionError` through the existing packaged-definition validation/wrapping model.

Do not make `walkingSpeed` optional in the packaged decoder merely because the Domain constructor has a `None` default.

Do not add silent normalization or coercion:

```text
"30" → invalid
True → invalid
null → invalid
-1 → invalid
```

The decoder continues to discriminate the actual Definition type before the existing `expected_type` check. `DefinitionSource`, `DefinitionNotFoundError`, `DefinitionTypeMismatchError`, and resource-path validation remain unchanged.
