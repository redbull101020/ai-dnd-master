## Goal

Harden the repository/Git boundary used by `AUTONOMOUS_PR` so every path that is actually mutated by one candidate is discovered without relying on Git's human-oriented quoting or `PATH1 -> PATH2` rendering, and so rename source paths cannot disappear from deterministic scope and authority checks.

The current implementation in `tools/autonomous_pr/repository.py` reads `git status --porcelain=v1` as newline-delimited human-readable text. `intent_to_add_untracked_files()` removes surrounding quotes without decoding Git quoting, while `changed_paths()` additionally splits on the literal text ` -> ` and retains only the destination side. This creates two avoidable classes of failure:

- an untracked path whose Git status rendering uses quoting/backslash escapes can be passed back to `git add -N` under the wrong pathname and fail even though the file itself is valid;
- a tracked rename can be reduced to only its destination path, so a deterministic path allowlist may fail to see that the source path was also removed by the candidate.

After this task, path discovery must use Git's machine-readable NUL-delimited porcelain v1 format and expose one deterministic mutation-path set that is safe for checkpoint scope checks, prospective Task Closure scope checks, exact staging, and rejected-candidate discard. For a rename, both the source and destination are mutations and both must be present. For a copy record, the destination is a mutation but the original source is lineage metadata only and must not be misclassified as changed.

The task does not broaden `AUTONOMOUS_PR` authority, change A/B/C `review.patch` ranges, weaken exact-diff staging checks, or make the harness tolerant of ambiguous repository state. Malformed or internally inconsistent Git status output remains fail-closed through `RepositoryError`.

Because this task changes the deterministic enforcement boundary that protects `AUTONOMOUS_PR` scope and commit composition, it must be delivered in `MANUAL` mode. Do not execute TSK-0043 through `AUTONOMOUS_PR TSK-0043` or `NEXT`.   - the two-character porcelain `XY` status;
  - the primary path reported by porcelain v1 `-z`;
  - the original path when Git supplies rename/copy lineage, otherwise `None`.

- Add one private parser for porcelain v1 `-z` output and one repository helper that obtains that output with:
  `git status --porcelain=v1 -z --untracked-files=all`.

- Parse the `-z` stream according to Git's documented field semantics:
  - the first NUL-delimited item for a record contains `XY`, one separating space, and the primary pathname;
  - path text is preserved exactly as decoded by the repository's existing UTF-8 Git subprocess boundary; do not call `.strip()` on pathnames, remove quotes, unescape C-style path text, or split on textual arrows;

  - in `-z` rename/copy output the primary path is the target and the second pathname is the original source;

## Approved implementation approach

1. Introduce a private immutable `_WorktreeStatusRecord` in `tools/autonomous_pr/repository.py` with `xy: str`, `path: str`, and `original_path: str | None`. This type is repository-tooling state only; it is not persisted, serialized, exported as a public domain contract, or exposed through the generic CLI.

2. Introduce `_parse_porcelain_v1_z_status(status: str) -> tuple[_WorktreeStatusRecord, ...]`. Parse the NUL-separated stream without `splitlines()`, pathname `.strip()`, quote removal, or textual arrow parsing. Validate the fixed porcelain prefix shape (`XY` plus one separator space) and consume a second pathname exactly when `R` or `C` is present in `XY`. Any structurally impossible stream raises `RepositoryError`.

3. Introduce `_worktree_status_records(repo: Path) -> tuple[_WorktreeStatusRecord, ...]` that calls the existing strict Git command boundary with `["status", "--porcelain=v1", "-z", "--untracked-files=all"]` and delegates only parsing to `_parse_porcelain_v1_z_status()`. Do not create a second generic command runner.

4. Rebuild `intent_to_add_untracked_files()` on top of `_worktree_status_records()`. Select only records with `xy == "??"`, take their primary paths, de-duplicate and sort deterministically, then preserve the existing `git add -N -- <path>` behavior. A path must be passed back to Git exactly as it was parsed; human display escaping is never reconstructed.

5. Rebuild `changed_paths()` on the same records. The primary path of every returned status record is a mutation. When `R` is present in `XY`, require `original_path` and include it as a second mutation path. When only `C` supplies `original_path`, do not include that source in the mutation set. Return a sorted duplicate-free tuple of strings so downstream comparisons are independent of Git's unspecified record order.

6. Keep the existing orchestrator call signatures. The corrected `changed_paths()` result automatically strengthens ordinary checkpoint, late-repair, closure-only, staging, and discard boundaries. Change orchestrator production code only if a focused integration regression proves that one of those existing consumers incorrectly assumes a one-path rename; do not refactor neighboring orchestration merely to propagate the task.

7. Preserve `commit_reviewed_checkpoint()`'s exact reviewed-patch protections. It must still verify the current reviewed diff before staging, stage only the supplied factual path set, reject `review.patch`, compare the staged diff byte-for-byte with the reviewed patch, prove there is no remaining unstaged/untracked candidate content, and only then commit. A rename fix must not weaken any of these checks.

8. Preserve `discard_reviewed_uncommitted_candidate()`'s destructive-operation proof. It must still verify the reviewed patch and complete factual mutation set before reset/clean, revalidate the remote head, restore the exact predecessor, and finish clean. Supplying both rename endpoints is expected: after reset the original source is tracked again and `git clean -f --` must not remove it, while an untracked rejected destination may be removed.

## Known constraints / edge cases

- Git porcelain v1 `-z` record order is not a stable policy input. The task therefore requires sorted duplicate-free derived path tuples; status-record order must not control authorization or staging decisions.

- Under porcelain v1 `-z`, rename/copy records report the target pathname first and the original pathname second. The parser must preserve that distinction rather than reusing the human `PATH1 -> PATH2` order.

- Rename and copy lineage are not equivalent. A rename mutates both source and destination. A copy mutates only its destination; its original source is retained only so the structured record is parsed correctly and remains inspectable.

- Git may report a filesystem move as an `R` record or as independent deletion/addition records depending on rename detection. Both representations must lead to a complete mutation set without changing Git configuration.

- `--untracked-files=all` is intentional: intent-to-add must operate on exact untracked files rather than a human-facing collapsed directory entry.

- The task does not establish a new arbitrary-byte filename contract. Pathnames still cross the existing repository Git subprocess boundary as UTF-8 text. A broader external-process/decoding hardening task may later make that boundary more explicit, but TSK-0043 must not introduce a parallel byte-path subsystem.

- Ignored files remain outside ordinary `git status` candidate discovery, matching existing harness behavior. This task does not redefine what ignored workspace content means.

- Unmerged/conflicted paths may be surfaced by the status parser, but this task does not implement conflict resolution. Existing downstream Git/staging/revalidation checks remain responsible for failing closed when a candidate cannot be committed safely.

- A private parser unit test may use synthetic porcelain text for copy records or unusual pathname content that is difficult to create portably. Authority-level rename regressions must still use real Git repositories so the safety property is not proven only by mocked parser input.

- This hardening was identified proactively during post-TSK-0042 audit; no claim is made that a rename-based scope bypass has already occurred in production. The purpose is to close the deterministic enforcement gap before regular autonomous use makes it material.

- TSK-0043 is execution-ready but MANUAL-only for delivery. Its approved document is not standalone authorization for commit, push, PR creation, merge, or any autonomous invocation.
