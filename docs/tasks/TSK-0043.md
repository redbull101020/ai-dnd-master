## Goal

Harden the repository/Git boundary used by `AUTONOMOUS_PR` so candidate-path discovery no longer depends on Git's human-oriented pathname quoting, textual `PATH1 -> PATH2` rendering, or newline-delimited `splitlines()` parsing, and so rename source paths cannot disappear from deterministic scope and authority checks. This correctness boundary remains within the existing UTF-8 Python text subprocess transport; it does not establish exact arbitrary-byte POSIX pathname transport.

The current implementation in `tools/autonomous_pr/repository.py` reads `git status --porcelain=v1` as newline-delimited human-readable text. `intent_to_add_untracked_files()` removes surrounding quotes without decoding Git quoting, while `changed_paths()` additionally splits on the literal text ` -> ` and retains only the destination side. This creates two avoidable classes of failure:

- an untracked path whose Git status rendering uses quoting/backslash escapes can be passed back to `git add -N` under the wrong pathname and fail even though the file itself is valid;
- a tracked rename can be reduced to only its destination path, so a deterministic path allowlist may fail to see that the source path was also removed by the candidate.

After this task, path discovery must use Git's machine-readable NUL-delimited porcelain v1 format and expose one deterministic mutation-path set that is safe for checkpoint scope checks, prospective Task Closure scope checks, exact staging, and rejected-candidate discard. For a rename, both the source and destination are mutations and both must be present. For a copy record, the destination is a mutation but the original source is lineage metadata only and must not be misclassified as changed.

The task does not broaden `AUTONOMOUS_PR` authority, change A/B/C `review.patch` ranges, weaken exact-diff staging checks, or make the harness tolerant of ambiguous repository state. Malformed or internally inconsistent Git status output remains fail-closed through `RepositoryError`.

Because this task changes the deterministic enforcement boundary that protects `AUTONOMOUS_PR` scope and commit composition, its implementation must be delivered in `MANUAL` mode. Do not execute TSK-0043 through `AUTONOMOUS_PR TSK-0043` or `NEXT`, and do not use it as an autonomous canary. An accidental standalone approved publication already occurred and was repaired by PR #131; after this reviewed refinement, production implementation, documentation synchronization, and terminal closure must remain on this one MANUAL delivery line, with merge performed only by a human.

## Scope

- Replace the two ad hoc line-oriented `git status --porcelain=v1` parsers in `tools/autonomous_pr/repository.py` with one private structured status-discovery boundary. Candidate paths must no longer depend on human-oriented Git pathname quoting, textual `PATH1 -> PATH2` rendering, or newline-delimited `splitlines()` parsing; exactness remains bounded by the existing UTF-8 Python text subprocess transport.

- Add a private immutable status-record representation carrying exactly:
  - the two-character porcelain `XY` status;
  - the primary path reported by porcelain v1 `-z`;
  - the original path when Git supplies rename/copy lineage, otherwise `None`.

- Add one private parser for porcelain v1 `-z` output and one repository helper that obtains that output with:
  `git status --porcelain=v1 -z --untracked-files=all`.

- Parse the `-z` stream according to Git's documented field semantics and this fail-closed structural contract:
  - `status == ""` is valid and returns an empty tuple;
  - every non-empty stream must end in NUL; the end of the Python string is never an implicit terminator, and a missing terminal NUL raises `RepositoryError`;
  - the first NUL-delimited token for each record contains exactly two `XY` status characters, one separator space as its third character, and a non-empty primary pathname; a short/malformed prefix, invalid separator, or empty primary path raises `RepositoryError`;
  - validate structure without inventing an exhaustive whitelist of Git `XY` combinations or duplicating Git's status state machine;
  - when `R` or `C` occurs in either `XY` column, consume exactly one following NUL-delimited non-empty pathname as `original_path`; missing or empty lineage raises `RepositoryError`;
  - in `-z` rename/copy output the primary path is the target/destination and the second pathname is the original/source;
  - path text is preserved exactly as decoded by the existing UTF-8 Git subprocess boundary; do not use `splitlines()`, call `.strip()`, `.lstrip()`, or `.rstrip()` on pathnames, remove quotes, manually C-unescape path text, or split on textual arrows;
  - do not guess pathname pairing or silently recover a dangling or structurally impossible token sequence; raise `RepositoryError`.

- Keep `intent_to_add_untracked_files(repo) -> tuple[str, ...]` as the existing caller-facing shape, but derive it only from structured records whose status is exactly `??`. Because `--untracked-files=all` is used, operate on exact untracked file paths rather than relying on a collapsed directory display. Return a deterministic, duplicate-free tuple and pass the exact returned path strings to `git add -N --`.

## Known constraints / edge cases

- Git porcelain v1 `-z` record order is not a stable policy input. The task therefore requires sorted duplicate-free derived path tuples; status-record order must not control authorization or staging decisions.

- Under porcelain v1 `-z`, rename/copy records report the target pathname first and the original pathname second. The parser must preserve that distinction rather than reusing the human `PATH1 -> PATH2` order.

- Rename and copy lineage are not equivalent. A rename mutates both source and destination. A copy mutates only its destination; its original source is retained only so the structured record is parsed correctly and remains inspectable.

- Git may report a filesystem move as an `R` record or as independent deletion/addition records depending on rename detection. Both representations must lead to a complete mutation set without changing Git configuration.

- `--untracked-files=all` is intentional: intent-to-add must operate on exact untracked files rather than a human-facing collapsed directory entry.

- The existing Git subprocess boundary is a UTF-8 Python text stream. This task does not establish exact arbitrary-byte pathname transport and does not promise exact POSIX pathname transport for CR/CRLF byte sequences because text mode may normalize newlines. Changing `_run()`, subprocess text mode, decoding, or introducing a byte-path subsystem is separate future hardening.

- Ignored files remain outside ordinary `git status` candidate discovery, matching existing harness behavior. This task does not redefine what ignored workspace content means.

- Unmerged/conflicted paths may be surfaced by the status parser, but this task does not implement conflict resolution. Existing downstream Git/staging/revalidation checks remain responsible for failing closed when a candidate cannot be committed safely.

- A private parser unit test may use synthetic porcelain text for copy records or unusual pathname content that is difficult to create portably. Authority-level rename regressions must still use real Git repositories so the safety property is not proven only by mocked parser input.

- This hardening was identified proactively during post-TSK-0042 audit; no claim is made that a rename-based scope bypass has already occurred in production. The governance incident was instead the accidental standalone approved publication at `b8b229a3add47a8321a2b3a031117764ce8c2159`, which temporarily exposed the task to `NEXT` and was repaired by PR #131 / `564eecf6f844f5ec0eec5fec7fbde54d2974da43` before MANUAL refinement resumed.

- TSK-0043 is execution-ready but MANUAL-only for delivery. Its approved document is not standalone authorization for commit, push, PR creation, merge, or any autonomous invocation.
