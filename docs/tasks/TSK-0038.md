## Goal

Зафиксировать в repository governance пользовательский принцип, что planning/refinement будущих задач по умолчанию должен завершаться не vague design intent и не крупной `L`-задачей, а одной или несколькими полностью проработанными `S/M` Task Execution Specs, которые содержат все применимые material scope / architecture / contract decisions, имеют deterministic verification и обычно пригодны для запуска через `AUTONOMOUS_PR`.

После TSK-0038 repository должен направлять каждый будущий task-planning cycle по следующему default flow:

```text
Roadmap capability / requested change
→ planning and refinement
→ inspect current canonical sources and implementation
→ identify all material unresolved questions
→ resolve them during planning
→ persist any new canonical architecture decision through the normal canonical-doc procedure
→ decompose L or independently mergeable work
→ approve and publish one or more execution-ready S/M task specs
→ separate explicit AUTONOMOUS_PR <ID|NEXT> invocation
→ deterministic implementation / verification / review
→ human merge
```

Ключевой принцип:

```text
execution-ready is the default quality bar;
AUTONOMOUS_PR is the ordinary preferred delivery path for an eligible approved task;
MANUAL delivery is an authority/delivery exception, not permission for a vague task.
```

TSK-0038 не меняет runtime `AUTONOMOUS_PR`, его authority, selector semantics, parser format, task metadata schema, development modes или human-only merge boundary. Она меняет только planning/refinement governance и agent-facing instructions, чтобы future task authors consistently доводили work до существующего `execution-ready` стандарта до approval.

### Existing repository rules already in place

`docs/TASK.md` already defines:

- `draft` task documents are never executable;
- approved task documents contain all nine execution sections and no unresolved execution requirement;
- `S` is a narrow coherent slice;
- `M` is larger but still cohesive/reviewable;
- `L` is too broad or insufficiently understood for execution as one task;
- approved executable work is `S` or `M`;
- `L` must be decomposed before approval;
- every task must remain independently reviewable and mergeable;
- `NEXT` selects only eligible approved S/M tasks.

`docs/AUTONOMOUS_PR_HARNESS.md` already defines `execution-ready` on the execution side:

- approved specs must be concrete and contain no unresolved/open decision blocking execution;
- a Task Execution Spec cannot introduce a new architectural decision not already recorded through normal repository procedure;
- a spec may cite an approved architectural decision but may not be the source that creates it;
- an implementer may take local coding decisions only when they do not expand scope, change canonical contracts, violate approved implementation approach, alter required results, require a new architectural decision or add an unapproved production dependency;
- a required missing architecture/scope/decision produces terminal `BLOCKED` rather than being invented by the orchestrator or agent.

`AGENTS.md` already requires agents to inspect current Architecture/Roadmap/Task sources, preserve canonical architecture, avoid silent conflict resolution and follow eligible standalone tasks. It does not yet state the planning default that task authors should resolve material questions before approval and target AUTONOMOUS_PR-suitable execution-ready S/M specs by default.

### Gap addressed by TSK-0038

The repository currently specifies what an already-approved execution-ready task must look like, but does not explicitly define the intended **planning/refinement strategy** that should produce it.

Without an explicit planning policy, a future agent may unnecessarily create a design-only task followed by an implementation task when the architecture could have been resolved during the current planning cycle, or may leave material choices for an autonomous implementer/reviewer to discover, or may treat `MANUAL` as permission to accept lower specification quality.

TSK-0038 closes that governance gap without changing runtime mechanics.

### Planning conversation is not project storage

A decision reached in chat/planning is not durable project truth by itself.

The planning policy must distinguish:

```text
task-specific implementation decision
→ may be persisted as binding content in the approved TSK

new canonical architecture decision
→ must first be recorded through the normal canonical procedure
   (ARCHITECTURE.md + DECISIONS.md as applicable)
→ approved TSK may then cite/rely on it
```

When a planning cycle discovers and resolves a new canonical architecture decision, its canonical-doc update and the resulting approved task spec(s) may be prepared and reviewed in the same **MANUAL planning/publication PR**, provided repository authority and document ownership rules are satisfied. A separate architecture-only TSK is not required merely because architecture work occurred during planning.

### Delivery mode

TSK-0038 itself is **MANUAL**.

Reason: it changes the governance that controls how future autonomous task inputs are refined and approved. It must not self-host that governance change through `AUTONOMOUS_PR`.

The task itself must nevertheless be fully execution-ready. MANUAL delivery does not weaken specification quality.

Commit, push, PR creation and merge remain separate MANUAL user authorizations.

## Approved implementation approach

**A. Keep one existing concept: `execution-ready`.** Do not create `semantic-ready`, `autonomous-ready` or another lifecycle/readiness state. TSK-0038 changes how planning/refinement reaches the existing approved/execution-ready contract.

**B. Make execution-ready S/M the default planning result.** `docs/TASK.md` explicitly states that ordinary future task planning/refinement aims to publish one or more independently mergeable execution-ready S/M specs, ordinarily suitable for AUTONOMOUS_PR.

**C. Distinguish quality from delivery authority.** MANUAL/AUTONOMOUS_PR describes how a task is delivered. Execution readiness describes task quality. A MANUAL task still receives the same material-decision/refinement discipline.

**D. Resolve material decisions before approval.** During planning, inspect the current repository and close every applicable decision whose absence would force execution to choose scope/architecture/contracts. A task is not approved while such a choice remains open.

**E. Preserve local implementation freedom.** The task does not pre-specify every private helper, variable, test fixture or local refactor. Existing Harness §24 remains the boundary.

**F. Persist canonical architecture before autonomous execution.** A planning conversation may decide new architecture, but chat is not authoritative project storage. If the decision changes canonical system behavior/contracts, update `ARCHITECTURE.md` and append the required `DECISIONS.md` record through normal MANUAL review before an autonomous execution task relies on it.

**G. Allow one planning/publication PR when appropriate.** When architecture and an implementation task are refined in one planning cycle, a MANUAL publication change may include both canonical architecture/decision updates and the resulting approved TSK file. This avoids an unnecessary architecture-only TSK while ensuring canonical truth exists on `main` before the separate AUTONOMOUS_PR invocation.

**H. Keep architecture-only tasks exceptional.** Use a separate architecture-only TSK only when that architecture/documentation outcome is independently valuable/reviewable or should be accepted separately before implementation.

**I. Decompose before approval, based on cohesion.** L work must be split into independently mergeable S/M outcomes. Do not use a hard checkpoint/file-count threshold.

**J. Keep draft as the refinement state.** Draft remains non-executable and may be incomplete. Do not add a planning status or extra metadata.

**K. Keep binding decisions in binding sections.** Task-specific decisions that control execution belong in Goal, Scope, Out of scope, Approved implementation approach, Acceptance criteria, checkpoint Objective/Required result/Constraints/Verification or Full verification as applicable. Context/Known constraints/Review focus alone never carries a binding requirement.

**L. Update workflow text, not runtime mechanics.** The canonical task workflow explicitly includes planning, decision resolution, canonical persistence and decomposition before task publication. The subsequent AUTONOMOUS_PR flow remains unchanged.

**M. Keep AGENTS concise and discoverable.** Add one short subsection to `Working method`, because that is the instruction surface a coding agent reads before task planning. Link to TASK for details rather than duplicating policy.

**N. Add only a narrow regression.** Extend `test_task_tracker.py` with one governance test confirming stable policy anchors remain present. Do not encode full Markdown paragraphs or add executable tooling logic.

**O. Deliver TSK-0038 in MANUAL.** It changes future task-governance inputs and must not self-host. Commit/push/PR/merge remain separately authorized.

## Known constraints / edge cases

- `execution-ready` is an existing repository term and remains the only readiness concept. This task changes the planning policy that leads to it, not the runtime definition.
- “Suitable for AUTONOMOUS_PR by default” is a planning target, not an authorization grant. Publication/approval still never activates AUTONOMOUS_PR.
- Some tasks legitimately require MANUAL delivery because they change governance, authority, dependencies or other boundaries that should not self-host. They should still be execution-ready before implementation begins.
- Some architecture-only tasks remain legitimate. The policy prevents creating them mechanically when planning can resolve architecture and publish canonical decisions plus an implementation-ready task together.
- A new canonical architecture decision cannot live only in an approved task. `ARCHITECTURE.md` owns canonical system behavior/contracts and `DECISIONS.md` records rationale/history. The task may cite those decisions after normal publication.
- Task-specific implementation choices that do not alter canonical architecture may be binding inside the approved task itself.
- The policy must not force every task to discuss State, Commands, Events, persistence or schema when those concerns are not applicable. The requirement is to resolve every applicable material decision.
- The policy must not turn execution-ready specs into line-by-line coding scripts. Local implementation freedom remains intentionally available under existing Harness §24.
- “Independently mergeable” is a decomposition signal, not the only one. Cohesion, independently observable outcomes and review/verification boundaries must be considered together.
- A task may legitimately contain several checkpoints. Checkpoint count alone is never a decomposition threshold.
- Draft task files remain optional during early planning. A planning conversation may produce an approved task only after refinement is complete; it does not need to create an early placeholder draft.
- TSK-0023 is intentionally not modified here. After TSK-0038, it should be revisited under the new policy and either refined/decomposed or superseded through the existing terminal-governance procedure as appropriate.
- This task intentionally does not add a semantic readiness linter. Architectural completeness requires informed planning/review and cannot be reliably proven by regex without creating false confidence.
- The focused regression test may assert stable short phrases or equivalent compact anchors. It should not freeze paragraph formatting or prevent future editorial improvements.
- Because implementation scope is documentation/process guidance plus one architecture governance test, current AGENTS testing policy does not require full gameplay pytest or mypy. If implementation unexpectedly changes executable tooling, stop and refine the task rather than silently broadening verification.
