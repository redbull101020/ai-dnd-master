## Goal

Повысить сходимость operational `AUTONOMOUS_PR` v2 review/repair loop без ослабления его строгости: каждый blocking finding должен быть привязан к конкретному binding requirement и описывать наблюдаемый failure mode; designated reviewer должен завершать полный material review применимых требований до verdict и агрегировать найденные независимые дефекты в один `CHANGES_REQUESTED`; implementer должен выполнять внутренний pre-review conformance pass до передачи candidate; run должен выдавать диагностическую review-convergence telemetry, производную только от уже существующей in-memory истории gate.

После этой задачи повторный `CHANGES_REQUESTED` должен быть диагностически различим как минимум между: повторно неустранённым требованием, новым binding basis, впервые обнаруженным после первого review, и deterministic verification failure до review. Ни одна новая метрика не становится gate, repair limit или основанием для автоматического `APPROVED`/`BLOCKED`.

## Scope

1. Расширить provider-neutral `RepairFinding` двумя обязательными полями: `binding_basis` и `failure_mode`, сохранив существующие `problem`, `evidence`, `required_outcome`, `recommended_repair`, `verification_focus` и optional `affected_paths`.
2. Ввести узкую синтаксическую grammar для `binding_basis`, достаточную для stable audit/telemetry: binding section Task Execution Spec, binding field конкретного checkpoint или repository contract reference; advisory `Review focus` не является допустимым binding basis.
3. Обновить structured reviewer-output parsing fail-closed: отсутствующий, пустой или синтаксически недопустимый `binding_basis`, а также отсутствующий/пустой `failure_mode`, делают `CHANGES_REQUESTED` malformed и завершают run по существующим правилам.
4. Канонизировать verdict semantics: `APPROVED` означает завершённый applicable material pass без доказанного binding defect; `CHANGES_REQUESTED` означает один или более доказанных repairable binding defects внутри fixed spec; `BLOCKED` означает, что корректное продолжение требует отсутствующего решения, scope, architecture contract, dependency или иной информации, которой fixed approved spec не предоставляет.
5. Обязать designated reviewer до verdict пройти все binding requirements, применимые к текущему gate, и при `CHANGES_REQUESTED` вернуть все независимые material findings, обнаруженные этим pass. Optional improvements, style preferences, speculative generalization и advisory guidance не являются blocking findings без отдельного binding basis.
6. Определить gate-specific applicability: checkpoint review проверяет task-wide boundaries и только текущий checkpoint; pre-closure cumulative review проверяет полный implementation contract; closure review проверяет только canonical prospective closure content/evidence и его governance constraints; Mode C остаётся final cumulative branch audit; late implementation-repair review проверяет repair против исходных findings и применимых task/repository boundaries до обязательного downstream replay.
7. Для second-or-later review одного gate сохранить fresh independent context, но требовать логический порядок: сначала проверить previous reviewer findings на текущем candidate, затем выполнить полный fresh material pass; текущий repair packet содержит только дефекты, которые остаются material на текущем candidate, включая новые независимые defects, найденные fresh pass.
8. Обновить все candidate-changing implementer handoffs так, чтобы перед возвратом implementer выполнял внутренний context-appropriate conformance pass по применимым binding requirements и исправлял найденные нарушения. Этот self-check не создаёт отдельный artifact/verdict, не становится evidence и не передаётся designated reviewer как утверждение implementer о собственной корректности.
9. Добавить review-convergence telemetry как чистую производную от существующих `GateHistory`/`GateAttempt`: review iterations, `CHANGES_REQUESTED` count, verification rejections, findings/binding bases по review iteration, binding bases впервые появившиеся после первого review, binding bases повторившиеся на нескольких `CHANGES_REQUESTED`, и последний reviewer verdict при его наличии.
10. Сделать telemetry доступной в `RunResult` и final CLI report в детерминированном machine-readable представлении для всех уже наблюдавшихся gate histories, не создавая persisted run state, database, dashboard или нового audit store. Для run без designated review telemetry остаётся пустой.
11. Добавить короткое authoring guidance в `docs/TASK.md`: для orchestration/tooling tasks material boundary failure modes, если они известны при refinement, должны быть представлены в binding `Constraints`, `Acceptance criteria` и/или deterministic `Verification`; одного advisory `Review focus` недостаточно, чтобы сделать требование binding.
12. Синхронизировать `AGENTS.md` и `docs/AUTONOMOUS_PR_HARNESS.md` с новым operational review contract; проверить `CLAUDE.md` и обновить только если его deliberately duplicated guidance становится неточной. Добавить/обновить focused tests и выполнить full tooling regression.

## Approved implementation approach

### A. Binding-grounded repair findings

`RepairFinding` остаётся узким provider-neutral value object. К существующим полям добавить:

- `binding_basis: str` — точная нормативная основа, делающая finding blocking;
- `failure_mode: str` — конкретное наблюдаемое несоответствие candidate этому requirement или конкретный неправильный outcome, который candidate допускает.

`binding_basis` использует один из трёх форматов:

- `task:<section>` — где `<section>` один из `goal`, `scope`, `out_of_scope`, `approved_implementation_approach`, `acceptance_criteria`, `full_verification`;
- `checkpoint:<CP-N>:<field>` — где `<field>` один из `objective`, `required_result`, `constraints`, `verification`;
- `repo:<reference>` — непустая repository-relative contract reference, например `repo:AGENTS.md#review-authority` или `repo:docs/AUTONOMOUS_PR_HARNESS.md#25`.

Parser проверяет только эту grammar и непустые required strings. Он не строит requirement graph и не решает semantic applicability requirement к candidate — это остаётся задачей designated reviewer и gate-specific handoff. `review_focus` намеренно отсутствует в grammar: по §24 это advisory ordering hint.

`recommended_repair` остаётся обязательным для actionable handoff, но является advisory способом достижения `required_outcome`. Implementer обязан удовлетворить binding requirement/required outcome, а не копировать предложенную reviewer'ом реализацию, если другой внутри-scope способ корректнее.

### B. Complete material review semantics

Общая reviewer instruction должна быть одна по смыслу для всех review builders и отличаться только gate-specific applicability. Перед verdict designated reviewer обязан:

1. определить применимые к gate binding requirements;
2. проверить полный current review artifact и переданное deterministic evidence;
3. при repeat review сначала перепроверить previous findings на текущем candidate;
4. после этого выполнить fresh pass остальных применимых requirements;
5. вернуть verdict только после завершения pass.

`CHANGES_REQUESTED` содержит все независимые material defects, найденные этим pass. Finding без доказуемого binding basis недопустим. Не являются blocking сами по себе: style preference, более красивый refactor, speculative abstraction, дополнительная generalization, advisory `Review focus`, будущий scope или иной outcome, которого fixed spec/repository contract не требует.

Gate applicability фиксируется так:

- **Checkpoint review:** `task:goal`, `task:scope`, `task:out_of_scope`, `task:approved_implementation_approach`, binding fields только текущего `CP-N`, и применимые `repo:*` contracts. Final `task:acceptance_criteria` и `task:full_verification` не являются самостоятельным основанием требовать future-checkpoint result досрочно.
- **Pre-closure cumulative implementation review:** весь binding Task Execution Spec, все declared checkpoints, Full verification и применимые repository contracts.
- **Late implementation-repair review:** исходные findings/required outcomes плюс task-wide boundaries и применимые repository contracts; затем существующий replay заново подтверждает downstream cumulative evidence.
- **Prospective Task Closure review:** exact closure diff, factual evidence и repository closure/governance contracts; это не повторный полный implementation review.
- **Mode C:** весь final cumulative candidate — implementation + unpublished closure — против полного applicable task/repository contract.

Три verdict tokens и текущий fail-closed handling malformed reviewer output сохраняются.

### C. Implementer pre-review conformance

Каждый implementer handoff, который может изменить candidate, получает context-specific pre-return instruction выполнить внутренний conformance pass и исправить найденные нарушения до возврата:

- ordinary checkpoint implementation;
- checkpoint repair после review/verification feedback;
- late implementation repair;
- prospective Task Closure preparation/repair.

Для implementation checkpoint pass покрывает task-wide scope/out-of-scope/approved approach, current checkpoint Required result/Constraints, current repair packet при наличии и релевантные negative/fail-closed cases, прямо следующие из этих requirements. Для closure pass покрывает только closure content/evidence и existing closure boundaries.

Orchestrator не парсит и не сохраняет self-assessment implementer'а. Никакой новый self-review artifact не передаётся reviewer. Designated review остаётся fresh, independent и основанным на fixed spec, exact patch, deterministic evidence и разрешённой previous-review history.

### D. Review-convergence telemetry

Добавить узкий immutable `ReviewGateMetrics` (или эквивалентную dataclass с тем же смыслом) и pure summarizer одного `GateHistory`. Минимальные поля:

- `gate_id`;
- `review_iterations`;
- `changes_requested_count`;
- `verification_rejection_count`;
- `findings_per_review`;
- `binding_bases_per_review`;
- `new_binding_bases_after_first_review`;
- `repeated_binding_bases`;
- `last_reviewer_verdict`.

`findings_per_review` и `binding_bases_per_review` соответствуют фактическим designated review iterations; `APPROVED`/`BLOCKED` iteration имеет zero findings, если reviewer не возвращает repair packet. `new_binding_bases_after_first_review` содержит exact basis strings, впервые появившиеся в `CHANGES_REQUESTED` после review iteration 1. `repeated_binding_bases` содержит basis strings, появившиеся в `CHANGES_REQUESTED` более чем в одной review iteration. Порядок этих derived collections детерминирован по первому фактическому появлению, без timestamps.

Это diagnostic telemetry, а не correctness signal: она никогда не влияет на verdict, retry, no-progress, replay, phase transition или merge readiness.

`RunResult` получает backward-compatible default-empty `review_metrics`. Orchestrator включает metrics всех gate histories, которые фактически возникли и доступны до terminal return, в том числе при `BLOCKED` после review activity. `NO_ELIGIBLE_TASK` и pre-review failures возвращают пустой tuple.

CLI выводит каждую metric в стабильном machine-readable JSON line с явным префиксом; формат не содержит prompts, secrets, full patches или hidden model reasoning.

### E. Documentation ownership and authoring guidance

`docs/AUTONOMOUS_PR_HARNESS.md` остаётся подробным operational contract владельцем verdict/repair/material-pass/gate-applicability/telemetry semantics. `AGENTS.md` получает только короткую load-bearing governance формулировку: blocking finding должен иметь binding basis; reviewer завершает applicable material pass; advisory preference сама по себе не блокирует.

`docs/TASK.md` получает только task-authoring guidance для orchestration/tooling refinement: известный material failure mode должен быть перенесён из advisory discussion в binding task content и, где это возможно, в deterministic verification. Формат standalone task и девять execution sections не меняются.

`CLAUDE.md` меняется только если его существующая краткая operational выжимка после этих изменений становится фактически неверной. `README.md`, `docs/ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md` и gameplay documentation не меняются, если реализация соответствует этому spec и не создаёт отдельного нового architectural contract вне development workflow.

## Acceptance criteria

1. `RepairFinding` требует непустые `binding_basis` и `failure_mode`; существующие required fields сохраняются, `affected_paths` остаётся optional.
2. `binding_basis` принимает только утверждённые `task:*`, `checkpoint:CP-N:*` и непустой `repo:*` formats; advisory `Review focus` не может быть encoded как binding section/field.
3. Malformed/missing `binding_basis` или `failure_mode` в `CHANGES_REQUESTED` обрабатываются тем же fail-closed reviewer-output path, что и другие malformed repair packets; они никогда не преобразуются в `APPROVED`.
4. `recommended_repair` документирован и используется как advisory implementation suggestion; `required_outcome` и binding requirement остаются обязательной целью repair.
5. Reviewer handoff для каждого operational review gate явно требует полный applicable material pass до verdict и запрещает blocking findings, основанные только на preference/advisory/future scope.
6. Checkpoint review не требует result будущего checkpoint только на основании final Acceptance criteria/Full verification; current CP binding fields, task-wide boundaries и repository contracts остаются проверяемыми.
7. Pre-closure cumulative review проверяет полный implementation contract; closure review остаётся closure-scoped; Mode C остаётся final cumulative audit; late repair review не подменяет обязательный downstream replay.
8. На second-or-later review previous findings сначала оцениваются против current candidate, после чего выполняется fresh pass; current repair packet не обязан повторять уже исправленные defects.
9. Initial checkpoint implementation, checkpoint repair, late implementation repair и closure preparation/repair prompts требуют internal pre-return conformance pass.
10. Implementer self-assessment не добавляется в structured reviewer input, не становится accepted evidence и не создаёт новый review gate.
11. `ReviewGateMetrics` детерминированно вычисляется из существующей gate history и различает review count, CR count, verification rejections, findings/bases per iteration, late-first-seen bases и repeated bases.
12. Telemetry никогда не участвует в approval/block/retry/no-progress/replay decisions и не вводит numeric repair budget.
13. `RunResult` backward-compatibly несёт zero-or-more review metrics; runs без review activity возвращают пустую telemetry, а terminal returns после review activity сохраняют доступные metrics.
14. CLI выдаёт metrics в стабильном machine-readable виде без prompts, patches, secrets или hidden reasoning.
15. Existing fresh reviewer isolation, exact `review.patch`, candidate identity, non-convergence diagnosis, no-progress/cycle detection, evidence invalidation, unpublished closure, Mode C, CI и human-only merge semantics не ослаблены.
16. `docs/TASK.md` получает узкое authoring guidance по material failure modes orchestration/tooling tasks без изменения standalone task schema, NEXT selection или terminal registry.
17. Никаких model/provider escalation rules, second reviewer/quorum, persisted run state, gameplay edits, production dependencies или CI-topology changes не добавлено.
18. Focused reviewer/parser/orchestrator/CLI tests, architecture/process tests, full pytest, configured mypy и `git diff --check` проходят на final prospective-closure tree.

## Known constraints / edge cases

Все ограничения, влияющие на execution, уже находятся в Scope, Out of scope, Approved implementation approach, Acceptance criteria и checkpoint Constraints; этот раздел только фиксирует контекст для review.

- Structured prompts могут требовать полный semantic pass, но обычный Python-код не может доказать внутреннее качество reasoning opaque external reviewer; deterministic enforcement ограничен output shape, repository/evidence boundaries и существующими fail-closed checks.
- Exact `binding_basis` strings используются для diagnostics. Эквивалентные требования, сформулированные reviewer'ом разными допустимыми `repo:*` references, могут выглядеть как разные telemetry bases; эти metrics не используются как correctness gate.
- Fresh-context capability и отсутствие direct Git/GitHub write capability внешних implementer/reviewer executables по-прежнему являются operator/configuration assertions с существующими defense-in-depth repository guards.
- Первый production `AUTONOMOUS_PR` pilot после этой задачи должен быть отдельной approved S/M task с уже решённой архитектурой, objective deterministic verification и ограниченным cross-layer risk.
- Автоматическое повышение model/effort имеет смысл оценивать только после накопления telemetry нескольких реальных runs; TSK-0030 не предрешает такую policy.
