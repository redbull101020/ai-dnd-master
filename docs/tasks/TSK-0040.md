## Goal

Implement the first authoritative runtime voluntary-Movement vertical slice for an active Monster in Combat, using the already-implemented Combat-owned tactical positions and authoritative Monster base walking speed.

After this task, an active positioned Monster with an authoritative non-`None` `MonsterDefinition.walking_speed` can issue one or more `MoveCombatantCommand` instances during its current turn. Each successful Command moves that same Monster from its current `CombatPosition` to one requested destination, records one `CombatantMoved` V1 Event, accumulates the deterministic whole-foot distance in `CombatState.movement_spent`, persists the replacement `CombatState` exactly once, and leaves the Monster's ordinary Action resource independent and unchanged.

The slice must support split movement across multiple Commands in one turn while preventing cumulative voluntary movement beyond the authoritative Monster walking speed. `TurnAdvanced` resets `movement_spent` to `0` for the new active turn. State schema V10 persists the new turn-local expenditure fact while remaining strictly additive over V9.

This task implements the runtime contract fixed by Architecture §3.38, the State schema V10 contract in Architecture §12.13, and DEC-0054. It does not implement Character voluntary Movement, Dash, Disengage, Reactions, Opportunity Attacks, difficult terrain, forced movement, pathfinding, collision, occupancy, or a generic Movement framework.

## Approved implementation approach

### Canonical execution boundary

This task is the production implementation continuation of Architecture §3.38 / DEC-0054 and the additive V10 contract in Architecture §12.13.

The implementation must not change the Movement owner, Command shape, actor/mover identity, distance policy, budget semantics, Event payload, reset policy, schema compatibility policy, validation precedence, failure mapping, or explicit exclusions fixed by those published contracts.

If authoritative `main` does not contain Architecture §3.38, the corresponding §12.13 V10 contract, and DEC-0054 at preflight, execution must stop. The implementer must not infer those contracts from this task or from conversation history.

### State ownership and turn-local expenditure

`CombatState.positions` remains the sole authoritative tactical position State. `movement_spent` is another field on that same existing Combat State Owner because it describes only how much distance the current `active_creature_id` has already voluntarily moved during its current turn.

The canonical shape becomes conceptually:

```python
@dataclass
class CombatState:
    id: str
    round: int
    order: tuple[str, ...]
    active_index: int
    positions: tuple[CombatPosition, ...] = ()
    action_spent: bool = False
    movement_spent: int = 0
```

`movement_spent` is not remaining Movement and is not Definition data. Remaining capacity is derived at the Movement boundary from authoritative `MonsterDefinition.walking_speed - combat.movement_spent`; no second remaining-capacity fact is persisted.

The Domain State invariant is only exact non-negative integer expenditure. `CombatState` must allow values greater than a particular Monster's current walking speed because the State object has no Definition context and because later mechanics may alter available speed without making already-recorded expenditure structurally corrupt.

### State schema V10

State schema V10 is strictly additive over V9. The only new wire field is required non-null-Combat field:

```text
movementSpent: int
```

with exact integer / non-negative semantics.

V10 must preserve every V9 behavior, including:

```text
Creature.conditions
Character skillProficiencies
Character weaponProficiencies
Character deathSaveSuccesses
Character deathSaveFailures
Character deathSaveStable
Character dead
Inventory
Equipment
Combat.positions
Combat.actionSpent
```

The implementation must audit every explicit serializer version set/branch that currently names V9 and include V10 wherever V10 inherits that V9 semantic. In particular, V10 must continue using the V9 Character field set and lifecycle decoding rather than accidentally falling back to an older Character schema.

Historical schema contracts remain exact. V5–V9 active Combat loads with `movement_spent=0`; historical payloads do not acquire an optional `movementSpent` field. V10 requires it for non-null Combat. Saving a successfully loaded historical snapshot materializes the current V10 shape.

### Turn lifecycle compatibility

`CombatStarted` V1 remains unchanged. The first active turn receives `movement_spent=0` from the `CombatState` default.

`TurnAdvanced` V1 remains unchanged. `apply_turn_advanced_v1` resets both current-turn facts:

```text
action_spent = False
movement_spent = 0
```

The reset is a State-projection rule for the new active turn, not a new Event payload fact.

Existing Character Death Save turn-start orchestration must remain compatible: when `AdvanceTurnHandler` or `StartCombatHandler` also processes the existing Character lifecycle consequences, the resulting snapshot must preserve the correct Combat `movement_spent` reset/default and any Character replacement in the same existing single-save transaction.

`TurnActionSpent` and placement Event appliers use `dataclasses.replace`-style concrete projection and must preserve `movement_spent` unless their own contract explicitly changes it. Attack persistence must likewise preserve the Movement expenditure already recorded in the current turn.

### Command and actor identity

`MoveCombatantCommand` expresses voluntary Movement by the Command actor. The payload carries only `combat_id` and destination coordinates.

There is intentionally no separate `creature_id`: voluntary Movement in this slice cannot move another combatant. Future forced movement or teleportation must define their own contracts rather than weakening this identity rule.

Character actors are rejected before Monster Definition lookup because this task has no authoritative Character walking-speed source. This is a supported-slice limitation, not corrupt Character State.

### Monster speed and eligibility

Application resolves the actor's `CreatureState`, requires the current active Combat and active actor, excludes a matching `CharacterState`, and then resolves the actor's Definition as `MonsterDefinition` through the existing `DefinitionSource` boundary.

`walking_speed` is authoritative immutable Definition data. It is never copied into Combat State and is never caller supplied.

`walking_speed is None` means this Monster lacks a supported Movement speed source for this phased contract and therefore cannot use the Command. `walking_speed == 0` remains a valid Definition value; it simply leaves no capacity for a positive voluntary Movement segment.

A Monster at `current_hp == 0` cannot voluntarily move in this slice. This is a concrete Movement eligibility rule only; it does not define Monster death, unconsciousness, stabilization, removal from Combat, or broader lifecycle behavior.

### Position prerequisite and geometry

The actor must already have a `CombatPosition`. `MoveCombatantCommand` never performs initial placement.

The requested destination uses the existing integer feet coordinate system. One Command represents one straight endpoint-to-endpoint segment. The project-defined first-consumer cost is deterministic whole-foot ceiling Euclidean distance:

```text
dx = to_x - from_x
dy = to_y - from_y
squared = dx*dx + dy*dy
root = isqrt(squared)

distance =
    root      if root*root == squared
    root + 1  otherwise
```

No floating-point `sqrt` or generic geometry library/service is used.

This policy is local to the published first Movement consumer. It does not retroactively redefine §3.30's Dagger reach approximation as a universal geometry framework and does not establish grid/hex/path rules.

Destination equal to source is an invalid Movement Command. Choosing not to move is represented by not issuing the Command.

Multiple combatants may still occupy identical coordinates. The Movement slice does not add collision or occupancy semantics.

### Split movement and budget

A turn may contain zero, one, or multiple `MoveCombatantCommand` instances.

Pure Domain resolution derives:

```text
distance
new_movement_spent = combat.movement_spent + distance
```

Application compares that resolved cumulative expenditure with authoritative Monster walking speed before allocating Event metadata:

```text
new_movement_spent <= walking_speed
```

is required for success.

The implementation must not create a separate rejection merely because existing `combat.movement_spent` already exceeds the currently read walking speed. Any positive candidate segment naturally fails the cumulative budget check when the new total is above capacity.

Movement is independent of the ordinary Action:

```text
Move -> Attack -> Move
Attack -> Move
Move -> Move
```

are all structurally permitted when every Command independently passes its own eligibility and remaining Movement budget. Movement never creates `TurnActionSpent` and `action_spent=True` does not by itself reject Movement.

### Result and Event contract

`MoveCombatantResult` contains the resolved source/destination coordinates, exact segment distance, and new cumulative `movement_spent`.

`CombatantMoved` V1 contains only the occurred Movement segment:

```text
combatId
fromX
fromY
toX
toY
distance
```

The cumulative `movement_spent` is not duplicated into the Event payload because the applier can derive it deterministically from the previous authoritative Combat State plus Event distance.

The Event is directly caused by the Command (`causedBy = null`). It does not claim that Reaction/Opportunity Attack adjudication does not exist in D&D; that adjacent event ordering remains outside this slice.

### Event application and atomicity

`apply_combatant_moved_v1` is a concrete Combat State applier. It validates the Event against the exact pre-event Combat State, replaces the actor's position at the same tuple index, and increments `movement_spent` by the audited Event distance.

The applier does not access Definitions. Walking-speed legality belongs to Command resolution/Application before Event creation. A stale source position, wrong actor, wrong combat, wrong distance, malformed payload, or missing actor position is a propagating `TypeError`/`ValueError` integrity failure, not a gameplay `EngineError`.

One successful Command changes position and expenditure in one replacement `CombatState`, then one replacement `StateSnapshot`, then exactly one `StateStore.save()` call. There is no intermediate authoritative State containing only one half of the transition.

### Application validation and side effects

Validation order is binding and must match the Scope list exactly.

Rejected gameplay/eligibility paths return the specified `ResolutionResult` error before Event metadata, Event creation, State replacement, or persistence.

`DefinitionNotFoundError` / `DefinitionTypeMismatchError` keep their existing Application mappings. No new `ErrorCode` is introduced.

`MoveCombatantHandler` receives no `DiceEngine`. Runtime Movement in this slice is deterministic.

### Reactions and Opportunity Attacks boundary

TSK-0040 emits only `CombatantMoved` for successful voluntary Movement. It does not process a Reaction budget, detect hostile reach departure, pause a segment, emit an Opportunity Attack, or determine future causality/ordering between Movement and Reaction Events.

This absence is a phased implementation boundary only. It must not be documented as a rule that Movement never provokes Opportunity Attacks.

TSK-0023 remains separate draft future work and is not a dependency of this task.

### Documentation synchronization

DEC-0054 is historical rationale and must already be published before autonomous execution; TSK-0040 does not rewrite or append another decision merely to report implementation completion.

After production behavior lands:

- Architecture §3.38 changes from contract-defined/implementation-pending wording to implemented status;

## Known constraints / edge cases

- The first runtime voluntary-Movement consumer is Monster-only because the repository has no authoritative Character walking-speed source.
- `MoveCombatantCommand` is intentionally named for the mechanic rather than for the current actor category; the published implementation contract still rejects Character actors in this slice.
- `movement_spent` means distance already voluntarily moved by the current active combatant during the current turn. It is not remaining Movement and is not capped structurally by `CombatState`.
- `MonsterDefinition.walking_speed` remains immutable base walking speed, not a mutable/current/effective movement allowance.
- `movement_spent` and `walking_speed` use feet.
- Split movement is represented by multiple Commands and persisted cumulative expenditure, not by a path array inside one Command.
- One Command is one straight endpoint-to-endpoint segment.
- The whole-foot ceiling Euclidean segment rule is a project-defined first-consumer policy. It does not make §3.30 reach geometry, grid rules, or arbitrary future movement modes universal.
- Integer coordinates mean sub-foot destinations are not representable.
- Negative coordinates remain legal.
- No-op destination is rejected; choosing not to move requires no Command.
- Identical coordinates for different combatants remain legal because occupancy/footprint/collision is not modeled.
- No path legality is checked between source and destination. Obstacles, walls, difficult terrain, and traversal are outside this contract.
- The applier trusts only Event plus pre-event Combat State and therefore cannot independently enforce walking-speed capacity; that legality must be established before Event creation.
- V5–V9 `movement_spent=0` is a compatibility default. This is safe for the implemented history because no authoritative voluntary-Movement expenditure existed in those schemas.
- V10 must explicitly inherit V9 Character lifecycle decoding; changing `SCHEMA_VERSION` without updating explicit version branches is not sufficient.
- `action_spent` and `movement_spent` are independent current-turn facts. This task intentionally does not combine them into a generic resource abstraction.
- A zero-HP Monster is rejected for this voluntary Movement Command, but the task does not decide Monster death/stabilization/removal semantics.
- `walking_speed is None` and `walking_speed == 0` remain distinct: the former means no supported authoritative source; the latter is an authoritative zero walking speed.
- Existing `movement_spent` greater than a newly read walking speed is not itself declared corrupt State; a positive new segment simply cannot satisfy the cumulative budget check.
- No Reaction/OA Event is emitted. That is an implementation boundary, not a statement that leaving hostile reach never provokes an Opportunity Attack.
- TSK-0023 remains separate draft future work and is not a dependency.
- Character Movement requires a separately published Character speed contract before implementation.
- Dash requires a separately published capacity rule; this task does not encode it through hidden doubling or a generic modifier.
- No Event history/EventStore exists; the current project persistence boundary remains snapshot persistence plus returned Events.
- No new production dependency is required.
- This task is independently reviewable and mergeable after §3.38 / DEC-0054 / §12.13 V10 are authoritative on `main`.
