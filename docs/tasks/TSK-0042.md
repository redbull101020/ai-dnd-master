## Goal

Fix the observed `AUTONOMOUS_PR` prospective Task Closure failure mode in which a deterministic, candidate-local closure defect terminates the invocation as `BLOCKED` even though the defect is fully known, remains inside the fixed closure-only scope, and can be safely corrected by the already-existing `TASK_CLOSURE_REPAIR` path.

After this task, a prospective closure candidate that is mechanically invalid but safely attributable to the candidate itself must remain inside the same in-memory closure-gate episode:

```text
Task Closure preparation
→ build exact uncommitted closure candidate
→ deterministic closure validation
→ candidate-local validation failure
→ reject candidate identity
→ TASK_CLOSURE_REPAIR
→ deterministic closure validation
→ independent Closure Review
→ unpublished closure commit
→ fresh origin/main revalidation
→ Mode C
→ exact publication
→ required CI
→ READY_FOR_HUMAN_MERGE
→ STOP
```

The repair path must not weaken any closure validator, reviewer gate, Mode C audit, publication invariant, CI gate, Git/GitHub boundary, or human-only merge boundary. A failure may enter automatic closure repair only when the orchestrator can positively establish that the authoritative closure baseline remains valid and that the defect belongs to the newly produced closure candidate. Repository-integrity failures, ambiguous side effects, disallowed implementation-file mutations, agent failures, stale authoritative inputs, and cases whose closure-only nature cannot be proven remain terminal `BLOCKED`.

The production incident motivating this task occurred during TSK-0040 after the implementation checkpoints, Full Verification, pre-closure cumulative review, and draft PR creation had succeeded. The closure implementer produced terminal evidence `draft PR #129`, while the deterministic terminal-only validator required exact evidence `PR #129`. The validator diagnosed the mismatch precisely, but `_prepare_v2_unpublished_closure()` converted that repairable candidate defect directly into terminal `_Blocked`, so the invocation never reached Closure Review, Mode C, required CI, or `READY_FOR_HUMAN_MERGE`. The closure was subsequently recovered manually. TSK-0042 fixes that orchestration classification defect, not the terminal-row contract that correctly rejected the candidate.

This task changes the operational repair semantics of `AUTONOMOUS_PR` itself and must be delivered in `MANUAL` mode. Do not execute TSK-0042 through `AUTONOMOUS_PR`.

TSK-0042 changes the operational repair behavior of `AUTONOMOUS_PR` itself. Deliver it through the repository's `MANUAL` development workflow.

Do not invoke `AUTONOMOUS_PR TSK-0042` and do not use literal `NEXT` to attempt to deliver this task autonomously. This avoids using the defective prospective-closure path to modify its own repair semantics and keeps self-modification outside the ordinary autonomous run.

After that merge, authoritative `main` must record TSK-0042 as terminal `Done`, making it ineligible for future explicit execution and `NEXT`. Retaining `docs/tasks/TSK-0042.md` after closure is permitted because the terminal registry excludes its task ID from selection.

### Responsibility and transition boundary

The post-change closure boundary is:

```text
accepted implementation + draft PR
    ↓
authoritative closure baseline prevalidation
    ↓
closure implementer
    ↓
uncommitted candidate diff
    ↓
allowed-path guard
    ├─ disallowed path / unsafe repository condition
    │      → BLOCKED
    │
    └─ candidate remains closure-only
           ↓
       candidate identity / no-progress guard
           ↓
       deterministic closure-candidate validation
           ├─ candidate-local failure
           │      → record rejected GateAttempt
           │      → hand exact deterministic failure to TASK_CLOSURE_REPAIR
           │      → repeat inside same gate/context
           │
           └─ pass
                  → independent Closure Review
                  → existing downstream flow
```

The orchestrator, not an LLM, owns the classification between repair and terminal stop.

### Authoritative baseline prevalidation

Before the first candidate in one `_prepare_v2_unpublished_closure()` episode can classify a `TaskTrackerError` as repairable, the orchestrator must positively establish from the immutable `task_md_baseline` that:

1. the baseline terminal registry parses successfully; and
2. the selected task is not already terminal in that baseline.

Failure of either condition is terminal `BLOCKED`.

The same baseline string is then used for every candidate in that closure-gate episode. Because those authoritative baseline facts have already been established, a later `TaskTrackerError` emitted by `validate_terminal_only_closure()` against that unchanged baseline is attributable to the current candidate and may enter closure repair.

Do not distinguish baseline versus candidate errors by matching exception-message substrings.

### Candidate path classification

For each closure implementer result:

1. verify the branch HEAD remains unchanged across the implementer invocation;
2. fail terminally on implementer timeout/non-zero result;
3. build the exact uncommitted closure patch and touched-path set;
4. fail terminally if any touched path is outside `_CLOSURE_ALLOWED_FILES`;
5. compute the closure candidate identity;
6. fail terminally on identity already present in `rejected_candidate_identities`;
7. deterministically collect candidate-local closure-validation failures;
8. if failures exist, record one rejected pre-review attempt and continue as `TASK_CLOSURE_REPAIR`;
9. only a candidate with no deterministic closure-validation failure reaches the designated Closure Review.

Required-file absence belongs to step 7, not step 4. Therefore a candidate that omits `docs/TASK.md` or `docs/DEVELOPMENT_LOG.md` can be repaired, while a candidate that edits `src/`, `tests/`, `tools/`, arbitrary documentation, or another non-closure file remains terminal.

When `strict_closure_only_repair=True`, preserve or strengthen the same disallowed-path fail-closed boundary; the flag must never make an implementation mutation repairable as closure-only.

### Deterministic candidate-validation handoff

Extend `_build_v2_closure_prompt()` with a dedicated value carrying only the immediately preceding deterministic closure-candidate validation failure.

The prompt should have an explicit block equivalent to:

```text
CURRENT_CLOSURE_VALIDATION_FAILURE:
(none)
```

or, after rejection:

```text
CURRENT_CLOSURE_VALIDATION_FAILURE:
<stable deterministic diagnostic for the rejected closure candidate>
```

The exact helper/parameter name is a local implementation choice, but the semantic handoff is binding.

For a candidate with multiple simultaneously discoverable closure-local defects, report them in stable deterministic order where all can be obtained without crossing a repository-integrity failure. At minimum, missing required closure files must be reportable together with a terminal-only row defect when `docs/TASK.md` is present and exact-readable.

This handoff is not a `RepairPacket`. It coexists with and does not overwrite:

- upstream late-gate repair context;
- the latest valid Closure Review repair packet;
- the authoritative closure evidence JSON;
- the accepted implementation patch used for factual closure prose.

### Gate history and no-progress

Add `CandidateRejectionBasis.CLOSURE_VALIDATION_FAILURE`.

For a deterministic pre-review closure rejection, store a `GateAttempt` that identifies the rejected candidate but has no verification evidence and no reviewer iteration/verdict.

The rejected identity participates in the existing same-gate/fixed-spec/accepted-base no-progress set. Therefore:

```text
invalid A → repair → invalid A
```

is terminal no progress, while:

```text
invalid A → invalid B → valid C
```

may continue.

There is no numeric closure-validation repair limit.

A deterministic validation rejection must not be written into `previous_reviewed_candidate_identity` or `previous_reviewed_candidate_state`. Those fields retain their literal meaning: the preceding candidate actually seen by the designated reviewer.

If a repeated identity is detected, record or preserve the existing repeated-identity diagnostic convention consistently with other v2 repair loops before terminal `BLOCKED`; do not invoke another reviewer merely to rediscover no progress.

### Reviewer, metrics, and routing preservation

`ReviewGateMetrics.review_iterations` counts designated reviewer iterations only. A deterministic closure-validation rejection is therefore invisible to that count.

`ReviewGateMetrics.verification_rejection_count` remains limited to `CandidateRejectionBasis.VERIFICATION_FAILURE`. Do not include `CLOSURE_VALIDATION_FAILURE`.

No new public metric is required.

Routing remains:

```text
initial Task Closure preparation → ROUTINE
Task Closure repair              → DELIBERATE
Task Closure review              → DELIBERATE
Mode C                           → CRITICAL
```

A closure-validation rejection makes the following implementer invocation `TASK_CLOSURE_REPAIR` because the gate already contains a rejected attempt; it does not create a verification-rejection escalation reason.

A candidate that later passes deterministic validation always proceeds to the existing fresh Closure Review. The reviewer receives the exact current candidate, not the rejected predecessor as `CURRENT_PATCH`, and no invalid pre-review candidate is falsely described as previously reviewed.

### Fail-closed boundary

The following remain terminal and do not enter the new repair path:

- authoritative baseline cannot be parsed or selected task is already terminal;
- exact worktree candidate cannot be safely read/staged and raises `RepositoryError`;
- candidate touches any disallowed file;
- branch/HEAD invariants move unexpectedly;
- implementer/reviewer process failure;
- required capability/tool failure;
- ambiguous Git/GitHub side effect;
- required scope expansion or new architectural decision;
- safe closure-only classification cannot be established.

This task must not use exception-message matching to turn these conditions into repair.

### Documentation synchronization

Update `docs/AUTONOMOUS_PR_HARNESS.md` to make code and contract agree:

- §28 rejected-candidate semantics include deterministic prospective-closure candidate validation failure;
- the failure has no reviewer verdict and is eligible for repair only when candidate-local closure scope is positively established;
- exact identity repetition after such a rejection is no progress;
- closure repair remains unbounded by count;
- routing escalation language remains verification-specific;
- unsafe/ambiguous/baseline/repository failures remain fail-closed.

Do not rewrite unrelated historical sections or gameplay documentation.
