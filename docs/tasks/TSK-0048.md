## Goal

Implement the smallest independently mergeable *dormant* Windows-only foundation required by the canonical verification-containment contract: checked Win32 Job-object ABI bindings, creation of one fresh unnamed `J_supervision` and one fresh unnamed `J_command`, exact `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` configuration and readback, single-owner handle accounting, and fail-closed pre-assignment release. All newly added tests must exercise an injected fake native API or pure ctypes declarations without calling any real Windows Job/containment operation. Existing project tests that run ordinary subprocesses remain in scope of the unchanged full pytest suite. Do not create, assign, resume, terminate, or inspect an actual Job or its processes as part of this task’s checks.

This slice must **not** be wired into `_run_one_verification_command()` or any existing executable path. In particular, it does not implement `STARTUPINFOEX`, `CreateProcessW`, `PROC_THREAD_ATTRIBUTE_JOB_LIST`, worker bootstrap, pipes, IPC, quiescence, cancellation, deadlines, or any successful `VerificationCommandResult`. Those independently reviewed continuations follow later MANUAL tasks and separately approved Windows-native validation. Publishing or completing this task does not assert Windows runtime containment.

It must pass the repository's exact `parse_task_document` with an approved-metadata validation copy before being called execution-ready; that local validation is not itself approval. ## Scope

1. Add a narrow private native-API adapter with typed 64-bit ctypes structures, constants and checked functions **only** for this slice: `CreateJobObjectW`, `SetInformationJobObject`, `QueryInformationJobObject` and `CloseHandle`, plus checked failure-code capture through `ctypes.get_last_error()` on the real Windows backend. Bind `JOBOBJECT_BASIC_LIMIT_INFORMATION`, `IO_COUNTERS`, and `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`; use the correct information class (`JobObjectExtendedLimitInformation`) and full native input/output buffer sizes, checking a supplied query return length when the API provides it. Define Win32 `BOOL` and `DWORD` as 32-bit values, `LARGE_INTEGER` as signed 64-bit, `SIZE_T`/`ULONG_PTR` and `HANDLE` as pointer-sized, and `WCHAR` (where needed) as 16-bit; never assume host `ctypes.wintypes` declarations have Windows sizes on Linux/macOS. Verify sizes, field offsets, alignment, argument/result widths and signedness. The production loader uses `ctypes.WinDLL(..., use_last_error=True)` on supported Windows only, capturing `ctypes.get_last_error()` immediately after a failed native call; do not mix unsynchronized direct `GetLastError` with the ctypes last-error copy. All declarations/layout checks and injected-fake tests work on non-Windows without referring to unavailable `ctypes.WinDLL`/`get_last_error` attributes. No dependency is added.
2. Implement a small injected-API H-side ownership object for exactly two new, *unnamed* Job Objects, labeled `J_supervision` and `J_command`. Allocate sequentially, configure each with only `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE = 0x00002000` (zero-initialize the complete extended structure except `BasicLimitInformation.LimitFlags`), and independently query/read back the exact flag set, including absence of both breakaway flags and any unapproved other limits. Do not open or modify existing/outer Jobs, create job names, assign processes, elevate, or enable breakaway. These two objects are **not yet nested** merely because they have been created; nested membership requires a separately approved atomic process-creation slice.
3. Define explicit per-handle ownership and a pre-assignment-only checked release path, with reverse-order retirement (`J_command`, then `J_supervision`) and one checked close per owned handle. A successfully created valid handle becomes owned immediately, including if an unexpected duplicate numeric value is returned: detect a duplicate and fail without double-closing the aliased value. A failed stage closes only handles genuinely acquired. Attempt reverse-order cleanup of every remaining owned handle even when an earlier close fails, preserving each failure without any second close attempt. Failed `CloseHandle` is terminal cleanup uncertainty and cannot be reclassified as success, retried blindly, forgotten, or treated as proof the underlying Job/process state is quiet. The object must not offer an externally reachable unguarded general-purpose release method for Jobs with assigned processes.
4. Fail closed on unsupported platform or unvalidated ABI, unavailable Win32 functions, zero/null/`INVALID_HANDLE_VALUE`/otherwise invalid returned handles, unexpected status, failed or incomplete limit configuration/readback, mismatched information-class/buffer dimensions or returned query length, duplicate handle value/ownership, repeated release, and cleanup failure after an earlier failure. Capture OS error numbers immediately; present only bounded stage/category/numeric diagnostic fields consistent with Harness §37.5/§37.9, never raw native transcripts, arbitrary exception string, raw handle values, environment, paths or argv. Preserve the primary cause and separately report failure to retire already owned handles; do not invent a completed result.
5. Add deterministic fake-native fault-injection tests on every supported CI platform: successful two-Job allocation/configuration/readback/checked release; exact flags and ABI sizes; every failed API stage and cleanup partial order; invalid handle ownership and double-close prevention; correct failure classification; injected platform/ABI rejection (do not globally monkeypatch `os.name`, which can destabilize unrelated Python/pytest code); non-Windows safe import; proof no new real Win32 Job/containment calls are made by these tests or added to the production orchestrator. The mock must record call arguments and ownership, not merely return successful booleans.
6. Document any factual delivered internal boundary concisely in `docs/DEVELOPMENT_LOG.md` as part of reviewed terminal closure, following `AGENTS.md` and `docs/TASK.md`. Do not revise C0 or historical DEC-0055/TSK-0046, change gameplay contracts, or declare a Task `Done` before actual reviewed closure. ## Approved implementation approach

**Authority and platform.** This is a MANUAL-only future implementation slice because it defines native lifetime/ownership primitives that the autonomous harness itself will later depend on. It must not be invoked through `AUTONOMOUS_PR NEXT` or `TSK-0048`. A separate explicit implementation instruction and independently reviewed delivery are required. On non-Windows the new modules must be safely importable by tests and expose no usable native API; requesting a real native adapter must fail closed. On Windows, support is limited to the validated native 64-bit Python/Win32 ABI and eligible OS; a simple Windows-version string is not sufficient proof that later job-list creation works. No fallback to uncontained subprocesses exists.

**ABI boundary.** `tools/autonomous_pr/_windows_verification_native.py` owns ctypes Win32 declarations; no eager DLL acquisition as a module-import side effect. Select `JobObjectExtendedLimitInformation` (`9`) and size the whole `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`, not merely its `BasicLimitInformation`. On a valid 64-bit ABI its layout must match the documented C layout (including `sizeof(JOBOBJECT_BASIC_LIMIT_INFORMATION) == 64`, `sizeof(IO_COUNTERS) == 48`, `sizeof(JOBOBJECT_EXTENDED_LIMIT_INFORMATION) == 144`). Verify exact pointer widths, signedness, all field offsets, alignment, `restype`/`argtypes` and Win32 WCHAR (16-bit), BOOL/DWORD (32-bit), LARGE_INTEGER (64-bit) and SIZE_T/HANDLE (pointer-width). The portable structure definitions must not silently use host-native `ctypes.wintypes` sizes; `ctypes.WinDLL` and `ctypes.get_last_error` may not exist on non-Windows. Production API acquisition is lazy and uses `use_last_error=True`; read its error immediately after failure before any other Win32 call. If any ABI/API prerequisite is uncertain, no Job creation is attempted.

**Job configuration.** `tools/autonomous_pr/_windows_verification_jobs.py` owns the H-only creation transaction. It accepts a narrow native API protocol so tests can inject an entirely fake implementation. Create `J_supervision` and `J_command` through `CreateJobObjectW(NULL, NULL)`; do not create named Jobs or use an existing Job as a fallback. Configure each using a fully zero-initialized extended structure and `SetInformationJobObject(JobObjectExtendedLimitInformation, ...)` with only `BasicLimitInformation.LimitFlags == JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Do not set additional limits or flags. Query `JobObjectExtendedLimitInformation` for each newly owned Job using the full correctly sized output buffer; validate the BOOL result, available returned length and exact effective local `LimitFlags == 0x00002000` (including no breakaway/unapproved limit bits). Mismatch or incomplete query is terminal. Creation order is supervision then command. Success returns one H-owned pair in pre-assignment state, not a usable verification executor and not proof of nesting.

**Ownership lifecycle.** Every non-null Job handle has exactly one H-side owner and explicit state: never acquired, owned/pre-assignment, close attempted, confirmed closed, or uncertain close. Do not silently reconstruct ownership from numeric handles or use finalizers, garbage collection or context-manager exit to claim verified success. A pre-assignment close attempts command first and supervision second, each at most once, including when the first close fails. On any failure, release every already acquired owned handle through checked one-shot closes, retaining the primary failure and bounded secondary cleanup-uncertain diagnostics. An uncertain close consumes that one attempt and leaves an explicit unresolved-owned-resource record; it is never presented as successfully closed or silently retried. No direct or indirect TerminateJobObject call or automatic retry. A future process-creating component must introduce its own authoritative nonempty-Job lifecycle and quiescence before reusing any retirement mechanism.

**Error contract.** Internal native failures are typed `WindowsVerificationError(OSError)` (or an equivalently narrow internal error meeting C0 §37.9), carrying bounded allowlisted `stage` (`preflight`, `jobs`, `close`, `cleanup` as applicable), `category` (`unsupported_platform`, `os_api`, `ownership`, `invalid_handle`, `resource`, `uncertain_state` as applicable), numeric/null `winerror` and `errno`, `timed_out=False`, and truthful `cleanup_confirmed`. Never project API user text, raw Win32 handles or exception `str` into diagnostics. When cleanup fails after the primary error, it does not replace the first causal exception. This dormant module does not create or map a public `RepositoryError`; that mapping belongs at a later orchestrator integration boundary.

**No-runtime proof.** None of the new modules may be imported by existing production dispatch paths. No `CreateProcessW`, resume, process assignment, W or payload execution is delivered. Do not let the preparatory API export raw owned handles to a production caller or provide a generic `close()` for future assigned Jobs; ownership transfer into a later atomic-launch lifecycle requires its own reviewed contract. Tests must construct the fake API directly and assert all expected native-like calls in order. ABI structure tests may inspect ctypes definitions without loading a DLL or creating a Job. Native smoke/probe approval is separate and cannot be inferred from passing mocks, code review, or the future approval of this Task.

**Scope/closure discipline.** Implementation files are restricted to the two private modules and one fake-only test module above, plus one factual `docs/DEVELOPMENT_LOG.md` closure entry and the authorized selected Task/terminal documentation when actually permitted by MANUAL governance. No `docs/TASK.md` terminal `Done` claim before reviewed evidence; no automatic repo/PR writes. The implementation must be independently reviewable and mergeable even though a later slice will add process launch.

## Acceptance criteria

1. **Fake success (unit/fault injection, no native execution).** One H transaction creates exactly two new unnamed Jobs in order, sets and re-queries KILL_ON_JOB_CLOSE on both, checks breakaway absence, and returns only an owned pre-assignment pair. Exactly two checked closes in reverse order are recorded; no duplicate close or extra handle appears. Expected failure gate: any unexpected call/flag/ref state fails test and cannot return a success object. Safety deadline/cleanup: no real OS resources; fake operations are finite.
2. **ABI correctness (pure unit/static).** On supported 64-bit declarations, structure sizes/field offsets, constants and function signatures match C0/Win32 on Windows and on Linux/macOS hosts that execute the same pure declarations; BOOL/DWORD/WCHAR must not inherit host-native ABI widths. Fail-closed gate: unsupported pointer width, missing API, invalid or ambiguous type/flag/length causes terminal internal error before native creation. No native smoke is claimed.
3. **Partial acquisition (fake fault injection).** Fail first CreateJobObjectW; fail second CreateJobObjectW; fail SetInformation/QueryInformation on either Job; corrupt readback; null/invalid returned handle. Each path closes only actually owned handles once, in reverse order, and returns no usable owned pair. Cleanup errors preserve primary cause and add truthful uncertainty; no silent success.
4. **Checked release (fake fault injection).** Failed CloseHandle after either or both Job acquisitions is terminal cleanup uncertainty; remaining owned handles are still each attempted once in reverse order. A second close/release cannot invoke the native API again; unknown/foreign handle is never closed. Explicit pre-assignment release is the only permissible successful release state; future assigned-Job cleanup remains unimplemented and cannot be inferred.
5. **Diagnostic confinement (pure/fake).** Every error contains bounded allowlisted stage/category and numeric/null WinError/errno only, with no raw handle, argv, cwd, environment, OS error text or transcript. A failed native API result captures its error before subsequent API calls. No fabricated verification result is constructed.
6. **Non-Windows and existing-runtime parity (cross-platform).** Importing new private helpers on non-Windows has no `WinDLL`/kernel API side effect; native adapter acquisition fails closed. All existing non-Windows `subprocess.run` tests remain unchanged; `orchestrator.py`, `run_agent()`, Codex/MXC, Git/GitHub, Task dispatch and gameplay have no changed call paths or results.
7. **No unsafe validation (static/unit).** Tests are discovered in normal pytest yet use *only* fake API instances and ctypes layout inspection. No native CreateJobObject, job query, process creation, Job assignment, termination, probe, W startup or outer-job mutation is attempted or authorized. No default-discoverable native test suite is added.
8. **C0 traceability (documentation/static).** This slice provides only prerequisites for umbrella cases 5 (pre-assignment Job creation/configuration/failure containment), 12 (checked resource ownership), 18 (bounded diagnostics), and 19 (verification-only call-site confinement). **No one of the 19 cases is fully closed.** Cases 1–4, the rest of case 5, cases 6–11 and 13–17, the remaining obligations of 12/18/19, and all required native evidence remain assigned to later independently reviewed slices; report them as deferred rather than passing based on these mocks.
9. **Delivery (cross-platform/static).** Focused tests, full `pytest`, configured mypy, `git diff --check`, exact authorized changed-file allowlist review and independently verified cumulative diff pass; factual reviewed Task/Development Log closure is recorded only when actually delivered. If the exact requested module paths conflict with current files, or a required native API cannot be represented safely without widening the scope, stop for refinement instead of silently changing the architecture.

## Known constraints / edge cases

First actual native validation requires a separately reviewed exact test command, environment, independent safety owner, bounded deadline, sentinel and cleanup plan (§37.11). - KILL_ON_JOB_CLOSE initiates termination of Job membership only when the last relevant handle is closed. Here no process may ever be assigned; this initial ownership API must not silently become the live assigned-Job cleanup method. Never treat CloseHandle success as descendant termination proof.
- If a Handle close fails, report uncertainty. An attempted close may have had ambiguous side effects; no blind retry or double-close is permitted. Preserve primary and cleanup failure facts without reporting arbitrary OS text or accidentally closing a foreign/reused handle.
