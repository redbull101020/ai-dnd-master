## Goal

Добавить в operational `AUTONOMOUS_PR` v2 детерминированный per-invocation routing вычислительного профиля implementer/reviewer между `ROUTINE`, `DELIBERATE` и `CRITICAL`, чтобы обычная хорошо определённая работа выполнялась на базовом compute-профиле, а дополнительный model/reasoning budget включался только при заранее определённых признаках сложности или non-convergence.

Routing должен автоматически возвращаться к baseline нового этапа после завершения сложного gate: никакой повышенный profile, model или effort не наследуется следующим checkpoint, closure phase, новому run или следующему task только потому, что предыдущий этап потребовал эскалации. При этом gates, которые сами по себе требуют более сильного semantic review — pre-closure cumulative review и Mode C — получают высокий baseline независимо от предыдущего downgrade.

Конкретные provider/model/reasoning-effort значения остаются provider-specific runtime configuration на существующей external-process invocation boundary. Канонический harness выбирает только provider-neutral compute profile и не ранжирует модели, не интерпретирует их имена и не предоставляет LLM право выбирать собственный compute budget.

## Scope

1. Ввести закрытый provider-neutral compute-profile vocabulary `ROUTINE`, `DELIBERATE`, `CRITICAL` и типизированные значения для routing decision/diagnostics. Compute profile является уровнем вычислительного бюджета, а не именем модели или provider.
2. Ввести закрытый `AgentWorkKind`, достаточный для всех существующих LLM invocation paths: initial checkpoint implementation, implementation repair, checkpoint/replay review, implementation-repair review, pre-closure cumulative review, initial Task Closure preparation, Task Closure repair, Task Closure review и Mode C review. Post-publication Mode C replay использует тот же Mode C work kind с отдельным `gate_id`.
3. Добавить отдельный pure `tools/autonomous_pr/routing.py` (или эквивалентный узкий модуль с той же ответственностью), который по role, work kind, текущему `GateHistory` и явному direct seed/upstream repair/verification context детерминированно возвращает routing decision. Модуль не выполняет subprocess, Git/GitHub, filesystem I/O, prompt parsing или provider API calls.
4. Зафиксировать baseline policy:

   | Work kind | Role | Baseline profile |
   | --- | --- | --- |
   | initial checkpoint implementation | implementer | `ROUTINE` |
   | implementation repair | implementer | `DELIBERATE` |
   | initial Task Closure preparation | implementer | `ROUTINE` |
   | Task Closure repair | implementer | `DELIBERATE` |
   | first checkpoint/replay review | reviewer | `DELIBERATE` |
   | first implementation-repair review without upstream repair packet | reviewer | `DELIBERATE` |
   | pre-closure cumulative implementation review | reviewer | `CRITICAL` |
   | first Task Closure review | reviewer | `DELIBERATE` |
   | Mode C review, including post-publication replay | reviewer | `CRITICAL` |

5. Implementer escalation поверх baseline использует только структурированные факты текущего causal repair episode. `IMPLEMENTATION_REPAIR` становится `CRITICAL`, если выполняется хотя бы одно условие: cumulative verification-rejection count текущего episode, включая direct seeded upstream verification failure, достиг двух или более; либо хотя бы один exact `binding_basis` в RepairPacket, который управляет следующим repair invocation, уже встречался в любом более раннем RepairPacket того же episode, включая direct seed/upstream packet. Первый repair без этих признаков остаётся `DELIBERATE`.
6. Новый binding basis, впервые появившийся в более позднем `CHANGES_REQUESTED`, сам по себе не повышает implementer выше `DELIBERATE`: при отсутствии repeated basis и второго verification rejection это считается прежде всего дополнительной review information, а не доказательством того, что implementer не смог исправить уже известное требование.
7. Reviewer escalation поверх baseline становится `CRITICAL`, если baseline уже `CRITICAL`, если предстоящий review является review iteration 2+ одного `GateHistory`, либо если кандидат был создан в прямой ответ на seed/upstream RepairPacket из предыдущего review gate. Это правило должно покрывать late implementation repair и новый closure gate, созданный из upstream repair packet, даже если их локальный `GateHistory.review_iteration` начинается с нуля.
8. Causal routing episode имеет явную узкую границу. Direct seed/upstream `RepairPacket` и seeded verification failure переходят только в непосредственно созданный repair gate, которому они причинно принадлежат. Локальные `CHANGES_REQUESTED`/verification failures этого gate продолжают тот же episode. После принятого `APPROVED`/accepted repair эта escalation lineage заканчивается; replay, следующий checkpoint, следующий closure/audit gate и следующий run начинают собственный routing context, кроме нового прямого repair handoff, явно создаваемого существующим orchestration flow.
9. Routing не хранит mutable `current_profile` и не выполняет imperative `upgrade()`/`downgrade()`. Перед каждым agent invocation selected profile вычисляется заново из baseline и текущих routing signals. Именно recomputation обеспечивает обязательный downgrade после преодоления сложного этапа.
10. Runtime profile mapping остаётся на существующей external-process boundary. Для каждой role сохраняется один configured executable; profile tier не может менять executable/provider. Existing role-common argv могут сохраняться, а CLI/config добавляет explicit profile-specific argv, детерминированно добавляемые к common argv для выбранного tier. Required mappings: implementer `ROUTINE`/`DELIBERATE`/`CRITICAL`; reviewer `DELIBERATE`/`CRITICAL`.
11. Required profile-specific mappings должны быть явно настроены до первого agent invocation и образовывать различимые final argv для разных required tiers одной role, чтобы adaptive routing не превращался в silent no-op. Harness проверяет только структурную полноту/различимость mapping и сохранность role/capability fields; он не пытается доказать semantic качество модели, фактический reasoning effort или provider entitlement.
12. Любой composed invocation сохраняет исходные `role`, `cwd`, timeout, environment и capability assertions соответствующей role. Reviewer profile variants по-прежнему обязаны соответствовать существующему operator assertion `fresh_context_capable=True`; никакой profile-specific argv не даёт implementer/reviewer Git/GitHub write authority и не ослабляет fingerprint/branch-head guards.
13. Если выбранный profile невозможно фактически запустить — external executable отсутствует, authentication/model/profile недоступны, process timeout/error или иная существующая invocation failure — run использует текущий fail-closed path. Запрещён automatic fallback на более слабый profile, другой model/provider или повторный invocation только ради обхода выбранного compute tier.
14. Интегрировать routing во все существующие agent invocation paths: ordinary checkpoint initial/repair, verification repair, replay review, late implementation repair/review, pre-closure cumulative review, initial/repair Task Closure implementation, Closure Review, Mode C и post-publication Mode C replay. Ни один production LLM invocation operational v2 не должен обходить router.
15. Добавить append-only in-memory routing diagnostics для фактически выбранных invocations. Минимальный `RoutingDecisionRecord` (или эквивалент) содержит monotonic per-run `sequence`, `role`, `work_kind`, `gate_id`, `baseline_profile`, `selected_profile` и deterministic closed-set escalation reasons. Он не содержит prompt, patch, stdout/stderr, full argv, environment, secrets, model hidden reasoning или provider credentials.
16. `RunResult` получает backward-compatible default-empty `routing_decisions`; CLI выводит каждую запись в стабильной machine-readable JSON line. Successful, `BLOCKED` и partially progressed runs сохраняют уже сделанные routing records; `NO_ELIGIBLE_TASK` и failures до первого agent routing decision имеют пустой tuple. Telemetry никогда не влияет на routing, verdict, retry, no-progress, phase transition или merge readiness.
17. Синхронизировать `docs/AUTONOMOUS_PR_HARNESS.md` новым operational routing contract без перенумерации существующих §§20–35 и `AGENTS.md` коротким provider-neutral summary там, где описываются deterministic orchestration/review mechanics. `docs/TASK.md` schema/selection rules не меняются. `CLAUDE.md` проверяется и меняется только если существующая deliberately duplicated guidance фактически станет неточной.
18. Добавить focused routing/config/orchestrator/CLI tests и выполнить полный tooling/repository regression. Новая production dependency не добавляется.

## Out of scope

- Hardcoded имена конкретных GPT/model families, provider-specific model ranking или утверждение, что один model tier объективно лучше другого во всех задачах.
- Automatic provider switching, разные executables внутри одной role, provider registry/factory, `BaseProvider`, provider SDK или multi-provider failover.
- LLM-классификатор сложности, self-selected model/effort, просьба implementer/reviewer повысить собственный compute, semantic анализ свободного текста `NonConvergenceDiagnosis` или prompt content для routing.
- Model ensemble, второй reviewer, reviewer quorum, majority voting или параллельные agent invocations.
- Price-aware/latency-aware routing, token budget optimization, live price lookup, usage billing integration, automatic cost minimization или статистическое/ML самообучение policy.
- Persisted routing state, `run.json`, resume после process loss, cross-run/cross-task memory, database, broker или dashboard.
- Новый numeric repair limit, изменение существующих no-progress/cycle rules, candidate identity, verdict tokens или second+ non-convergence diagnosis.
- Automatic retry/fallback после explicit `BLOCKED`, malformed reviewer output, missing capability, process failure или unavailable selected profile.
- Изменение A/B/C `review.patch` semantics, review applicability, Task Closure ordering, Mode C ordering, CI topology, invocation authority, commit/push/PR authority, human-only merge или branch policy.
- Изменение standalone Task schema, `NEXT` selection, terminal registry semantics, TSK-0023 или Roadmap gameplay ordering.
- Gameplay, `src/dnd_engine/**`, canonical D&D Architecture, State/Event/Command/Definition contracts или production dependencies.
- Проведение первого production `AUTONOMOUS_PR` pilot внутри TSK-0031; pilot остаётся отдельной approved S/M task после merge этой работы.
- Автоматическая настройка baseline/escalation policy по результатам pilot telemetry; TSK-0031 реализует фиксированную deterministic policy, а её эмпирическая настройка выполняется отдельно после накопления реальных данных.

## Approved implementation approach

**A. Typed provider-neutral routing contract**

Добавить provider-neutral typed vocabulary рядом с operational harness model values: `ComputeProfile` с exact values `ROUTINE`, `DELIBERATE`, `CRITICAL`; `AgentWorkKind` с закрытым набором work kinds из Scope; closed-set routing reasons; immutable routing decision/record values. Имена конкретных models, provider names и reasoning-effort strings не входят в эти canonical types.

Routing policy реализовать как чистую функцию/набор чистых функций в отдельном routing module. Orchestrator передаёт только уже известные ему structured facts; router не читает repository, task text, prompts или stdout и не вызывает LLM.

**B. Baseline plus local escalation, never inherited profile state**

Каждый invocation получает baseline из exact role/work-kind matrix в Scope. Затем pure policy повышает selected profile только на основании текущего causal repair episode. Профили упорядочены `ROUTINE < DELIBERATE < CRITICAL`; escalation saturates at `CRITICAL` и сама по себе никогда не завершает run.

Implementer repair signals вычисляются из history плюс explicit seed context. Для verification используется `seed_verification_rejection_count +` количество локальных `CandidateRejectionBasis.VERIFICATION_FAILURE` attempts. Для repair findings строится ordered causal packet lineage: direct seed/upstream packet, если он есть, затем structurally valid local `CHANGES_REQUESTED` packets текущего gate в фактическом порядке. Перед следующим implementer invocation packet, который управляет этим repair, сравнивается по exact `binding_basis` со всеми более ранними packets того же episode; наличие exact повторения означает `CRITICAL`. Equivalent-but-differently-spelled `repo:*` references не семантически нормализуются.

Первый repair packet или первый verification failure переводит работу только в repair work kind с baseline `DELIBERATE`. Если поздний `CHANGES_REQUESTED` содержит только basis, которых ранее в causal packet lineage не было, implementer остаётся `DELIBERATE`, если отдельное verification escalation condition не выполнено.

Reviewer получает `CRITICAL` при baseline `CRITICAL`, при local review iteration 2+ либо при первом review нового gate, который прямо проверяет candidate, созданный из seed/upstream RepairPacket. Seeded verification failure без upstream RepairPacket сам по себе не повышает первый repair review выше его `DELIBERATE` baseline.

`APPROVED`/accepted repair завершает local escalation lineage. Новый checkpoint не читает историю предыдущего checkpoint для routing. После `CRITICAL` checkpoint следующий ordinary checkpoint снова начинает с `ROUTINE`. После `CRITICAL` cumulative review initial Task Closure preparation снова начинает с `ROUTINE`. Mode C остаётся `CRITICAL`, потому что это его собственный baseline, а не наследование предыдущей сложности. После `STOP`/`BLOCKED` routing context живёт только до завершения текущего process/run и не является input следующего invocation.

**C. Minimal invocation-profile configuration boundary**

Сохранить один executable на role и существующие role-level capability assertions. Existing common argv остаются role-wide. CLI/config добавляет profile-specific repeated argv entries для implementer `ROUTINE`, `DELIBERATE`, `CRITICAL` и reviewer `DELIBERATE`, `CRITICAL`; selected invocation args строятся детерминированно как common args, затем argv выбранного profile. Exact CLI flag names должны быть однозначно задокументированы и покрыты CLI tests; их реализация не должна вводить отдельный JSON/YAML config parser или новый persisted config artifact.

До первого agent invocation configuration validation подтверждает наличие всех required profile mappings, непустые profile-specific argv и различимые composed argv каждого required tier внутри одной role. Все composed specs сохраняют executable/cwd/timeout/env/capability fields исходной role. Harness не интерпретирует provider-specific argv и не проверяет, какой именно model/effort они выбирают; ответственность за корректность external command/profile и operator capability assertions остаётся на конфигурации среды, как и до TSK-0031.

Если external executable отвергает выбранные args/model/profile, это обычная fail-closed invocation failure. Router не делает fallback и не меняет selected profile постфактум.

**D. Orchestrator integration and causal seed handoff**

Каждый вызов `run_implementer`/`run_structured_reviewer` в production orchestration должен предваряться одним routing decision и materialization соответствующего profile-specific `AgentInvocationSpec`. Central reviewer wrapper должен получать work kind/gate routing context явно, а не выводить его из human-readable context string или substring `gate_id`.

Ordinary checkpoint loop классифицирует первый implementer invocation как checkpoint implementation; любой последующий candidate-changing invocation после verification/review rejection — как implementation repair. Late repair helper получает explicit seed `RepairPacket | None` и seeded verification-rejection count из вызывающего gate. Replay history остаётся отдельным review context; если replay создаёт новый repair gate, только фактический packet/failure, который вызвал этот repair, передаётся как seed. Closure preparation аналогично различает initial preparation и repair, включая direct upstream packet из Mode C/closure flow. Никакая ранее accepted история не импортируется целиком в новый gate ради повышения profile.

Routing не меняет существующие workflow transitions. Verification по-прежнему выполняется orchestrator и не является LLM invocation. `APPROVED`, `CHANGES_REQUESTED`, `BLOCKED`, candidate rejection, no-progress, publication, CI и terminal outcomes остаются владельцами существующей state machine.

**E. Routing observability**

Orchestrator хранит append-only in-memory list routing records только для текущего `run()`. Record создаётся после deterministic profile selection и до subprocess invocation, поэтому failed/timeout agent process всё равно оставляет diagnostic fact о выбранном profile. Per-run `sequence` начинается заново для каждого `run()` и отражает фактический порядок agent invocations.

`RunResult.routing_decisions` имеет default empty tuple и выводится CLI как отдельные stable JSON lines с сортированными ключами. Telemetry содержит только provider-neutral decision facts; raw/common/profile argv, prompt, review patch, agent output, environment и credentials не выводятся. Routing records не читаются самим router и не образуют feedback loop.

**F. Documentation ownership**

`docs/AUTONOMOUS_PR_HARNESS.md` получает новый operational v2 section после существующего §35, фиксирующий provider-neutral profile vocabulary, baseline/escalation/de-escalation semantics, causal seed boundary, invocation-profile mapping и fail-closed no-fallback rule. Existing §§20–35 не перенумеровываются.

`AGENTS.md` получает только необходимый high-level invariant: compute profile выбирает orchestrator детерминированно, модель/effort не выбирает implementer/reviewer, повышение локально gate/repair episode и не переносится после accepted gate/terminal run, а profile routing не ослабляет review/authority/provider-neutrality. Низкоуровневые baseline tables и CLI mechanics остаются в Harness/tooling, а не дублируются в `AGENTS.md`.

`docs/TASK.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, Roadmap gameplay scope и `src/dnd_engine/**` не меняются этой capability, кроме обычной prospective terminal row в `docs/TASK.md` при Task Closure. `CLAUDE.md` меняется только если проверка покажет, что его существующая intentionally duplicated guidance стала неточной.

## Acceptance criteria

1. `ComputeProfile` содержит только `ROUTINE`, `DELIBERATE`, `CRITICAL`; routing policy не содержит hardcoded provider/model names или reasoning-effort strings.
2. Все operational routing decisions вычисляются pure deterministic code до invocation; implementer/reviewer output, prompt prose и `NonConvergenceDiagnosis` text не выбирают profile.
3. Initial checkpoint implementer использует `ROUTINE`; initial Task Closure preparation использует `ROUTINE`.
4. Первый implementation/closure repair без repeated basis и без второго verification rejection использует `DELIBERATE`.
5. Cumulative verification-rejection count текущего causal episode включает direct seeded upstream verification failure; count `>= 2` делает следующий implementation repair `CRITICAL`.
6. Exact `binding_basis`, повторившийся в RepairPacket, который управляет следующим repair, относительно любого более раннего RepairPacket того же causal episode, включая direct seed/upstream packet, делает следующий implementation repair `CRITICAL`.
7. Поздний `CHANGES_REQUESTED`, содержащий только ранее не встречавшиеся binding bases, не делает implementer `CRITICAL` без отдельного verification escalation signal.
8. First checkpoint/replay review использует `DELIBERATE`; local review iteration 2+ того же gate использует `CRITICAL`.
9. Первый review нового late-repair/closure-repair gate, candidate которого создан в прямой ответ на seed/upstream RepairPacket, использует `CRITICAL`, даже если локальный `review_iteration` равен нулю до invocation.
10. Seeded verification failure без upstream RepairPacket не повышает первый implementation-repair review выше `DELIBERATE` только из-за самого seed failure.
11. Pre-closure cumulative implementation review и любой Mode C review используют `CRITICAL` baseline независимо от предыдущей истории.
12. После `APPROVED` сложного checkpoint следующий initial ordinary checkpoint снова выбирает `ROUTINE`; после `CRITICAL` cumulative review initial closure preparation снова выбирает `ROUTINE`.
13. Replay/следующий gate не наследует предыдущую escalation lineage, кроме explicit direct seed packet/verification failure, которым существующий orchestrator причинно создаёт новый repair gate.
14. `BLOCKED`, malformed reviewer output, repeated candidate/no-progress, agent process failure и unavailable selected runtime profile не вызывают более сильный retry; существующий terminal/fail-closed behavior сохраняется.
15. Compute tier никогда не становится repair budget: достижение `CRITICAL` не создаёт terminal condition и дальнейшие iterations остаются под существующими v2 verdict/no-progress rules.
16. Для одной role все profile variants используют один и тот же executable и сохраняют role/cwd/timeout/env/capability assertions; provider switching через routing отсутствует.
17. CLI/config структурно требует implementer `ROUTINE`/`DELIBERATE`/`CRITICAL` и reviewer `DELIBERATE`/`CRITICAL` profile-specific argv; required composed argv различимы внутри role. Missing/empty/duplicate effective mappings fail configuration before first agent invocation.
18. Selected external profile failure не имеет fallback на другой tier/provider/model и завершает run через существующий fail-closed invocation path.
19. Все production implementer/reviewer invocation points operational v2 проходят через router; focused tests доказывают ordinary checkpoint, late repair/replay, cumulative review, closure и Mode C/post-publication paths.
20. Каждый фактический routed invocation добавляет один `RoutingDecisionRecord` до subprocess call; records имеют deterministic per-run order и сохраняются в `RunResult` для successful и blocked runs.

## Known constraints / edge cases

Все требования, ограничивающие execution, уже находятся в Goal, Scope, Out of scope, Approved implementation approach, Acceptance criteria и checkpoint Constraints; этот раздел только фиксирует дополнительный контекст для review.

- Provider-neutral Python harness может структурно проверить выбранный profile mapping, но не может заранее доказать, что конкретный external provider account имеет entitlement к model/profile или что provider интерпретирует opaque argv как ожидаемый reasoning effort. Фактический отказ external command остаётся fail-closed runtime failure.
- Exact `binding_basis` используется как identity routing signal. Семантически эквивалентные требования, записанные разными допустимыми `repo:*` references, считаются разными basis; TSK-0031 не вводит requirement graph или semantic normalization.
- Direct seed repair lineage нужна из-за существующих flows, где late repair создаёт новый `GateHistory` уже после finding/verification failure другого gate. Это не разрешение переносить всю историю upstream gate: causal bridge ограничен только packet/failure, который непосредственно вызвал child repair.
- Profile-specific argv остаются opaque и не логируются routing telemetry. Оператор отвечает за то, что каждый configured reviewer variant действительно сохраняет fresh one-shot context и sandbox/tool restrictions, заявленные существующими capability assertions.
- Первая empirical настройка соответствия concrete model/effort профилям и возможная корректировка baseline/escalation policy должны опираться на отдельный production pilot и накопленные `review_metrics` + `routing_decisions`; эта задача не предрешает последующий tuning.
