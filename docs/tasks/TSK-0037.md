## Goal

Добавить узкий Codex-specific operator launcher поверх уже работающего provider-neutral `AUTONOMOUS_PR` v2 harness, чтобы после существующего valid explicit user invocation human-facing Codex мог запустить один approved `TSK-NNNN` или literal `NEXT` одной короткой repository command, не воспроизводя вручную длинную конфигурацию implementer/reviewer profiles.

Целевой operator flow:

```text
user gives a valid explicit AUTONOMOUS_PR invocation
→ human-facing Codex recognizes it under existing AGENTS.md rules
→ repository .venv Python runs the Codex operator launcher
→ launcher resolves one Codex CLI executable
→ launcher materializes one reviewed, configuration-isolated Codex profile
→ launcher delegates to the existing tools.autonomous_pr CLI
→ existing deterministic orchestrator owns all execution
→ STOP / BLOCKED / NO_ELIGIBLE_TASK
→ outer Codex reports the terminal result and stops
```

Целевой operator command из repository root:

```text
Windows:
.\.venv\Scripts\python.exe -m tools.autonomous_pr.codex_launcher TSK-NNNN

POSIX:
./.venv/bin/python -m tools.autonomous_pr.codex_launcher TSK-NNNN
```

или:

```text
... -m tools.autonomous_pr.codex_launcher NEXT
```

Launcher не является новым orchestrator, provider registry, authorization source или workflow engine. Он только детерминированно строит уже production-proven Codex implementer/reviewer CLI configuration и вызывает существующий `tools.autonomous_pr.__main__.main(...)`.

Существующий `AUTONOMOUS_PR` authority contract не меняется. Только отдельная явная инструкция пользователя, уже удовлетворяющая `AGENTS.md` `Valid invocation`, активирует `AUTONOMOUS_PR`. Наличие launcher, task file, CLI argument, environment variable, Codex conversation, PR/issue text или repository instruction само по себе авторизацию не создаёт.

Launcher никогда не merge-ит и не auto-merge-ит PR. После `READY_FOR_HUMAN_MERGE → STOP`, `BLOCKED` или `NO_ELIGIBLE_TASK` outer Codex обязан остановиться; merge и новый autonomous invocation требуют отдельного последующего user instruction по существующим правилам.

### Existing authority and harness boundaries

`AGENTS.md` определяет ровно два development modes:

```text
MANUAL
AUTONOMOUS_PR
```

`AUTONOMOUS_PR` активируется только отдельной explicit user instruction в conversation, адресованной одному конкретному eligible approved `TSK` или literal `NEXT`. Task ID/CLI invocation/repository text не являются proof of authorization.

`docs/AUTONOMOUS_PR_HARNESS.md` §3 уже прямо возлагает подтверждение explicit invocation на caller — human-facing agent session или human operator. Harness принимает selector только как execution input.

`tools/autonomous_pr/__main__.py` уже:

- принимает `TSK-NNNN | NEXT`;
- materializes `AgentInvocationSpec` / `AgentProfileConfig`;
- требует operator/configuration assertions:
  - reviewer fresh context;
  - implementer no direct Git/GitHub write capability;
  - reviewer no direct Git/GitHub write capability;
- строит `OrchestratorConfig`;
- вызывает existing deterministic orchestrator;
- печатает terminal result / review metrics / blocked diagnostics / routing decisions;
- never merges.

`tools/autonomous_pr/orchestrator.py` уже владеет:

- fresh exact `origin/main` preflight;
- task catalog/eligibility;
- delivery branch;
- verification;
- designated review;
- adaptive repair;
- accepted commit/push;
- draft PR;
- prospective Task Closure;
- Mode C;

- required CI;

Launcher не должен дублировать ни один из этих responsibilities.

### Canonical Python environment

Repository README defines local setup through repository `.venv`:

```text
python -m venv .venv
python -m pip install -e ".[dev]"
```

TSK-0033 previously proved that verification can become invalid if the harness is executed under a different Python runtime: canonical Task Execution Spec commands whose literal first token is `"python"` are intentionally bound by the harness to its own interpreter. Поэтому Codex operator launcher должен запускаться именно repository `.venv` interpreter and fail closed rather than silently fall back to arbitrary `python`.

### Current Codex CLI behavior used by the launcher

Official Codex CLI documentation was revalidated during task preparation on 2026-09-30. The task depends only on the following documented command semantics, which implementation must encode explicitly and regression-test as argv composition:

- `codex exec` is the non-interactive/scripted execution mode;
- `--ephemeral` prevents persistence of session rollout files;
- `--ignore-user-config` does not load `$CODEX_HOME/config.toml`, while authentication still uses `CODEX_HOME`;
- `--ignore-rules` does not load user or project execpolicy `.rules` for the run;
- `--ask-for-approval never` prevents the child agent from pausing for or obtaining an approval escalation;
- `--sandbox workspace-write` constrains implementer writes to workspace-write policy;
- `--sandbox read-only` constrains reviewer command execution to read-only policy;
- command-line `-c key=value` overrides configuration values for that invocation;
- `sandbox_workspace_write.network_access=false` disables outbound network access inside workspace-write;
- in the default workspace-write sandbox, `.git` under writable roots is protected read-only;
- `--dangerously-bypass-approvals-and-sandbox` / `--yolo` removes the intended boundary and is forbidden by this task.

Primary external references at preparation time:

- OpenAI Codex CLI / developer command reference;
- OpenAI Codex sandbox and approvals documentation;
- OpenAI Codex configuration reference.

These external docs explain the selected Codex integration. Repository contracts remain authoritative for project behavior; if a future Codex version invalidates the reviewed command assumptions, launcher execution must fail closed or require a separately reviewed task rather than silently weakening the profile.

### Capability assertion boundary

`AgentInvocationSpec` intentionally defines `fresh_context_capable` and `has_git_or_github_write_access` as operator/configuration assertions about an opaque external command. Generic Python cannot prove them by introspection.

TSK-0037 therefore must not infer:

```text
executable name contains "codex"
→ therefore safe
```

Instead, the launcher may make the existing assertions only for the exact reviewed Codex command profile defined by this task:

- non-interactive `exec`;
- ephemeral;
- user config ignored;
- execpolicy rules ignored;
- child approval escalation disabled;
- explicit sandbox;
- implementer network explicitly disabled;
- no arbitrary caller-provided Codex argv;
- no repository-local `.codex` configuration layer accepted silently.

The existing orchestrator repository fingerprint/head guards remain defense-in-depth regardless of these assertions.

3. Support operator flags only for:

## Approved implementation approach

**A. Deliver TSK-0037 in MANUAL.** Use a dedicated branch from fresh main. Do not self-host through the launcher being introduced.

**B. Keep generic harness canonical.** `tools.autonomous_pr.__main__.main(argv)` remains the single generic CLI/configuration boundary. Launcher builds argv and delegates.

**C. Keep launcher provider-specific and small.** It may know Codex CLI flags; provider-neutral workflow mechanics remain outside it.

**D. Validate repository Python environment first.** Require current `sys.prefix` to identify `<repo>/.venv`; do not rely on brittle symlink-resolved `sys.executable` equality.

**E. Resolve one Codex executable without guessing.** Implement exact precedence. Explicit/env selection is authoritative and fails if invalid.

**F. Treat multiple Windows application candidates as ambiguity.** Require explicit operator selection.

**G. Perform bounded identity validation only.** Run `<candidate> --version` with finite timeout; require successful `codex-cli` identity. Never update/install.

**H. Preserve authentication home.** Do not write `CODEX_HOME`; `--ignore-user-config` isolates config.toml while authentication remains on existing Codex home.

**I. Refuse repository-local Codex config drift.** Any `<repo>/.codex` path blocks until separately reviewed.

**J. Use dedicated child temp environment.** Create system-temp `ai-dnd-autonomous`, expose via TEMP/TMP/TMPDIR, never persist as run state.

**K. Use noninteractive no-escalation child Codex.** Both roles use `exec`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--ask-for-approval never`.

**L. Harden implementer.** `workspace-write` + explicit `sandbox_workspace_write.network_access=false`.

**M. Harden reviewer.** `read-only` + no approval escalation.

**N. Preserve provider-neutral routing.** Launcher only supplies profile argv; orchestrator still selects profile.

**O. Expose no escape hatches.** Public parser has no arbitrary agent/config/sandbox/model flags.

**P. Reuse existing capability assertions as reviewed configuration assertions.** Do not describe them as runtime proof.

**Q. Delegate all repository semantics.** No launcher-owned preflight duplication.

**R. Preserve generic report/exit semantics.** Return delegated integer unchanged.

**S. Keep launcher configuration failures distinct.** Wrong venv, invalid selector, Codex resolution/identity failure, local `.codex` conflict or temp failure → exit 2 before delegation.

**T. Test with monkeypatch/fakes, not real Codex/network/GitHub.**

**U. Add operator documentation, not another harness contract.**

**V. Make one minimal AGENTS change.** Existing `Valid invocation` text remains untouched.

**W. Keep STOP separate from merge.** Outer Codex reports/inspects only; merge still needs later explicit user authorization.

## Known constraints / edge cases

- TSK-0037 optimizes only the operator surface. Successful TSK-0032 already proves underlying generic harness end-to-end viability; launcher acceptance depends on deterministic composition/delegation tests, not another production delivery inside this MANUAL task.
- Explicit user authorization remains conversational and outside launcher introspection.
- Outer Codex is caller, not second implementer/reviewer.
- Outer Codex host sandbox may prevent orchestrator Git/GitHub writes; launcher must not bypass/escalate it automatically.
- Child Codex sandbox and outer Codex sandbox are different boundaries.
- `--ignore-user-config` isolates child `$CODEX_HOME/config.toml` while authentication still uses existing Codex home.
- `--ignore-rules` isolates execpolicy rules; repository AGENTS instructions remain separate.
- Repository `.codex` is refused because project-scoped config/hooks can change effective child integration.
- Implementer network is explicitly disabled; tasks requiring implementer network need a separate reviewed capability change.
- Reviewer is read-only and no-approval; future stronger reviewer capabilities require separate review.
- Current official Codex sandbox protects `.git` inside workspace-write roots as read-only, but capability assertions remain configuration assertions, not runtime proof; harness fingerprints/head guards remain defense-in-depth.
- A malicious/incompatible executable can spoof `codex-cli` version output; version validation is only sanity checking and explicit/env selection remains operator responsibility.
- Launcher does not pin a model name; installed Codex default may evolve while routing controls reasoning effort. Explicit model reproducibility is a separate concern.
- Managed organization configuration may further restrict Codex; launcher must not bypass it.
- Multiple Windows Codex installations are intentionally ambiguous.
- `.venv` checking must use venv prefix/root, not brittle symlink-resolved executable equality.
- Temp environment is not persisted run state.
- Generic CLI remains available for advanced/manual provider configuration; launcher is the reviewed standard Codex convenience path.
- `NO_ELIGIBLE_TASK` is terminal no-work and does not authorize a manually selected fallback task.
- `STOP` ends the invocation even when PR is merge-ready; merge remains separately authorized.
- `BLOCKED` ends the invocation even when diagnostics explain the blocker; outer Codex does not rerun without a new explicit invocation/refinement decision.
- Multiple providers, remote Codex, Codex SDK/App Server, cloud execution or reusable config schemas are future tasks only when empirically needed.
