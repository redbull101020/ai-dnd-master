## Goal

Implement the first bounded Reaction-resource foundation required by a future Opportunity Attack. Track one Reaction resource per participant in active Combat: before it is spent, the resource is available, and a spent resource becomes available again only at the start of that same participant's next turn. Resource availability is distinct from gameplay eligibility: the foundation alone never grants permission to take a particular Reaction. Persist the spent-per-participant facts in existing Combat-owned State, model their use with an auditable `ReactionSpent` V1 Event/applier, and introduce strictly additive State schema V12 while preserving the current Action, Movement, Attack, Combat lifecycle, Event Envelope and historical State readers.

The first task **does not yet make a Reaction executable by a player/AI**. No production Command or Application handler may spend Reaction in isolation; a future concretely authorized Opportunity Attack consumer will produce `ReactionSpent` after a valid player/DM choice; it must not be fired automatically merely because a resource is free. This specification is a fully elaborated **planning draft**, not an authorized task invocation. The approved architecture decision must first be published as Architecture §3.41 / DEC-0058, and this exact execution specification must be independently reviewed, parser-validated, approved, and published on authoritative `main` before autonomous implementation can begin. A separate explicit `AUTONOMOUS_PR TSK-0023` invocation is required afterward.

## Scope

- Append `reactions_spent: frozenset[str] = frozenset()` to `CombatState` **after** `movement_spent` without changing earlier constructor argument positions. Record IDs of participants who spent a Reaction since their most recent own turn began. Enforce exact `frozenset` type, exact `str` entries, membership only in `combat.order` and no new owner or generalized resource model. `CombatState` remains mutable as today; serializer independently validates its current field and cross-field integrity to reject post-construction corruption.
- Introduce `ReactionSpent` V1 as a concrete immutable GameEvent (`payload` has exactly `combatId`), with an Event builder and pure `apply_reaction_spent_v1(combat, event) -> replacement CombatState`. A valid Event identifies the reacting participant as `actorId`, refers to the same active Combat, has a non-empty causal link to the concrete reaction-attack-resolution Event, and consumes a previously available Reaction even if the attack misses. Because the future attack producer does not exist in this slice, **no production handler is wired to emit this Event**; only Event builder/applier/serializer and their Domain tests are implemented now. The producer in the subsequent Opportunity Attack task is solely responsible for establishing valid trigger/attack authorization and resolving Attack before this Event.
- `CombatStarted` V1 applier initializes all reactions as available via `CombatState` default. `TurnAdvanced` V1 applier removes **only the new active participant's ID** from `reactions_spent`, preserving the spent facts for everyone else. Preserve the exact V1 Event payloads, Event ordering, `action_spent=False` and `movement_spent=0` new-turn projection, and the existing Character Death Save consequence ordering. `EndCombat` continues to discard the entire Combat projection.
- Upgrade the exact `StateSerializer` writer from V11 to V12 by adding mandatory `reactionsSpent` (a lexicographically sorted JSON list of unique participant IDs) **only inside a non-null V12 Combat object**, otherwise preserving all V11 field sets, Character walking speed, HP/lifecycle, Conditions, Inventory/Equipment, Action and Movement values. V12 `combat=null` remains valid. Decode V1–V11 under their original strict schemas; decode legacy non-null Combat as `reactions_spent=frozenset()` without pretending to recover a historical reaction fact. Reject V12-only fields in V1–V11 and reject missing/extra/wrongly typed/duplicate/nonparticipant entries in V12.
- Update deterministic tests and a concrete filesystem StateStore/turn-advance regression for the new field and legacy compatibility, without introducing a player-facing Reaction capability. When actual production implementation is delivered, update Architecture §3.41, §12.13, Roadmap's narrow capability commentary, CLAUDE's current writer reference, and append a factual DEVELOPMENT_LOG entry; broad Reactions and Opportunity Attacks remain unchecked.

## Approved implementation approach

1. Retain existing `CombatEngine` State Ownership and the current Action/Movement single-active-combatant model, but add a participant-specific Reaction resource to `CombatState`. New `reactions_spent` field is appended to preserve prior positional constructors; default is empty `frozenset`, with no per-participant dict or extra mutable resource entities. Constructor validates exact `frozenset[str]`, every member belongs to the unique `combat.order`, and the V12 serializer re-validates after object mutation. Normal `CombatState` replacement operations preserve the field unless explicitly consuming or resetting one participant.
2. Define `ReactionSpent` V1 Event with standard GameEvent Envelope (`type="ReactionSpent"`, `version=1`, `campaign_id`, `command_id`, UTC `timestamp`, `event_id`, `actor_id=<reactor ID>`, `caused_by=<reaction Attack-resolution Event ID>`). Payload contains exactly `{ "combatId": str }`; it excludes resource counts, round, active index, source target, hit status and other values derivable from the resolved Event chain. Use the exact pure builder signature `build_reaction_spent_v1(*, event_id: str, timestamp: datetime, command_id: str, campaign_id: str, actor_id: str, combat_id: str, caused_by: str) -> GameEvent`. It accepts the encompassing authorized Command's identity, explicit reacting actor identity, Combat identity and externally allocated metadata; it validates exact string types and a non-empty/non-whitespace-only `caused_by`, but **does not** manufacture a new Command, resolve the attack or consume Reaction. `GameEvent` enforces the existing UTC timestamp and Envelope contract. The future consuming Application use case must keep every Event's `command_id` equal to the encompassing Command/`ResolutionResult.command_id`. Its `ReactionSpent.actor_id` is the reactor and may differ from the Command actor if the reaction interrupts somebody else; no new Command-type or movement-interruption design is established by this foundation. A non-empty `caused_by` is a required reference, not proof that the event exists; the later Application consumer must supply a genuinely preceding attack-resolution Event in the same ordered batch.
3. Implement `apply_reaction_spent_v1` with strict Event type/version and exact payload validation, matching Combat ID, `actor_id` exact str and present in `combat.order`, non-null/non-empty exact-string `caused_by`, and the actor's ID absent from `combat.reactions_spent`; reject wrong/duplicate/stale Events with `TypeError`/`ValueError` integrity errors, not a gameplay `EngineError`. Return `dataclasses.replace(combat, reactions_spent=combat.reactions_spent | frozenset({actor_id}))`. Active-turn equality is **not** required; current `action_spent` and `movement_spent` never gate or change Reaction consumption. The builder/applier must not invoke dice, DefinitionSource, StateStore or Event metadata allocation. Reject empty or whitespace-only `caused_by`; an applier cannot independently verify the referenced Event exists without a future producing transaction.
4. In unchanged `CombatStarted` V1 projection, a new Combat begins with `reactions_spent=frozenset()`; do not add Event payload data. In `apply_turn_advanced_v1`, use the resolved `new_active_id` from the existing validated Event and project `reactions_spent=combat.reactions_spent - frozenset({new_active_id})` alongside existing `action_spent=False`/`movement_spent=0`. Do not clear all participants at round change; do not reset the previous actor at turn end. Confirm restoration on first-turn entry and round wrap, including a one-participant Combat. Preserve Start/Advance handler's single-save and existing automatic Character Death Save order and outcomes. There is no reaction reset Event V2: restoration is an agreed turn-start projection rule.
5. Persist strict, additive schema V12: introduce fixed `SCHEMA_V12_VERSION=12`; promote current `SCHEMA_VERSION` only when the full serializer implementation is complete. Define exact `_V12_COMBAT_FIELDS = _V10_COMBAT_FIELDS | {"reactionsSpent"}`; non-null V12 Combat requires `reactionsSpent` as a JSON list of exact strings, rejects duplicates/nonparticipants and unknown/missing keys, accepts either order for valid unique IDs and decodes to `frozenset`. Serialize in sorted ID order and independently validate the stored dataclass. V12 still uses V11 Character `walkingSpeed`, V10 Combat `movementSpent`, V8 Combat `actionSpent`, V9 Character lifecycle, V7 Combat `positions`, V6 Inventory/Equipment and Condition-era Creature fields. Audit **every version-branch dispatch**: allowed schema sentinels, V4+ Creature Conditions, V5+ Combat, V6+ Inventory/Equipment/weapon proficiency, V7+ positions, V8+ Action, V9+ Character lifecycle, V10+ Movement, and V11+ Character walkingSpeed, plus exact V12 Combat field decoding; V12 must not lose V11 data. All historical sentinels V1–V11 and strict field sets remain untouched; V5–V11 Combat decodes absent reaction facts to empty frozenset, V1–V4 keep `combat=None`. V12 with null Combat round trips with no additional root fields. Add invalid post-construction State mutation write rejection and nested-schema tests.
6. Add focused Domain/Event/serializer/Application/real-adapter tests. The Reaction Event is a prepared but not yet produced Domain foundation: do **not** add Application code that permits a free-floating reaction spend merely to produce an end-to-end test. Real adapter verification may seed valid `reactions_spent` in a trusted initial/test fixture, persist/reload, then exercise actual `AdvanceTurnHandler` through a fresh filesystem StateStore and assert only the new active combatant is restored. Assert the unchanged two-combatant Attack/Move scenario retains resource values and existing Event causality; no unnecessary edits to that scenario or any Attack/Move handler. After delivering code and tests, publish a concise truthful implementation-status update, not a claim of fully implemented Reactions/OA.

## Acceptance criteria

- `CombatState` has unchanged existing fields followed by exact `reactions_spent: frozenset[str] = frozenset()`; constructor rejects list/set/tuple/wrongly typed members and IDs not present in `combat.order`. V12 serializer also rejects corruption introduced after construction. Multiple spent participants and zero spent participants remain representable; `action_spent` and `movement_spent` values are independent.
- `ReactionSpent` V1 builder returns exact GameEvent Envelope and only `combatId` in payload with off-turn `actorId`, valid UTC timestamp, caller-provided encompassing `commandId`, non-empty `causedBy`; `EventSerializer` JSON round trip retains this identity. The builder has the exact keyword-only signature fixed in the binding implementation approach, without a premature dependency on `AttackCommand`. Event applier changes only one participant's Reaction membership and returns a replacement Combat; an actor can be non-active but must belong to current Combat.
- Invalid Event type/version/payload, mismatched Combat ID, unknown/null actor, missing/empty/whitespace-only causedBy and duplicate spend fail closed with `TypeError`/`ValueError`; loaded input Combat is unchanged. They do not return `ResolutionResult`, roll dice, save state or allocate new Event metadata. `RESOURCE_NOT_AVAILABLE` is reserved for the **future** Application consumer, not synthesized by the Domain applier.
- `CombatStarted` V1 initializes all Reaction resources as available, and `TurnAdvanced` V1 restores **only** the incoming active participant, including round wrap and one-participant order; existing Action/Movement resets and death-save orchestration remain unchanged. No extra Event or additional `StateStore.save()` is emitted by start/turn handlers.
- Production State writer is strict V12, with `reactionsSpent` mandatory in non-null Combat and lexicographically sorted on write; V12 null Combat remains valid. Values are a nonduplicated exact-string subset of `combat.order`; V12 reader accepts an unsorted valid list and canonical writer sorts it, while wrong types, duplicate IDs, missing/unknown fields, non-member IDs and bools are rejected. No extra V12 fields are accepted by V1–V11 readers; V5–V11 active Combat projects `reactions_spent=frozenset()` without historical guessing, while legacy `StateSnapshot` projections remain intact.
- Existing V11 state (Character walkingSpeed, Creature Conditions/HP, Character death-save state, Inventory/Equipment, Combat positions/actionSpent/movementSpent) survives exact V12 fresh-store write/reload. Existing Move→Attack→Move, TurnAdvanced, StartCombat and EndCombat regression suites pass unchanged or with mechanical exact-field fixture adjustments only.
- No standalone Reaction Command, no OA trigger, no new Attack/Move behavior or generic resource framework is added. Broad Roadmap `Reactions`, `Opportunity attacks` and `Movement` remain unchecked; docs distinguish implemented Reaction **foundation** from unimplemented gameplay Reaction consumer.

## Known constraints / edge cases

- SRD 5.1 restores a Reaction at the **start of its user's next turn**, not at the end of any turn or the start of the next round. Single-participant Combat must obey this rule. Using a Reaction during one's own turn does not create a second Reaction before the next turn begins.
- The current Engine does not model Surprise, hostility, visibility, incapacitation, teleportation or Disengage; no guess about these omitted facts is allowed in a reaction consumer. None is silently implemented by this resource task.
- `reactions_spent` is a current Combat projection, not a global Creature field or a reusable resource manager. A Creature outside `combat.order` must not acquire a spent Reaction entry.
- `ReactionSpent` V1 is a concrete prepared Event type, not evidence of an executable reaction. It will be emitted only when a later legal consumer resolves an authorized Reaction Attack and constructs its ordered Event batch. A rejected future attempt may not consume Reaction; a successful valid attempt consumes it even on a miss.
- V1–V11 legacy snapshot reads do not reconstruct unknown past Reaction history; empty-set projection is a compatibility convention, as with historical Action state. EventStore/replay and exactly-once across external retries are not present.
- No user instruction in this document constitutes commit/push/PR/merge authority. Publication and implementation are separate controlled steps under `AGENTS.md` and `docs/TASK.md`.
