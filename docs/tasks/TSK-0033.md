## Goal

Устранить два подтверждённых structural defects operational `AUTONOMOUS_PR` v2, обнаруженных при первом production pilot TSK-0032, не расширяя authority, review semantics или gameplay scope.

Первый результат: canonical verification argv с exact первым token `"python"` должен исполняться тем же Python interpreter, которым запущен harness process, а не зависеть от ambient Windows/PATH/base-interpreter resolution. Одновременно approved Task Execution Spec argv и записываемая verification evidence должны сохранять исходный provider-neutral command identity `"python"`, без machine-specific абсолютного пути.

Второй результат: уже существующая authoritative Full Verification evidence, accepted cumulative-review evidence и реальные draft-PR/implementation identities должны детерминированно доходить до prospective Task Closure. Closure implementer должен получать эти факты как единственный authoritative источник verification claims, а fresh designated Closure reviewer — тот же compact authoritative evidence context для проверки closure facts. Current review artifact Closure reviewer остаётся exact closure candidate diff; полный implementation patch не добавляется ему повторно и implementation review не выполняется заново.

Задача не утверждает, что отсутствие Full Verification evidence было единственной или непосредственной причиной explicit `BLOCKED` в первом TSK-0032 pilot: semantic reviewer rationale не был сохранён в terminal CLI result. Она исправляет независимо подтверждённый evidence-handoff gap и отдельно подтверждённый verification-runtime defect до повторного production pilot.

## Scope

1. Определить operational semantics exact verification executable token `"python"`: только когда `VerificationArgv[0] == "python"`, subprocess execution materializes первый argv element в current harness `sys.executable`.
2. Сохранить original approved verification argv как command identity и audit evidence; абсолютный interpreter path используется только на subprocess boundary и не заменяет `"python"` в `VerificationCommandResult.command`, Task Execution Spec или reviewer evidence.
3. Оставить все остальные executable tokens без Python-specific normalization: `python3`, `python.exe`, `py`, абсолютные/относительные executable paths, `git` и любые другие команды продолжают использовать существующую direct argv semantics.
4. Fail closed через существующий verification failure path, если materialized current Python interpreter нельзя фактически запустить; не добавлять PATH fallback, interpreter discovery или alias chain.
5. Добавить deterministic prospective-closure evidence consistency validation поверх уже существующих typed objects: successful Full Verification обязана существовать и быть bound к тому же fixed spec/base/accepted implementation HEAD, что и accepted pre-closure cumulative review.
6. Сформировать один deterministic compact closure evidence representation из existing `V2PreClosureExecutionResult` и реального draft PR context. Он должен содержать fixed spec identity, draft PR number, accepted base/head identities, Full Verification verified HEAD и per-command original argv/returncode/pass facts, а также accepted cumulative-review identity.
7. Передать этот authoritative evidence representation в initial Task Closure preparation и каждый closure-only repair; closure implementer продолжает получать accepted implementation patch как source для factual delivery summary.
8. Передать тот же authoritative verification/identity/PR evidence representation в fresh designated Closure reviewer. `CURRENT_PATCH` reviewer'а остаётся exact prospective closure diff; accepted full implementation patch не добавляется в Closure review input.
9. Явно ограничить closure implementer: verification claims в `docs/DEVELOPMENT_LOG.md` выводятся только из supplied authoritative evidence; implementer не запускает verification заново ради closure prose, не придумывает test counts и не объявляет собственный self-check accepted evidence.
10. Сохранить existing closure-only repair semantics: если authoritative evidence доступна, но closure candidate неточно или неполно отражает factual verification/PR facts, designated reviewer может вернуть обычный repairable `CHANGES_REQUESTED` с closure-only paths.
11. Сохранить existing implementation-affecting repair/replay semantics: после candidate-changing implementation repair старые Full Verification/cumulative facts не переносятся в новую closure; новый handoff строится только из актуального replayed `V2PreClosureExecutionResult`.
12. Синхронизировать `docs/AUTONOMOUS_PR_HARNESS.md` с exact `"python"` runtime semantics и complete closure-evidence handoff. Обновить локальные code comments/docstrings там, где current wording `"run exactly supplied argv"` или prospective-closure handoff становится неточным.
13. Добавить focused regressions для обоих production defects и выполнить полный tooling/repository regression, требуемый для изменения executable tooling behavior.

## Approved implementation approach

**A. Delivery and authority boundary.** TSK-0033 реализуется и доставляется в `MANUAL` на отдельной branch от fresh `main`. Task document не разрешает commit, push, PR или merge заранее. Не использовать `AUTONOMOUS_PR NEXT` для доставки этой задачи: пока TSK-0032 остаётся approved P1 с меньшим ID, deterministic NEXT может выбрать именно TSK-0032. Никакая часть реализации не должна менять authority contract, чтобы разрешить harness исправлять собственные permissions.

**B. Exact canonical Python token.** В verification runner ввести узкий materialization step непосредственно перед `subprocess.run`. Если original argv начинается ровно с `"python"`, runtime argv начинается с текущего `sys.executable`; остальные элементы копируются byte-for-byte как Python strings. Любой другой первый token выполняется существующим способом без специального преобразования. Это intentional operational-contract amendment для canonical verification commands, а не общая executable-resolution abstraction.

**C. Evidence identity remains provider- and machine-neutral.** `VerificationCommandResult.command` хранит original Task Execution Spec argv, например `("python", "-m", "pytest")`, даже если process boundary фактически использовал absolute `sys.executable`. `_format_verification(...)` и downstream reviewer/closure evidence показывают approved command identity, return code, pass/fail и verified HEAD, а не machine-specific runtime path. Не добавлять runtime path в stable CLI telemetry.

**D. Existing subprocess and failure behavior stays narrow.** Не изменять agent executable materialization, Git/GitHub subprocesses или environment ownership. Не модифицировать process-wide `PATH`. Если current `sys.executable` unusable, verification завершается через существующий fail-closed subprocess/verification error path; запрещён automatic retry через `python`, `python3`, `py` или другой interpreter.

**E. Deterministic closure-evidence consistency guard.** До первого Task Closure implementer invocation и при каждом rebuilt closure orchestrator проверяет, что `pre_closure.completed` true, `full_verification` и `cumulative_review` существуют, Full Verification overall passed, обе evidence принадлежат fixed spec, используют согласованный accepted base context и относятся к одному accepted implementation HEAD. `full_verification.head_sha`, nested `VerificationEvidence.head_sha`, `cumulative_review.reviewed_head_sha` и expected published implementation HEAD должны быть согласованы по существующему execution model. Missing, failed, stale или inconsistent evidence завершает flow fail-closed до LLM continuation; LLM не решает freshness.

**F. One deterministic compact closure evidence representation.** Построить один internal formatter/helper поверх existing typed evidence rather than обязательную новую persistent model abstraction. Representation включает как минимум: selected task/spec identity; actual draft PR number; accepted implementation base and HEAD; Full Verification verified HEAD; overall Full Verification pass fact; original argv, returncode и pass fact каждой command; accepted cumulative review base/head и review iteration. Successful command stdout/stderr не требуется и не включается. Если при реализации отдельный frozen helper value object существенно уменьшает duplicated parameters и улучшает type safety, его можно добавить как private/provider-neutral structure, но он не становится persisted schema или new public lifecycle contract.

**G. Closure implementer grounding.** `_build_v2_closure_prompt(...)` продолжает передавать actual PR number и accepted implementation patch, но дополнительно получает deterministic closure evidence representation. Prompt фиксирует, что supplied evidence является единственным authoritative source для verification claims. Delivery Log остаётся concise: implementer может суммировать command categories вместо копирования всех argv, но не должен выдавать partial subset за полный verification story, запускать проверки повторно ради narration или придумывать numeric pass counts, отсутствующие в structured evidence.

**H. Closure reviewer grounding without scope expansion.** `_build_v2_closure_review_input(...)` получает тот же compact authoritative evidence representation и exact closure candidate diff. Reviewer проверяет factual PR/verification/head claims и applicable closure/terminal/governance requirements. Full accepted implementation patch в этот prompt не добавляется: pre-closure cumulative implementation review уже его принял, а Closure Review не повторяет этот gate.

**I. Repair and replay freshness.** Closure-only repair сохраняет implementation HEAD и может reuse ту же evidence после повторной deterministic consistency check. Любой implementation-affecting repair использует existing conservative replay: accepted repair, checkpoint replay where required, new Full Verification and new cumulative implementation review occur before rebuilding closure. Closure evidence всегда recomputed from current `V2PreClosureExecutionResult`; stale text block не хранится как mutable cross-gate state.

**J. Documentation ownership.** `docs/AUTONOMOUS_PR_HARNESS.md` уточняет существующие operational sections rather than создаёт parallel runtime version: exact `"python"` verification token semantics принадлежат Task Execution Spec/deterministic verification boundary; complete closure evidence handoff belongs explicit handoff and unpublished-closure sections. Existing §§20–36 не перенумеровываются. `AGENTS.md`, `docs/TASK.md`, `docs/ARCHITECTURE.md`, `docs/ROADMAP.md` и `docs/DECISIONS.md` не меняются, если implementation не обнаружит фактическое противоречие; в таком случае не выбирать вариант молча, а остановить MANUAL implementation для отдельного решения. `CLAUDE.md` проверяется и меняется только если его deliberately duplicated operational guidance фактически становится неверной.

**Advisory expected touchpoints.** Наиболее вероятны `tools/autonomous_pr/orchestrator.py`, `tests/tools/autonomous_pr/test_orchestrator.py`, `docs/AUTONOMOUS_PR_HARNESS.md`; `tools/autonomous_pr/task_spec.py` может потребовать только docstring/comment sync для `"python"` semantics. `tools/autonomous_pr/model.py` меняется только если private typed helper доказанно уменьшает duplication. Не создавать новый production module только ради этой задачи.

## Acceptance criteria

1. При verification command с exact первым token `"python"` process запускается через current harness `sys.executable`.
2. Original approved argv остаётся неизменённым в `VerificationCommandResult.command`, formatted verification evidence и fixed Task Execution Spec.
3. Machine-specific absolute Python path не становится command identity, task-spec mutation или stable routing/review telemetry.
4. `python3`, `python.exe`, `py`, explicit Python paths, `git` и прочие executables не получают `"python"`-specific normalization.
5. Реализация не меняет global/process `PATH`, не использует shell и не добавляет interpreter discovery/fallback.
6. Harness, запущенный из repository virtual environment, выполняет canonical `["python", ...]` verification через тот же virtual-environment interpreter без operator workaround с системным Python.
7. Existing checkpoint Verification и Full verification используют одну и ту же exact `"python"` materialization semantics.
8. Successful `V2FullVerificationEvidence` остаётся bound к fixed spec, accepted base context и exact implementation HEAD.
9. До prospective Task Closure deterministic code подтверждает наличие, success и identity/SHA consistency Full Verification и accepted cumulative-review evidence.
10. Missing, failed, stale или inconsistent closure evidence приводит к fail-closed outcome до Task Closure implementer/reviewer invocation, а не к LLM inference.
11. Initial Task Closure implementer получает actual draft PR number, accepted implementation identities, accepted implementation patch и authoritative compact Full Verification/cumulative evidence.
12. Closure implementer использует supplied evidence как единственный authoritative source verification claims и не запускает verification повторно ради Development Log.
13. Closure implementer не выдумывает test counts или проверки, отсутствующие в structured evidence; concise factual summarization permitted.
14. Fresh Closure reviewer получает actual draft PR/accepted implementation identities и тот же compact authoritative Full Verification/cumulative evidence.
15. Closure reviewer `CURRENT_PATCH` остаётся exact prospective closure diff; full accepted implementation patch не добавляется в Closure Review input.
16. Closure Review остаётся closure-scoped и не повторяет pre-closure cumulative implementation review.
17. Если evidence существует, но closure candidate неверно отражает factual PR/verification facts, existing closure-only `CHANGES_REQUESTED` repair path остаётся доступным.
18. Closure-only repair может reuse всё ещё fresh implementation evidence только после deterministic consistency check.
19. Implementation-affecting repair не переносит stale Full Verification/cumulative evidence; новая closure строится после существующего repair/replay и новых downstream evidence.
20. Existing `APPROVED` / `CHANGES_REQUESTED` / `BLOCKED` semantics, binding-basis contract, non-convergence, no-progress and cycle detection остаются неизменными.
21. Adaptive compute routing, routing telemetry, profile baselines/escalation/de-escalation и external agent configuration остаются неизменными.
22. A/B/C review ranges, unpublished closure ordering, Mode C exact-candidate rule, required CI ordering и human-only merge остаются неизменными.

24. Gameplay/canonical D&D Architecture, `src/dnd_engine/**`, Roadmap gameplay scope и production dependency set не меняются.
25. Focused verification-runtime/closure-handoff regressions проходят.
26. Полный `tests/tools/autonomous_pr` suite проходит.
27. Полный architecture/process suite проходит.
28. Полный repository pytest проходит.
29. Configured mypy для `src/dnd_engine` и `tools/autonomous_pr` проходит.
30. `git diff --check` проходит на final MANUAL candidate.
31. Финальный diff не включает repair или closure PR #111/TSK-0032 и не создаёт unrelated refactor.
32. Повторный empirical production TSK-0032 pilot остаётся отдельным post-merge validation action и не используется как substitute для deterministic tests TSK-0033.

- Required result: Exact first token `"python"` materializes to current `sys.executable` только на subprocess boundary; original approved argv остаётся command/evidence identity; non-`"python"` executables сохраняют прежнее поведение; focused regressions доказывают virtual-environment binding, identity preservation и отсутствие alias/PATH fallback.
- Constraints: Не менять Task Execution Spec files/JSON argv representation, не переписывать `"python"` на stored absolute path, не менять global `PATH`, не нормализовать `python3`/`python.exe`/`py`, не добавлять generic resolver/fallback, не затрагивать agent/Git/GitHub subprocess boundaries и не добавлять dependency.

- Review focus: Exact token boundary; `sys.executable` materialization only at process invocation; original argv retained in evidence; fail-closed behavior; no hidden PATH/provider/agent side effects.

## Known constraints / edge cases

- Первый production TSK-0032 pilot является diagnostic history, а не resumable run state. Explicit `BLOCKED` завершил invocation; TSK-0033 не должна пытаться продолжать его in-memory gate history или unpublished closure candidate.
- Draft PR #111 и remote implementation branch сохраняют evidence первого pilot до отдельного human cleanup decision, но не являются implementation base TSK-0033 и не должны попадать в её diff.
- Semantic rationale explicit Closure reviewer `BLOCKED` из первого pilot не сохранён в terminal result. Поэтому задача фиксирует confirmed closure evidence-handoff gap, но не приписывает ему недоказанную причинность конкретного verdict.
- После публикации TSK-0033 на `main` TSK-0032 и TSK-0033 могут одновременно оставаться approved P1 nonterminal tasks; deterministic `NEXT` предпочитает меньший eligible numeric ID. Это не меняет selection contract и является дополнительной причиной доставлять TSK-0033 явно в MANUAL, а не через `NEXT`.
- Exact `"python"` semantics намеренно привязывают verification к interpreter текущего harness process. Оператор по-прежнему отвечает за запуск harness из environment с установленными repository dev dependencies; изменение не устанавливает packages и не создаёт environment manager.
- Original argv остаётся audit identity даже при materialized `sys.executable`; это означает, что evidence показывает approved command, а не machine-specific process path. Runtime path может использоваться внутренне для исполнения и ошибок, но не становится новым provider-neutral task contract.
- Closure handoff не требует numeric pytest counts. Если будущая задача действительно потребует structured test-count telemetry, это отдельный contract problem; TSK-0033 не извлекает counts из free-form stdout.
- Existing `_format_verification(...)` уже не включает stdout/stderr успешных commands. Если implementation использует его для compact closure evidence, fail-closed consistency guard должен гарантировать successful overall evidence до handoff.
- Повторный production TSK-0032 pilot после merge TSK-0033 является empirical validation исправленного harness. Его результат может выявить дополнительные runtime defects, но не изменяет acceptance TSK-0033 задним числом.
