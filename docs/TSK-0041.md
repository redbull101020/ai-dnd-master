## Goal

Fix the observed local Codex-chat delivery-path blocker in `AUTONOMOUS_PR` without weakening the existing deterministic harness or the sandbox restrictions of its implementer/reviewer child agents.

After this task, a valid explicit user invocation such as:

```text
AUTONOMOUS_PR TSK-0040
```

issued in a supported local Codex chat must lead the outer Codex to launch the existing repository operator command through the Codex client's sandbox-escalation / approval boundary before the generic harness starts:

```text
Windows:
.\.venv\Scripts\python.exe -m tools.autonomous_pr.codex_launcher TSK-0040

POSIX:
./.venv/bin/python -m tools.autonomous_pr.codex_launcher TSK-0040
```

The host-level launcher/harness process remains the sole owner of `git fetch`, delivery-branch creation, commit, push, `gh` draft-PR operations, and other already-authorized repository side effects. The existing implementer and reviewer child Codex profiles remain independently sandboxed with `workspace-write`, `approval_policy=never`, network disabled, and no Git/GitHub write capability.

The repository-level `AUTONOMOUS_PR` authorization and the Codex product's sandbox approval are separate controls:

```text
explicit user AUTONOMOUS_PR invocation
    → authorizes the bounded repository workflow

outer Codex sandbox escalation / approval
    → permits the one operator-launcher process to cross the local sandbox boundary

child implementer/reviewer profiles
    → remain restricted exactly as today
```

The outer Codex must request the required sandbox escalation before launching the operator command when its current execution context would otherwise protect `.git` or block required Git/GitHub network operations. It must not first run the launcher inside the known-insufficient sandbox, wait for `git fetch origin` to fail, and then retry implicitly.

If the active Codex surface/configuration cannot surface or grant the required sandbox escalation, or the escalation is denied, the run stops fail-closed and reports the outer execution-boundary blocker. It must not bypass the boundary by performing Git/GitHub writes directly, weakening the implementer/reviewer profiles, modifying user Codex configuration, or falling back to an independently executed PowerShell workflow.

This task changes the `AUTONOMOUS_PR` outer operator permission/dispatch contract and therefore must itself be delivered through the repository's `MANUAL` development mode. Do not execute TSK-0041 through `AUTONOMOUS_PR`. The task remains an approved execution-ready S task because execution readiness is independent from delivery mode.

## Approved implementation approach

### Delivery-mode constraint for TSK-0041

TSK-0041 changes the operational outer permission/dispatch contract of `AUTONOMOUS_PR`. Deliver it in `MANUAL` mode.

Do not invoke `AUTONOMOUS_PR TSK-0041` and do not use literal `NEXT` to attempt to deliver this task autonomously. The existing bounded-authority rule forbids an ordinary autonomous run from changing the rules that define `AUTONOMOUS_PR`'s own authority or permission boundary.

The implementation may add this approved task document and its code/documentation/test changes on the same dedicated MANUAL branch. Publication of the task document is not itself an autonomous invocation.

### Responsibility boundaries

The post-change responsibility model is exactly:

```text
User
    → gives valid explicit AUTONOMOUS_PR <TSK|NEXT> repository authorization

Outer local Codex chat
    → recognizes the valid invocation
    → requests the product sandbox escalation needed for one launcher command
    → does not independently perform harness Git/GitHub work

Approved outer launcher process
    → runs existing tools.autonomous_pr.codex_launcher
    → delegates to existing provider-neutral generic CLI/orchestrator

Generic harness
    → owns fetch / branch / deterministic verification / commit / push / draft PR / CI observation
    → remains bounded by the existing AUTONOMOUS_PR authority

Implementer child Codex
    → existing workspace-write / approval-never / network-off profile
    → edits working files only
    → no Git/GitHub write capability

Reviewer child Codex
    → existing disposable snapshot
    → existing workspace-write / approval-never / network-off profile
    → no Git/GitHub write capability
```

Outer escalation broadens only the deterministic launcher/harness process relative to the current Codex-chat sandbox. It does not flow as an authority grant into implementer/reviewer behavior; those are separate Codex child invocations that explicitly materialize their existing restricted profiles.

### Exact local chat dispatch rule

After a valid explicit invocation, the outer Codex must use the existing repository launcher command and must treat it as one side-effecting orchestration unit.

For Windows:

```text
.\.venv\Scripts\python.exe -m tools.autonomous_pr.codex_launcher <selector>
```

For POSIX:

```text
./.venv/bin/python -m tools.autonomous_pr.codex_launcher <selector>
```

`<selector>` is exactly the authorized canonical `TSK-NNNN` or literal `NEXT`.

When the current outer Codex session is in a bounded sandbox and the launcher requires writes/network outside that boundary, the outer Codex requests sandbox escalation for this launcher command before execution. It does not separately escalate individual later `git`/`gh` commands because those operations are internal deterministic steps of the already-authorized harness.

If the current product surface/configuration cannot request that escalation, if policy forbids it, or if the approval is rejected, the outer Codex reports terminal inability to start the harness and stops. It does not translate that failure into permission to perform the workflow manually.

### Authorization versus approval

Repository authorization remains unchanged:

```text
valid user AUTONOMOUS_PR instruction
```

is required before the launcher may be dispatched.

Codex product approval is separate:

```text
sandbox escalation approval
```

only determines whether the already-authorized launcher process may execute outside the current sandbox.

Therefore:

```text
approval without AUTONOMOUS_PR invocation
    → no autonomous repository workflow

AUTONOMOUS_PR invocation without available/approved outer escalation
    → fail closed before useful harness execution

AUTONOMOUS_PR invocation + approved outer execution
    → existing harness owns the bounded workflow
```

Do not describe product approval as commit/push/merge authorization. Commit/push/draft-PR authority still comes exclusively from the existing bounded `AUTONOMOUS_PR` contract; merge remains separate and human-only.

### Supported outer profiles

The repository documents capabilities, not user-machine configuration.

The preferred local Codex chat profile is conceptually:

```text
sandbox_mode = workspace-write
approval policy can surface sandbox escalation
approval reviewer = user or auto_review
```

The implementation may name current Codex configuration terms (`on-request`, granular `sandbox_approval`, `auto_review`) in operator guidance, but it must not make repository correctness depend on editing a particular user config file.

An outer `workspace-write + approval_policy=never` chat cannot satisfy this workflow because spawned commands inherit the outer sandbox and the required escalation cannot surface. The operator guide must diagnose that combination rather than instructing repeated retries.

User-selected full access is a sufficient outer environment but is not a repository requirement and is not automatically enabled or recommended as the ordinary fix.

### Harness behavior remains unchanged

Do not add a fallback to `repository.fetch_origin`, `fetch_and_capture_origin_main_sha`, branch creation, commit, push, or `gh` code.

Do not catch `.git/FETCH_HEAD` permission failure and pretend freshness was established.

Do not replace fetch with `ls-remote`, cached refs, GitHub API reads, or caller-supplied SHAs.

The fix is upstream of the harness: place the existing launcher/harness process in an execution context capable of carrying out the side effects the repository already authorizes.

### Child security remains unchanged

`tools/autonomous_pr/codex_launcher.py` remains the source of the fixed child profile materialization.

The implementation must preserve the existing exact-argv regressions that prove implementer/reviewer still receive their restricted profiles. No outer permission wording may be interpreted as permission to remove:

```text
--sandbox workspace-write
approval_policy=never
sandbox_workspace_write.network_access=false
windows.sandbox=mxc   # Windows child roles
```

or to change the no-Git/GitHub-write capability assertions.

### Product-surface boundary

This task targets local Codex surfaces capable of running repository shell commands and surfacing sandbox escalation/approval, such as supported desktop/IDE/CLI local sessions.

Do not claim equivalent behavior for ChatGPT web, remote cloud workspaces, or another surface whose local sandbox/approval model is materially different.

The repository contract must fail closed when the current surface lacks the required capability rather than inventing a provider-specific bypass.

### Verification strategy

Automated tests cannot simulate the host application's actual approval UI, so the repository-level proof is intentionally split:

1. deterministic contract tests prove the outer Codex instructions require approval-aware launcher dispatch and fail-closed behavior;
2. existing launcher unit tests prove the child security profiles and generic argv remain unchanged;
3. repository-wide regression tests and type checks prove no harness behavior was accidentally modified;
4. the first post-merge real Codex-chat `AUTONOMOUS_PR` invocation is operational evidence of product integration, but it is not manufactured by a test double and is not required to weaken the task's deterministic checks.

No test should pretend to prove that `auto_review` or a human approval UI will approve a specific real command.

## Known constraints / edge cases

- This task addresses local Codex chat execution where the client can run repository shell commands and can surface sandbox escalation/approval. It does not claim all ChatGPT/Codex surfaces expose the same controls.
- The repository cannot force the host Codex client to offer an approval prompt. The active client, user policy, and organization policy remain external enforcement layers.
- An outer session configured so that sandbox escalation prompts cannot surface cannot run chat-native `AUTONOMOUS_PR`; repeated retries in the same profile are not a fix.
- `approvals_reviewer=auto_review`, where available, may reduce human interruption but does not guarantee approval of every request and does not change the sandbox boundary by itself.
- Full access is not required by the repository design. A user may independently choose it, but the task neither enables nor recommends it as the default.
- The launcher cannot escape the parent sandbox by passing different arguments to its child processes. Descendants inherit the outer boundary until the product grants the outer launcher execution itself a broader boundary.
- The existing child `windows.sandbox=mxc` setting solves a different problem: it selects the Windows sandbox backend for implementer/reviewer child Codex processes. It does not grant the parent launcher process permission to write the checkout's protected `.git`.
- Product sandbox approval is not repository commit/push/PR/merge authorization. The existing `AUTONOMOUS_PR` bounded authority remains the only repository authority for its Git/GitHub side effects, and merge remains human-only.
- The first post-merge real Codex-chat invocation is the meaningful end-to-end proof that the current product surface honors the published operator contract. Repository tests can prove the instructions and child configuration but cannot emulate the host application's approval UI honestly.
- If current Codex product terminology changes later, documentation may be updated without changing the invariant: the outer launcher process must execute in a boundary capable of the harness-owned Git/GitHub operations, while implementer/reviewer children remain separately restricted.
- TSK-0040 remains a separate approved gameplay task. TSK-0041 changes only the delivery path used to run future autonomous tasks.
- No persistent host helper, service, plugin, or new dependency is required for this slice.
- Because TSK-0041 changes AUTONOMOUS_PR's own outer permission/dispatch contract, its implementation and review are intentionally MANUAL even though the specification is approved and execution-ready.
